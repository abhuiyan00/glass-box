    Iterated Local Search

    A metaheuristic with exactly four moving parts: an initial solution, a local search that descends to a local optimum, a perturbation that kicks the solution far enough to escape that optimum but not so far as to restart, and an acceptance criterion deciding whether to keep the new basin. Everything interesting is in the perturbation strength — too weak and it falls straight back into the same optimum, too strong and it degenerates into random restart.

    Unlike a genetic algorithm it carries no population, so there is no selection pressure and no crossover; the entire search is one trajectory. That makes it cheap per iteration and easy to reason about, and it is why the implementation in optimization-methods fits in one header and one source file while the GA needs a parameter block.

    #The concrete instantiation

    Built for permutation-flow-shop-scheduling in first_project, minimising total flow time:

    Part Choice
    Initial solutionNEH heuristic — order jobs by descending total processing time, insert one at a time at the best position found so far
    Local search1-shift insertion, first-improvement — remove a job, reinsert it at every other position, take the first improving move
    PerturbationRandom swaps, strength 4
    Restartafter max(200, maxIter/5) non-improving iterations
    Stopiteration budget, with an optional wall-clock cap

    Two details are worth pulling out because they are the ones that usually get skipped.

    First-improvement, not best-improvement. The local search takes the first improving reinsertion rather than scanning the whole neighbourhood for the best one. On a 500-job instance that difference is the whole runtime budget.

    A stagnation restart on top of the perturbation. Perturbation escapes a local optimum; the restart escapes a region of local optima. Having both is what separates this from a simple perturbation-loop, and the max(200, maxIter/5) floor means small budgets still get at least one patience window rather than restarting constantly.

    #Where it lands

    ILS is one of the five racers in first_project, plotted in purple across all six convergence figures. It was also the last method added, and the commit sequence is unusually legible for this repo — feat: add ILS interface → config: add ILS parameters → build: include ILS source file in CMake target → feat: add ILS implementation with NEH init, insertion local search, and perturbation loop → feat: integrate ILS runs and parameter sweeps in experiment runner. Five commits, interface before implementation, build wiring in the middle. That incremental shape is part of why first_project reads as a genuine working log rather than an import — see import-finished-work-into-git.

    Two of its parameters get their own sensitivity sweeps (param_ilsMaxIter.png, param_perturbStrength.png), so the strength-4 choice is at least plotted even if the reasoning is not written down.

    #Relation to other local-search work

    The same descend-then-escape structure appears in max-cut-and-local-search over in discrete-mathematics-laboratories, where a randomised local search is preferred to an exact solver for the same reason: the neighbourhood is cheap and the exact method does not scale. The multi-depot-vehicle-routing project a term later drops trajectory methods entirely for a population GA, because there the hard sub-problem is a partition and crossover on the depot gene is the lever that moves it.
