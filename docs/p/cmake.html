    CMake

    Cross-platform build-system generator: a CMakeLists.txt describes targets, and CMake emits Makefiles, Ninja files or an MSVC solution for whatever toolchain is present. The usual reason to reach for it in a C++ project is portability — one description, many generators.

    It appears once in optimization-methods, for first_project's permutation-flow-shop-scheduling benchmark, and is not carried forward.

    #The broken first line — a §10 contradiction, both claims recorded

    For the entire life of the coursework, first_project/CMakeLists.txt opened with:

    cmake_minimum_required(3.16)
project(PFSP)

    The VERSION keyword is missing. The command's signature is cmake_minimum_required(VERSION <min>), so cmake_minimum_required(3.16) is a hard configure error, not a warning. The rest of the file is fine — C++17 required, include_directories(include), a single pfsp executable over the 12 sources — but nothing downstream ever ran, because configuration aborted on line 1.

    It now reads cmake_minimum_required(VERSION 3.16) / project(PFSP CXX), repaired on 2026-08-01:

    Optimization Methods, git commit d116a84 "Fix the CMake invocation that stopped the build configuring", 2026-08-01

    The naming of the language in project() is the second half of the same repair and easy to miss. project(PFSP) enables C and CXX by default, so CMake probes for a C compiler this project never uses — a second failure waiting behind the first. The commit says so in its own words, and says it triaged before repairing: "all twelve sources compile clean under g++ -std=c++17, so the C++ was never the problem. Verified by an out-of-source configure and build that links pfsp.exe." Fixing only the visible error would have moved the failure rather than removed it.

    What follows is the analysis of why the defect survived so long. The repair does not touch it: it is dated 2026-08-01, three weeks after the course ended, and its own message records that the project still has no unit tests. Nobody hit this by following the README, which is the point.

    The README nonetheless presented CMake as the recommended build path. So for the whole course the documented happy path did not work as written, which lines up with the other evidence: a prebuilt pfsp.exe is committed and kept current (287876f build: update compiled pfsp executable), tracked despite the root .gitignore carrying an *.exe rule. The executable was the actual run path; CMake was aspirational.

    confidence: high — both versions of the file read directly. The repaired configure step is not independently re-run here: CMake is not installed on the auditing machine, so the only evidence that it now configures is the commit's own statement that it was verified out-of-source. That is weaker evidence than reading the file, and is worth less than it looks — see the residual gap below.

    This is a distinct species of documentation-drift: not documentation that fell behind working code, but documentation for code that never worked. Ordinary drift is caught by anyone following the README; this was not, which is the tell that nobody followed it — including the author, who had a working binary.

    The repair did not reach the README. first_project/README.md still says "From repository root: cmake -S . -B build", and there is no CMakeLists.txt at the git repository root — it is in first_project/. Read as written, against the root the sentence names, the command still fails; read as "the project root", it now works. One line of the documented path is fixed and the line above it is still ambiguous. confidence: high on the file layout, low on which root the sentence means.

    #Dropped for the second project

    final_project/mdvrp does not use CMake at all. It has a hand-written Makefile (-std=c++17 -O2 -static -Wall -Wextra) plus raw g++ invocations recorded in docs/commands.txt, building six executables from one header-only include tree. For a standard-library-only, header-only-dependency project targeting one toolchain (MinGW), a 20-line Makefile does genuinely carry less ceremony than CMake — but the switch is undocumented.

    • TODO: no recorded reason for dropping CMake between the two projects. Whether the broken cmake_minimum_required line was ever hit and prompted the switch, or the Makefile was simply preferred, is unrecoverable from the repo. confidence: low on the causal link.
    • TODO: the "recommended" CMake instructions in first_project/README.md still name the repository root, which holds no CMakeLists.txt. The build file was repaired on 2026-08-01 and the sentence pointing at it was not, so the documentation is now one step behind the code rather than ahead of it — ordinary documentation-drift, where it used to be the rarer kind.

    #Build verification across the repo

    There is no CI anywhere — no .github/, no build check. The claim that all seven C++ sources compile clean under -std=c++17 -O2 -Wall is attested by hand in docs/DATA_VERIFICATION.md, dated 2026-07-09, by the author. That is the same auditing-instead-of-testing posture as the rest of the repo — see generated-audit-artifact and the absence of any unit tests noted on optimization-methods.
