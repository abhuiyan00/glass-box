    Clean-Room Rebuild From Specification

    A clean-room rebuild implements a required outcome from independently written requirements and contracts rather than by adapting an existing source tree. It preserves the problem to solve, not another implementation's expression of that problem.

    The pattern is useful when the deliverable needs a domain model, operations, and observable behaviour, while source files and other expressive artefacts must remain outside the new work.

    #Establish the boundary first

    Write down the inputs that are legitimate to use: requirements, public interfaces, and facts needed to describe the desired behaviour. Keep source code, markup, configuration, assets, dependency manifests, commit history, and credentials out of the rebuild unless their licence and purpose expressly permit their inclusion.

    The distinction is practical. A requirement such as "members may update their own projects" describes a contract. The exact routes, data structures, variable names, tests, and visual assets used by another implementation are expressive implementation choices.

    #Rebuild the contract independently

    Start from a short description of each operation, its accepted inputs, its outcome, and its failure modes. Then choose a new architecture and write source and tests that make those contracts observable. The resulting code should be explainable from its own README and tests, without needing a reader to compare it to an excluded tree.

    For the project-management API, the current README describes a TypeScript service organized around domain policy, services, HTTP boundaries, and interchangeable stores. Its NOTICE states that the repository is independently authored and excludes course material and third-party source. Together, those documents define the claim this repository makes about its own contents.

    #Keep the claim checkable

    A provenance notice should state the actual boundary, not a broad assurance that cannot be reviewed. It should name what the repository contains and what it intentionally excludes. Source, tests, and documentation should then be readable on their own terms, with any external material used under its stated permission.

    This is not a substitute for licensing analysis. When material may be reused, follow its licence and attribute it as required. When it may not be used and there is not enough independent specification to implement the required outcome, exclusion is the honest result.
