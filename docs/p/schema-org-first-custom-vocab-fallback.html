    schema.org First, Custom Vocabulary as Fallback

    Decision. Describe every entity with schema.org terms wherever schema.org has one, and reach for the project's own mc: vocabulary only where it does not.

    Date. 2026-07-09, lab 6 of Information-Systems-Modelling.

    #The rule, stated and then enforced by code

    "schema.org covers most of the domain. Where it does not, the custom mc: vocabulary fills the gap (the \"missing classes/properties\" case the brief asks about). The renderer applies this rule programmatically."

    Information-Systems-Modelling/lab6/README.md, 2026-07-09

    The last sentence is what separates this from a style preference. RDFa wiring sets <html vocab="https://schema.org/" prefix="mc: … mcr: …"> once, so a bare term is schema.org by default and a custom term must be explicitly prefixed. Reaching for mc: costs six extra characters and shows up in review; using schema.org is the path of least resistance. The default is the policy.

    Types combine both rather than choosing — typeof="CreativeWork mc:DroneBuild" — so a generic consumer sees a CreativeWork and a domain-aware one sees a drone build.

    #Where the fallback was actually needed

    The mapping table is the decision's evidence: nine domain entities, and only three have no schema.org equivalent at all.

    Covered by schema.org Falls back to mc:
    Build → CreativeWork; votes → interactionStatistic/InteractionCounter; listing → Product + Offer; member → Person; test run → Event + Place + PostalAddress; club → OrganizationFlight log (mc:FlightLog, mc:flightAltitude, mc:pilotLicenseId) · Telemetry (mc:TelemetryRecord, mc:topSpeed, mc:crashCount) · Reputation (mc:ReputationRecord, four score properties)

    Those three are exactly the parts of the domain a general-purpose web vocabulary has no reason to model. That the fallback set is small and principled is the argument the decision makes.

    The mc: terms are not invented here — they come from the TBox built in lab 5, so the same vocabulary serves the reasoner and the published pages. See ontology-modelling-tbox-abox.

    #The rejected alternatives

    • Model everything in mc:. Internally consistent, and invisible to every consumer on the web — a search engine reading mc:MarketplaceListing learns nothing. Rejected.
    • Force everything into schema.org. Would mean modelling a flight log as a generic CreativeWork with untyped additionalProperty bags, losing the structure lab 5 built.
    • Maintain the mapping by hand in a comment. Rejected explicitly, and replaced by src/rdf/vocabmap.js, which walks the JSON-LD graph of each page and reports which schema.org and which mc: terms it actually contains — flagging nodes typed only with mc: classes as custom-only sub-graphs. A hand-written list would go stale the first time the data changed. That is provenance-and-limits-stated-inline and single-source-of-truth-generators applied to metadata about metadata.

    #Cost, stated in the repo

    Custom terms are not understood by third-party validators. lab6/README.md records the consequence rather than hiding it: custom mc: properties surface in structured-data testing tools as "recognised-but-unknown extras (expected — not schema.org terms)". Naming the expected warning is what stops a future reader from treating it as a defect.
