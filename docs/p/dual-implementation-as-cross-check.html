    Dual Implementation as Cross-Check

    Build the same thing twice, in two different stacks, and keep both. The second implementation is not redundancy — it is the only check available when there are no tests, because two independent implementations agreeing is evidence and one implementation asserting is not.

    #The strongest instance: lab 6

    lab6_Neo4j/viewer/pawlak.js reimplements every cypher query as, in the repo's words, "the exact analogue" in plain JavaScript, and renders the graph pictures and tables beside the Cypher that produces them:

    "Data note. The dataset holds 39 countries; earlier drafts of the guide said 38 (and 950 HAS_VALUE). The numbers were corrected to 39 objects / 975 edges throughout — the import logic itself was already correct (it MERGEs one object per row)."

    Discrete-Mathematics-Laboratories/lab6_Neo4j/README.md, 2026-07-10

    That correction is the pattern paying out: a discrepancy between what the documentation claimed and what a run produced was findable because the same system existed twice. See pawlak-information-system and idempotent-loading.

    #The other instances

    • Lab 4, Python and browser. Ackermann, Stirling and Nim exist as matplotlib/tkinter programs in part1 and again as a zero-build JS app in part2.
    • Lab 02, two shapes of the same answer. Eight questions answered both as weblog subcommands and as a single script — python-programming-laboratories.
    • Lab 04, the teaching class beside the production one.

    "weblog.LogEntry is the version the rest of the repository uses; the classes here are the teaching version, kept because writing the special methods by hand is the exercise."

    Python-Programming-Laboratories/labs/04_classes/README.md, 2026-07-25

    Recorded as a decision on keep-the-teaching-version.

    #When it is worth it, and when it is not

    It works here because the systems are small and the second implementation costs hours, not weeks, and because the purpose of the duplication is stated in the tree. It is closely related to multiple-solutions-side-by-side — that pattern compares algorithms within one program; this one compares whole implementations across stacks.

    The cost is real and shows up in this repo: two copies drift. guide.txt still says "object count = 38" after the README says the correction was applied "throughout" — documentation-drift. Two implementations cross-check each other only while someone is actually running both.
