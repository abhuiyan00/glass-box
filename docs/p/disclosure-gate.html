    Disclosure Gate

    A build step that must pass before anything derived from sensitive input may be published. It turns "I anonymised it" from an assertion into a check that can fail.

    "Anonymization you can't verify is a liability."

    labour-fraud-analysis-a-forensic-data-investigation/docs/methodology.md, 2026-07-11

    "the claim \"no PII here\" is not a promise, it's a passing test — and it caught real leaks during development"

    labour-fraud-analysis-a-forensic-data-investigation/docs/methodology.md, 2026-07-11

    #The four checks

    validate_anonymization.py in labour-fraud-analysis runs, and must print a PASS:

    1. Leak scan. A blocklist is assembled at run time from the private source — every sensitive column across people, companies, worksites, issuing authorities, permits and residence documents — and grepped across the data, docs, viewer and notebook directories. The blocklist is never written to disk.
    2. Stem guard. Word stems from a git-ignored local rules module, catching inflected and truncated forms that an exact-string blocklist misses.
    3. Regex sweep. Shape-based patterns for phone numbers and national identity numbers, plus an email pattern that allow-lists the fictional inboxes and domains the generated world is supposed to contain.
    4. Structural integrity. Primary-key uniqueness and foreign-key closure across ten tables — because an anonymisation run that silently dropped or duplicated rows has damaged the dataset even if it leaked nothing. See third-normal-form.

    One implementation detail is worth stealing: notebooks are scanned by cell source only.

    "For notebooks, scan only cell SOURCE (code+markdown), never base64 output blobs — random base64 would trip the substring checks."

    labour-fraud-analysis-a-forensic-data-investigation/src/validate_anonymization.py, 2026-07-11

    A gate that cries wolf gets disabled. Excluding the one input class guaranteed to produce false positives is what keeps it enabled.

    #The finding: the CI claim is overstated

    confidence: high, interview-confirmed 2026-07-28.

    The README states that no value in the dataset identifies a real party — "a claim that is test-verified in CI". It is not, on a clean runner. Checks 1 and 2 both require the private source and the git-ignored rules module, neither of which exists on a public runner, and the workflow says so itself:

    "On a clean runner the private source + rules are absent, so the leak/stem scans skip and this enforces structural integrity + the PII regex sweep."

    labour-fraud-analysis-a-forensic-data-investigation/.github/workflows/ci.yml, 2026-07-11

    So public CI enforces checks 3 and 4 only. The strong checks run on one machine, on demand, by one person. That is not nothing — it is how the real leaks were caught during development — but it is weaker than the README claims, and it is the single largest prose-vs-artifact gap in the repository. See documentation-drift. A milder instance sits alongside it: the README and methodology call this a "four-way" gate while the validator's own docstring says "two independent checks".

    This asymmetry is a general property of secret-scanning gates, not a local mistake: the check that needs the secret cannot run where the secret is absent. Any project whose gate depends on private input should state which subset a public runner actually enforces.

    #Related discipline

    The gate is the privacy analogue of verify-the-load-dont-declare-it — replace a claim with a query that can fail — and it is wired into make and github-actions so that it is not optional.
