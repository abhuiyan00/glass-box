    Client-Side Prediction and Reconciliation

    Under server-authoritative-netcode the client owns no state — but waiting a round trip before the player's own avatar moves is unplayable. Prediction resolves this: the client runs the same movement simulation locally and immediately, then corrects itself when the authoritative snapshot arrives.

    Two halves, and they are usually confused:

    • Prediction — apply the local input to the local avatar now, using a copy of the server's movement code.
    • Reconciliation — when a snapshot arrives showing a different position, get back to the server's answer without the correction looking like a teleport.

    #The two reconciliation strategies

    Input replay (the textbook form). Keep every unacknowledged input in a buffer. On correction, snap to the server position, then re-simulate every buffered input on top of it. This is correct — the client converges to exactly what the server will compute — at the cost of a buffer, sequence numbers on both sides, and a simulation that must be replayable from an arbitrary state.

    Blend toward snapshot (what stickfps ships). No replay, no buffer. reconcile() snaps outright when the error exceeds 3 m, and otherwise closes 15% of the gap per call. Errors decay geometrically instead of being cancelled.

    The repo names the limit itself rather than implying the stronger property:

    "Full input-replay reconciliation (re-simulating unacknowledged inputs after a server correction) is not implemented — v1 uses a simpler blend-toward-snapshot approach... Fine at low latency, will feel soft under real internet jitter."

    browser_game_stickfps/PROGRESS.md, 2026-07-25

    Do not read this page as documenting input replay. The percentage blend is the whole mechanism. Its failure mode is exactly the one quoted: under jitter the local avatar is persistently a little behind its own inputs and the controls feel rubbery, because a correction is never fully paid off before the next one lands.

    #Why the blend is defensible here

    Prediction only needs to cover movement, because shooting is a request, not a claim — the client never predicts a hit, so a mispredicted position can never produce a wrong kill. The worst outcome of a soft correction is a few centimetres of visual drift. That is the design property that makes the cheap strategy affordable, and it is the thing to check before copying it: prediction can be approximate only where nothing scored depends on it.

    Prediction also requires the client to hold a duplicate of the server's movement code, kept in sync by hand — see duplicate-sim-code-over-shared-package. Both copies step at the same rate under fixed-timestep-simulation; if the rates diverge, prediction error grows with no bound and the blend never catches up.

    #Not the same as interpolating others

    Prediction is for the local player, who is ahead of the server. entity-interpolation is for remote players, who are deliberately rendered behind it. A build can have one and not the other, and they fail in visibly different ways.
