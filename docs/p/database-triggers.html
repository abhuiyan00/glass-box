    Database Triggers

    Procedural code the database runs on your behalf when a table changes. Triggers enforce the cross-table and cross-row invariants that CHECK and foreign keys cannot reach — see referential-integrity — and every one of their difficulties comes from the fact that they execute inside the statement that fired them.

    #The four kinds, and what each is for

    Kind Fires Can see
    Row-level (FOR EACH ROW)once per affected row:OLD and :NEW for that row; not the table it fires on
    Statement-levelonce per statementthe table, but no per-row values
    Compoundat up to four timing points in one objectboth, with state declared once and reinitialised per statement
    Autonomous (PRAGMA AUTONOMOUS_TRANSACTION)as above, in its own transactioncommits independently of the caller

    #The mutating-table restriction

    A row-level trigger may not query or modify the table it fires on. Oracle raises ORA-04091, because the table is mid-change and any read would see an undefined state. Every trigger in oracle-database-laboratories is built to stay clear of it, and the comments say how.

    The cleanest example is band numbering. The naive implementation reads MAX(band_no) + 1 from the table it is inserting into — which is both illegal and wrong:

    "A sequence, not SELECT MAX(band_no) + 1. Reading Bands from a row-level trigger on Bands is the textbook mutating-table error, and MAX + 1 is also wrong under concurrency: two sessions inserting at once would compute the same number."

    Oracle-Database-Laboratories/sql/03_plsql/04_triggers.sql, 2026-07-25

    Two independent objections to the same line. A sequence is transactional and never touches the table, so it answers both at once.

    #State that spans a statement

    Some rules need the value of something read once before any row changed plus totals accumulated across all rows — a per-row trigger cannot hold either. Historically the workaround is three triggers sharing package variables: BEFORE STATEMENT initialises, BEFORE EACH ROW accumulates, AFTER STATEMENT settles up.

    That version is implemented, kept in the tree, and labelled inferior:

    "This works, but it is fragile in a way worth naming ... The guard flag below is what stops that recursion. Version (b) has no such problem and is the one to prefer."

    Oracle-Database-Laboratories/sql/03_plsql/04_triggers.sql, 2026-07-25

    The fragility is re-entrancy: the AFTER STATEMENT trigger updates the very column its own BEFORE UPDATE OF trigger watches, so it fires itself, and only a hand-managed boolean flag stops the recursion. A compound trigger holds the same state in its own declaration section, reinitialised per statement automatically, with no package globals leaking between statements. Recorded as compound-trigger-over-package-state; both versions retained side by side per keep-the-superseded-version-in-tree and multiple-solutions-side-by-side.

    #Autonomous transactions — audit that survives a rollback

    Two triggers here declare PRAGMA AUTONOMOUS_TRANSACTION so their log write commits independently of the transaction being audited. That is exactly what you want for "record that someone attempted this" — the attempt happened even though the change was rejected. It is exactly what you do not want for anything the caller's transaction should be able to undo, and the pragma gives no warning either way.

    The validation trigger pairs it with RAISE_APPLICATION_ERROR: log the attempt in the autonomous transaction, commit that, then raise so the offending statement fails. Two outcomes from one trigger, which is only possible because the two live in different transactions.

    #Three naming hazards the file records

    • No reserved words as column names. when and for read naturally for an audit table and neither can be used unquoted.
    • INTO targets named apart from the columns they read. Naming them alike makes PL/SQL resolve the WHERE clause against the variables, matching nothing — the same collision as in plsql-exception-handling.
    • RAISE_APPLICATION_ERROR takes -20000 to -20999. Any other code raises ORA-21000 in place of the intended message.

    ORA_LOGIN_USER gives the session user inside a trigger; outside one it is SYS_CONTEXT('USERENV','SESSION_USER'). And the insert-or-update in the audit path is a single MERGE rather than a count followed by a branch, closing the race between checking and writing.
