    BCrypt Crypto Only, No Spring Security

    Decision. Take spring-security-crypto for its BCrypt password encoder and nothing else from Spring Security. Authentication is a hand-written interceptor over jjwt.

    Date. 2026-05-28, lab 4 of Information-Systems-Modelling.

    #The decision is a comment in the build file

    "<!-- BCrypt password hashing (no full Spring Security pulled in) -->"

    Information-Systems-Modelling/lab4/StudentService/pom.xml, 2026-05-28

    Twelve words in a pom.xml, and they are doing real work: spring-security-crypto is a small standalone jar with no auto-configuration, whereas spring-boot-starter-security would lock down every endpoint by default, install a filter chain, and change the shape of the whole application. The comment exists because the next reader will otherwise see org.springframework.security in the dependency list and assume the framework is in play.

    #What was built instead

    Class Role
    JwtServiceissue / verify tokens — jjwt 0.12.6, HMAC-SHA, 24 h TTL
    AuthInterceptorSpring MVC HandlerInterceptor, registered in WebMvcConfig.addInterceptors
    CurrentUserthe resolved principal handed to controllers

    Plus passwordEncoder.encode(...) in UserServiceImpl.register and verifyCredentials(...) on login. That is the entire authentication system — see stateless-jwt-authentication.

    #The rejected alternative, and the trade actually made

    spring-boot-starter-security would have supplied, for free: a filter chain that runs before Spring MVC, CSRF handling, a session-fixation strategy, @PreAuthorize method-level authorisation, a standard UserDetailsService contract, and security-aware test slices.

    What the hand-rolled version gives up is mostly the first item. An interceptor runs inside Spring MVC's dispatch, a security filter runs before it — so anything served outside the DispatcherServlet mapping, or any handler path not covered by the interceptor's registration, is simply unguarded. The authorisation surface becomes "whatever is listed in WebMvcConfig" rather than "deny by default". With Actuator also on the classpath in lab 4, that is a real difference and not a theoretical one.

    What it buys is legibility: the whole auth path is three readable classes with no auto-configuration, no filter-order puzzles and nothing to un-configure. For a lab whose grading depends on the reader following the mechanism, that is a defensible call.

    #Not verified

    No test covers any of it. The interceptor's exclusion list, token expiry, a tampered signature, a missing header and role checks are all untested; lab 4's Java suite is one contextLoads() plus one integration test. A pointcut-style registration list that silently stops matching fails open, which is the specific hazard this design creates. See tests-that-pass-for-the-wrong-reason.

    Related, and worse in the ancestor: lab 3 has neither this dependency nor any of these classes, while its README and OpenAPI contract both promise bcrypt-backed JWT auth. The decision recorded here is what made lab 4 real. See forward-copy-lab-progression.
