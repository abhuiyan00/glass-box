    Replay a Recorded Run

    Record every event of one real run to a JSONL file. Then make that file do three jobs: restore the live UI after it is destroyed, drive the UI test suite, and generate the documentation screenshots. One artifact, three consumers, and none of them can disagree about what the product does.

    #It started as a bug fix, not a test strategy

    A VS Code WebviewView is destroyed on every switch to another view container and comes back with an empty DOM. The panel's state lives in JS variables, so chat, plan and a task still in flight all vanished — vs-code-extension-api. The fix is that the extension keeps a transcript and re-sends it as one restore event, and the panel rebuilds itself from that.

    Which means the panel already had to be a pure function of an event sequence. Everything below is that property being spent.

    #The three consumers

    Consumer Uses the recording to
    the productrebuild the sidebar after the view container is destroyed
    L2 tests (playwright)drive the real panel.html headless — 38 checks, no VS Code
    the screenshot matrixrender 12 committed figures for the README and architecture doc

    The test builds the transcript the way the extension does — same event filter, same coalescing of consecutive stream chunks per id — and the harness says so where someone might change one of them:

    "Mirrors record() in src/extension.ts. If the two drift, this test stops testing what actually ships, so keep the filter and the coalescing rule identical."

    vs-llm-orchestrator/agent-orchestrator/extension/harness/replay.js, 2026-08-07

    That comment is the pattern's known weakness, stated at the spot where it bites — document-the-failure-mode-next-to-the-fix.

    #Why the fixtures are real runs

    dag-waves and multi-fallback are recordings of actual work, not hand-written JSON. The payoff is in the second one: it contains a genuine Codex usage-limit refusal, so the fallback path in the tests and the fallback screenshot in the documentation are both showing something that really happened. Nobody had to stage a failure, and nobody could have staged that one convincingly.

    The cost is the ordinary cost of recorded fixtures: they age. A recording made against last month's CLI proves the panel handles last month's events. It is checked in generate-fixtures-not-commit's opposite direction deliberately — the recording is the evidence, so it is committed.

    #Where else this applies

    Any UI whose state is derived from a stream: log viewers, CI dashboards, anything with a WebSocket behind it. The requirement is that rendering be a fold over events with no hidden state, which is a discipline worth having anyway and is enforced for free the moment a restore path exists.
