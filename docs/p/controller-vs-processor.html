    Controller vs Processor

    The controller decides why and how personal data is processed. A processor processes it on the controller's behalf. The distinction decides who is accountable: the controller owes the legal bases, the rights responses and the transparency, while the processor owes the controller a contract and the controller owes the data subject an explanation of who the processors are.

    It is also the point at which a privacy policy stops being about the site's own code and starts being about its infrastructure.

    #How privacy-policy-template applies it

    §3 defines both terms in plain language, and §7 names the one processor:

    "This Service is hosted on GitHub Pages (GitHub, Inc.). As the host, GitHub acts as a"

    privacy-policy/PRIVACY_POLICY.md, 2026-07-10

    — processor, collecting IP addresses and server logs to operate the platform, maintain security and meet legal obligations. The policy says plainly that this is "outside our control" and links GitHub's own privacy statement and Pages data-collection notice rather than paraphrasing them. §8 lists the only disclosure routes: processors, legal requirement, protection of rights, and consent.

    #The consequence the policy actually draws

    This is the distinction that explains the site's whole data posture. The controller collects essentially nothing (data-minimisation); the processor collects logs the controller never sees and cannot switch off. So §11 has to split retention in two — correspondence deleted by the controller when the request is closed, server logs "retained by the hosting provider under its own retention schedule" — and §12 has to say that security is the provider's security (HTTPS, platform hardening, access controls), because the controller operates no infrastructure of its own.

    The same split drives §10: personal data may cross borders not because the site sends it anywhere, but because the processor's infrastructure spans jurisdictions. See host-on-github-pages for the decision that pins all of this to one named provider.

    #Where the boundary would move

    Every additional integration adds a processor and lengthens §7. An analytics script, a form backend, a comment widget, a CDN that fingerprints, a database, a cloud API — each is a new processor requiring disclosure and, in some cases, consent under gdpr-legal-bases. That is why the reuse checklist on one-reusable-policy-not-per-project flags §7 as one of the four fields to edit before republishing: an unedited §7 asserts "No other third-party processors", which is a factual claim about someone else's architecture.
