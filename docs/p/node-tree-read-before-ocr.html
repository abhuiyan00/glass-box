    Node-Tree Read Before OCR

    Decision. Read a ride offer's fare, distance and duration from the accessibility node tree. Treat optical character recognition as a fallback for apps that render offers as images — never as the default path.

    Date. 2026-07-02, recorded in 01-architecture.md, the first chapter of numbered-docs-chapters.

    #The reason, as written

    "Node tree before OCR. OCR is the expensive, fragile path. Many Android apps expose offer text as real TextView nodes, readable in microseconds with no image processing. OCR is a fallback, not the default."

    Farley/docs/ocr-overlay/01-architecture.md, 2026-07-02

    Three arguments in one paragraph — cost, fragility, and the observation that the data is already structured. Running a recognition model over a rendering of text that the platform will hand you as a string is work done twice, and the second copy is lossier. It is the same instinct as taught-selectors-over-guessed-labels: prefer the value you were given to the value you inferred.

    Latency is the binding constraint. An offer card carries a countdown, and the verdict has to be on screen while it still matters.

    #Alternative rejected

    OCR-first capture via MediaProjection + ML Kit. Rejected on the cost and fragility above. Two Android permissions still declared in the manifest — FOREGROUND_SERVICE_MEDIA_PROJECTION and FOREGROUND_SERVICE — are the fossils of that design; no code uses them. See android-accessibility-service.

    #The parse bug this design still had

    Structured input does not mean unambiguous input. Ride cards list the pickup leg before the trip leg, so a naive first-match read scored the wrong journey:

    "OfferNodeParser no longer takes the first money/km/min match: ride cards list the pickup leg before the trip leg, so first-match read the deadhead as the trip."

    Farley/docs/ocr-overlay/CHANGELOG.md, 2026-07-03

    The fix: fare is the largest money token; with two km/min hits the first is the pickup deadhead and the last is the trip. That distinction is precisely what deadhead-adjusted-net-profit depends on — the bug was silently pricing the free leg as the paid one.

    #Confirmed drift — OCR was never built

    The README, VISION and four documents describe Android ML Kit OCR as the shipped on-device engine. It is not shipped in any form:

    • com.google.mlkit:text-recognition appears in no build.gradle.
    • OcrReader.readNow() returns null behind a // TODO(Phase 4).
    • OcrReader.instance is never set, so the fallback cannot be reached even if it worked.
    • vision.ts carries an explicit NB (native) note that ML Kit text still needs wiring into ScreenCapture.hint.

    The working on-device reader is the node-tree parser, and the classifier that supports it runs over the node tree's flat text — not over pixels. Confirmed at interview; recorded on farely and documentation-drift as this repository's sharpest doc-vs-code gap. The decision itself was correct and was simply never revisited by the prose; what drifted is the claim that the rejected path also exists.
