    Referential Integrity

    Every foreign-key value either matches an existing primary key or is NULL. The database enforces it per statement, which means the constraint is not only a correctness guarantee — it is also an ordering constraint on how data may be loaded, and that consequence is where most of the practical work lies.

    #Constraints as a designed surface

    02_create_tables.sql in oracle-database-laboratories puts five relations under the full constraint vocabulary and names every constraint explicitly rather than letting Oracle generate SYS_C… names:

    Kind Example in the cat-herd schema
    Primary keycats_pk on nickname; incidents_pk on the composite (nickname, enemy_name)
    Foreign keycats_function_fk, incidents_cat_fk, incidents_enemy_fk
    Self-referencing FKcats_chief_fk — CATS.chief → CATS.nickname
    Uniquebands_site_uq, bands_chief_uq (no cat leads two bands)
    Checkgender IN ('M','W'), hostility_degree BETWEEN 1 AND 10, max_mice >= min_mice
    Not nullcats_name_nn, incidents_date_nn

    Named constraints are what make the error messages usable: a violation reports cats_band_no_fk, not a serial number. The same instinct appears in the object-relational rebuild, where every constraint carries an _r suffix because Oracle constraint names are unique per schema, not per table.

    #The composite key that costs something

    The INCIDENTS primary key is (nickname, enemy_name), and the file states the price rather than leaving it to be discovered:

    "The primary key is (nickname, enemy_name), which is what the assignment specifies. Note the consequence: a cat cannot record two separate incidents with the same enemy. Adding incident_date to the key would lift that restriction, and would be the right call outside the assignment's constraints."

    Oracle-Database-Laboratories/sql/01_schema/02_create_tables.sql, 2026-07-25

    This is a natural key doing entity-identity work it is not shaped for — the same tension surrogate-vs-natural-keys records from the warehouse side. Here the assignment fixes the choice and the comment records the cost.

    #Integrity dictates load order

    03_seed_data.sql cannot insert in an arbitrary order. Its header enumerates the forced sequence: reference tables with no outbound keys first (FUNCTIONS, ENEMIES), then BANDS with a null chief, then CATS ordered so every chief already exists when its subordinate arrives, then an UPDATE to fill the chiefs in, then INCIDENTS last. That is the same dependency logic as etl-load-order in a warehouse, arrived at from constraints rather than from a pipeline design.

    The hardest case — two tables that each reference the other — gets its own page: circular-foreign-key, resolved by circular-fk-via-alter-table.

    #Where integrity is not enough

    FUNCTIONS doubles as a validation table: it holds min_mice and max_mice per role. A foreign key can enforce that a cat's function exists; it cannot enforce that the cat's mice_ration falls inside that function's band, because the rule spans two rows in two tables. A CHECK cannot see another table either. That rule is pushed into a trigger — see database-triggers.

    The general shape: declarative constraints cover per-row and per-column rules; cross-row and cross-table invariants need procedural enforcement, and the boundary between the two is a design decision worth writing down.
