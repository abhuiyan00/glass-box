    Generated Docs Checked by CI Diff

    Generate documentation from the data, commit the output, and then have CI regenerate it and fail the build if the result differs. The committed file stays readable on GitHub without running anything; the diff check makes it impossible for it to go stale.

    It is the one mechanism in the source set that structurally cannot drift, which is why it earns a page next to documentation-drift.

    #The implementation

    build_docs.py in labour-fraud-analysis emits four artefacts from data/ — an ERD-and-columns schema page, a per-column data dictionary, a coverage report, and a row-count manifest — under a rule stated in its own docstring:

    "Run after anonymize.py so the numbers always match data/. No hard-coded counts."

    labour-fraud-analysis-a-forensic-data-investigation/src/build_docs.py, 2026-07-11

    make docs regenerates them. CI then runs the generator and compares:

    "git diff --exit-code docs/schema.md docs/data-dictionary.md docs/coverage.md data/_counts.json"

    labour-fraud-analysis-a-forensic-data-investigation/.github/workflows/ci.yml, 2026-07-11

    The step is named "Derived docs are in sync with data/" — the assertion, not the action. Change the dataset without regenerating, and the build goes red on that step with a diff showing exactly which number moved. See github-actions and make.

    #Why commit the output at all

    The obvious alternative — gitignore the generated docs and let each reader run the generator — is a real choice, and python-programming-laboratories makes it, ignoring its build output as "all reproducible from source". The case for committing here is that the docs are the reading surface of a portfolio artefact: a reviewer opens docs/schema.md in a browser tab and never clones. The diff gate is what buys the readability back without paying the staleness cost.

    The same reasoning covers the committed SQLite database and the ported case file — see generated-audit-artifact for the wider family, and reproducible-analysis for the seeding that makes any of it deterministic.

    #Where the gate ends — and where a claim outruns it

    confidence: high, interview-confirmed 2026-07-28. This matters more than the pattern itself.

    The README states that no value in the published dataset identifies a real party — "a claim that is test-verified in CI". That overstates what CI enforces, and the workflow says so in its own comment:

    "On a clean runner the private source + rules are absent, so the leak/stem scans skip and this enforces structural integrity + the PII regex sweep."

    labour-fraud-analysis-a-forensic-data-investigation/.github/workflows/ci.yml, 2026-07-11

    So the six CI steps split cleanly into two groups:

    Genuinely enforced on a clean runner Cannot run there
    lint; zero foreign-key violations; the four generated docs matching the data; PK/FK/row-count tests; the notebook executing; a regex PII sweepthe leak scan against a blocklist built from the private corpus; the stem guard from a git-ignored rules module

    The diff gate is real and it works. The privacy claim resting beside it is stronger than the machinery behind it. Both facts belong on the page, and the honest version is the one the workflow comment already tells: a gate that depends on a private input enforces less in public than it does on the author's machine, and the README should say which subset. Recorded in full on disclosure-gate.

    #The generalisation

    Any artefact derived from data by a deterministic script is a candidate: schemas, API reference, CLI help output, dependency inventories, fixture manifests. The requirements are only that the generator be deterministic and that its output be small enough to review in a diff. Where those hold, this replaces "remember to regenerate" with a build failure — and, as above, it is worth being precise about which claims the gate actually covers.
