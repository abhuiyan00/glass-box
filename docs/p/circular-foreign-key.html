    Circular Foreign Key

    Two tables that reference each other. A has a foreign key into B; B has a foreign key into A. The pair is legal and sometimes the correct model, but it breaks two things that normally come free: neither table can be created with both keys in place, and neither can be seeded first.

    #The instance

    In oracle-database-laboratories the cycle is between cats and their hunting bands:

    • CATS.band_no → BANDS.band_no — a cat belongs to a band.
    • BANDS.band_chief → CATS.nickname — a band is led by a cat.

    Both directions are real. Neither is redundant: membership is many-to-one, leadership is one-to-one and carries a UNIQUE constraint so no cat leads two bands. Dropping either key would lose information, so the cycle is a property of the domain rather than a modelling mistake.

    #Why it is awkward

    CREATE TABLE Cats with a foreign key into Bands fails because Bands does not exist yet; reversing the order fails symmetrically. And at load time, the first INSERT into either table violates the other table's key, because the row it points at has not been written.

    So a cycle costs you a schema-creation order and a data-load order, and the two are different problems with different fixes.

    #Two ways out

    Approach How Cost
    Create partial, then ALTER TABLEbuild CATS without band_no's FK, build BANDS in full, add the constraint afterwards; seed BANDS with a null chief, load CATS, then UPDATE the chiefs inthe load order is fixed and the UPDATE step is mandatory — an omitted UPDATE leaves the model silently half-built
    Deferrable constraintsdeclare both keys DEFERRABLE INITIALLY DEFERRED, insert in any order, let COMMIT check themyou lose per-statement error reporting: the failure surfaces at commit, pointing at a transaction rather than at the row

    The repository takes the first and names the second as the rejected alternative:

    "The alternative — deferrable constraints checked at COMMIT — buys free insert ordering at the cost of per-statement error reporting."

    Oracle-Database-Laboratories/README.md, 2026-07-25

    Recorded as circular-fk-via-alter-table.

    A third option exists and is not used here: make one side nullable and never enforce it, keeping the link in application code. That trades a database guarantee for convenience and is worse than either option above — it converts a load-order problem into an integrity problem.

    #Not the same as a self-reference

    CATS.chief → CATS.nickname is a self-referencing key, and it does not have this problem: a single table can be created with a key into itself, and rows load fine as long as each chief is inserted before its subordinates. The cat-herd schema has both, which is why they are easy to conflate. The self-reference is what hierarchical-queries walks; the cycle is what forces the load order in referential-integrity.
