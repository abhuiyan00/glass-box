    IndexedDB

    The browser's transactional object store. In farely it holds the diagnostics flight recorder — the only structured persistence in an app that otherwise uses localStorage, and the storage layer under on-device-black-box-diagnostics.

    #Schema in Farely

    Database farely-diag, a single object store events keyed by id, with a ts index for time-ordered reads. Ring-buffered to DIAG_CAP = 2000 rows.

    #Why IndexedDB and not localStorage

    Farely uses both, split by shape of data:

    Data Store Why
    Session, settings, API keyslocalStoragesmall, synchronous, read at boot
    Diagnostics event streamIndexedDBthousands of rows, needs an index, must not block

    localStorage is synchronous and string-only with a few-megabyte ceiling — writing an 8-kind event stream through it would stall the UI thread during exactly the moments worth recording. IndexedDB is asynchronous, indexed, and comfortably larger. Both survive inside the capacitor WebView with no native storage plugin, which is what keeps the persistence layer inside pure-domain-engine-shared-across-hosts rather than in Kotlin.

    #Written against the raw API

    diagStore.ts uses no wrapper library — no Dexie, no idb. It is an explicit "zero-dep IndexedDB" module in a repo carrying ~40 direct dependencies, one of several places where zero-dependency-no-build-step survives at module level inside a heavyweight shell.

    Three defensive properties come with that hand-rolling:

    • Writes are fire-and-forget and never throw. A diagnostics failure cannot break the feature being diagnosed.
    • In-memory bounded fallback when IndexedDB is absent or blocked, so the API surface never changes for callers.
    • A farely:diag CustomEvent is dispatched on every write, giving the live in-app view its data without a polling loop or a second read path.

    Export is a manual JSON dump to a dated filename — the user-triggered edge of generated-audit-artifact.

    #Limits worth stating

    Unencrypted at rest, like all WebView storage, and the decision rows contain the driver's earnings inputs. Also evictable — a browser or WebView under storage pressure may clear the whole database, so the ring buffer is a recent-history tool and never a ledger. Neither limit is documented in the repo.
