    click

    Third-party CLI framework for Python. Commands and options are declared as decorators on the function that implements them, so the parser definition sits directly above the code it feeds.

    #Where it is used

    Lab 09 of python-programming-laboratories — a CSV reporting CLI over a 10,360-row dataset, producing spreadsheet output via openpyxl and using factory-boy-and-faker for its test fixtures.

    #Why it is here at all

    Not because it was the best available option, but because the repo runs an explicit A/B: the core weblog CLI uses argparse and this lab uses click, on comparable problems, on purpose. The comparison and its verdict are recorded on click-versus-argparse.

    The short version of the trade-off as the repo states it: click's decorators are terser when a command has a lot of flags; argparse's subparsers give more control over a command hierarchy.

    #What the decorator style buys

    • @click.option / @click.argument attach directly to the handler — no separate parser-building block to keep in sync with the signature.
    • Type conversion and validation are declarative, including click.Path(exists=True), so "this file must exist" is a parser concern rather than a first-line-of-the-function concern.
    • Help text is derived from the same declaration, so it cannot drift from the parsing.

    The cost is a dependency and a layer of magic between sys.argv and the function — which is exactly why it lives in the optional labs extra rather than the dependency-free core. See setuptools-and-pyproject and zero-dependency-no-build-step.
