    Nullable Salesperson Key

    Decision. Declare mart.FACT_SALES.SalesPersonID as INT NULL with a foreign key to mart.DIM_SALESPERSON, and load every order line regardless of whether a salesperson exists.

    Date. 2026-07-25, data-warehousing-and-business-intelligence.

    #Why

    "SalesPersonID is nullable: roughly 60% of AdventureWorks orders are online and have no salesperson. Requiring one -- or filtering the load to rows that have one -- would discard most of the sales the warehouse exists to measure."

    Data-Warehousing-and-Business-Intelligence/sql/02_star_schema/01_create_star_schema.sql, 2026-07-25

    The reasoning is about grain, not about nullability. The fact table's grain is one row per sales order line (fact-grain), and it is enforced by the primary key. A NOT NULL on a dimension key that the source genuinely does not always have silently redefines that grain to "one row per order line that had a salesperson" — a different table answering a different question, with the majority of revenue missing. The dimension key is optional because the relationship is optional in the business, and the fact table's job is to record the business.

    ShipDateKey is nullable in the same DDL for the same class of reason: an unshipped order is a real order. A nullable foreign key is still enforced by SQL Server when a value is present, so the constraint does no less work — see sql-server.

    #The companion rule, in the other direction

    The load script draws the opposite line for descriptive dimension attributes:

    "ISNULL, not the column DEFAULT. A DEFAULT applies only when no value is supplied; selecting an explicit NULL into the column bypasses it, so the declared 'Unknown' would never take effect."

    Data-Warehousing-and-Business-Intelligence/sql/02_star_schema/02_load_star_schema.sql, 2026-07-25

    Missing descriptions — a product with no colour, no subcategory, no category — are replaced with a literal 'Unknown' at load time, because a report grouping by colour should show an Unknown bucket rather than dropping rows. Missing relationships stay NULL. Two kinds of absence, two treatments, both written down. See etl-load-order.

    #Alternatives rejected

    Option Why not Evidenced?
    NOT NULL on the keymost orders have no salesperson; the load would fail or the rows would be unloadableyes — named in the DDL comment
    Filter the load to rows that have a salespersondiscards the majority of sales; silently changes the grainyes — named in the DDL comment
    An "Unknown salesperson" member in the dimension, with a sentinel key—no

    The third row is the standard Kimball answer to an optional dimension relationship: add a -1 "Unknown" row to the dimension so every fact row has a real key and INNER JOIN behaves. It would also have matched the 'Unknown' treatment the same repo uses for descriptive attributes, above.

    #The number is an assertion

    TODO: "roughly 60% of AdventureWorks orders are online" appears in three places in the repository and all three are the same uncomputed statement — no query, no output, no committed result backs it. The same applies to a nearby claim about the count of products with a zero list price. Whether either was measured or recalled is unknown; confidence: low on both figures. The decision does not depend on the exact share — "most" is enough to carry it — but the number should not be cited from here as though it were measured. This is the class of claim verify-the-load-dont-declare-it exists to turn into a query, and in this repo the queries are written but never run and recorded.

    Page confidence: medium: the rationale is verbatim in the DDL and carried through independently by the load script, which joins header to detail with no salesperson filter — but it is one deliverable by one author and was not covered in the interview.
