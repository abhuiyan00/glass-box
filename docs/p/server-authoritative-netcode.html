    Server-Authoritative Netcode

    The client is an input device and a renderer. It never decides anything the game scores. Every outcome — who was hit, how much ammo remains, whose round it is — is computed on the server from inputs, and broadcast back as state the client is obliged to accept.

    The transferable rule is narrower than "trust the server": there must be exactly one place in the codebase where each authoritative outcome is decided, and it must be findable. In stickfps that place is named in a code comment as such — Room.resolveFireRequest is "the only method in this codebase that decides which player a shot hit (C1)".

    #What crosses the wire

    The message contract is the design. Client → server carries intent and nothing else:

    • PlayerInput — forward/backward/left/right, jump, crouch, yaw, client tick. No position.
    • FireRequest — weapon id, origin, direction, client tick. Never a hit result.

    Server → client carries state: position-snapshot-batch every tick, room-state on every phase transition, hit, weapon switch, purchase and roster change.

    #What the server owns

    Movement resolution · ammo · cooldowns · reload timers · equip settle (0.35 s) · aim error · hit-zone multipliers (×2.5 head, ×1.0 body, ×0.85 legs) · HP · kills, deaths, streaks · killstreak perk tiers · grenade arc, fuse and radial damage · money · round and phase state · map id.

    One detail is worth generalising: aim error is applied to the ray before the cast, server-side. Spread and recoil are not a client-side visual applied to a clean ray — so a modified no-recoil client gains nothing. The client's own copies of the weapon, movement and perk tables exist purely for prediction and are documented as cosmetic. Keeping them as copies rather than a shared import is duplicate-sim-code-over-shared-package.

    #The loopholes are the lesson

    Authority is not a property you declare; it is a surface you have to close hole by hole. One round of review in stickfps found five separate ways the server was not actually authoritative:

    • dead players could still fire, while simultaneously being skipped as raycast targets
    • firing was accepted during lobby and buy phase — a 100-damage rifle cross-map spawn kill
    • the server did not track which weapon was equipped, so a modified client could alternate two weapons and beat both cooldowns
    • joinRoom never left the previous room, leaving immortal zombie players holding rooms and their 60 Hz loops alive — a grief and denial-of-service vector at once
    • movement had no bounds at all; a client could walk to infinity

    A separate phase found the server passing the client-reported shot origin straight into the raycast. The fix, isOriginPlausible, rejects an origin more than 2 m from the shooter's server-tracked position.

    #What is deliberately absent: lag compensation

    There is no server rewind here. Hit validation raycasts against current server positions, so a shot is judged against where targets are when the packet arrives, not where the shooter saw them. isOriginPlausible is often mistaken for rewind and is not — it is a spoofing check on one scalar distance, with no history buffer of past positions to rewind into.

    The absence is the teachable part. Authority and fairness are different problems: this design is fully authoritative and still disadvantages the higher-latency player, because nothing reconciles the shooter's view of the world with the server's. Adding rewind means storing a ring buffer of past player transforms and re-casting against the snapshot the shooter actually saw.
