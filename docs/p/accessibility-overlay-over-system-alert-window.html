    Accessibility Overlay Over SYSTEM_ALERT_WINDOW

    Decision. Draw the ACCEPT / MARGINAL / DECLINE bubble as a TYPE_ACCESSIBILITY_OVERLAY window attached to the already-running accessibility service, instead of a SYSTEM_ALERT_WINDOW "draw over other apps" window.

    Date. 2026-07-03, recorded in the CHANGELOG.

    #The reason, as written

    "New OverlayController.kt draws the ACCEPT/MARGINAL/DECLINE bubble … using TYPE_ACCESSIBILITY_OVERLAY (no extra permission; attached via the running service)."

    Farley/docs/ocr-overlay/CHANGELOG.md, 2026-07-03

    The whole argument is in the parenthesis. SYSTEM_ALERT_WINDOW is not a normal permission — it sends the user out to a Settings screen for a scary-sounding grant, and it is the permission most associated with overlay malware. TYPE_ACCESSIBILITY_OVERLAY requires no additional grant at all, because the service already holds the only permission that matters: BIND_ACCESSIBILITY_SERVICE.

    Onboarding cost was the deciding factor. The app already asks for the single most powerful grant on Android (android-accessibility-service); adding a second alarming prompt on top of it is a real chance of losing the user at setup, for a window that behaves the same either way.

    #Alternative rejected

    SYSTEM_ALERT_WINDOW — the design originally documented in 03-android-permissions-and-legal.md. Rejected once the overlay was implemented, on the extra-grant cost above. Nothing technical was lost: the bubble is FLAG_NOT_FOCUSABLE so it never steals input from the ride app, tap-dismisses, and auto-hides after 20 s.

    The permission is still declared in the manifest. SYSTEM_ALERT_WINDOW sits there unused, along with FOREGROUND_SERVICE and FOREGROUND_SERVICE_MEDIA_PROJECTION (fossils of the OCR path — see node-tree-read-before-ocr) and ACCESS_FINE_LOCATION (no native location code). So the decision achieved its goal in code and then failed to collect the benefit: a user or store reviewer inspecting the manifest still sees the scary permission. Removing it was never done — and the permissions chapter still documents the rejected design as the required one, an instance of documentation-drift.

    #Second-order effect

    Tying the overlay's lifetime to the service means the bubble cannot outlive the thing that produced it. If the service is disabled, the window goes with it — there is no orphaned always-on-top view. For an app whose overlay sits on top of another company's driver app while the user drives, that coupling is a safety property, not just tidiness. It fits the restraint posture recorded on never-automate-the-accept-tap and privacy-documented-beside-the-feature.

    #Never validated in the field

    Like every native path in farely, this ran in a debug build and never on a live shift. Whether the overlay actually sits correctly over a Bolt offer card in traffic is untested — the state the roadmap board honestly reports as "code-complete — remaining: validate on device". See phase-status-board.
