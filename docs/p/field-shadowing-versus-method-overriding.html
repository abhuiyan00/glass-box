    Field Shadowing Versus Method Overriding

    Methods dispatch on the runtime type of an object. Fields resolve from the static type of the expression. A subclass field with the same name as a base-class field is separate storage; it does not override the base field.

    That distinction matters whenever a base class supplies common rendering or behaviour and each subclass supplies one varying value.

    #Put varying behaviour in a method

    Container makes the label a polymorphic method:

    ~~~java public abstract String label();

    @Override public String toString() { return "[" + label() + " - ...]"; } ~~~

    Bag, ShoppingBag, and HandHoldBag implement label(), while the base class owns the shared rendering. Calling toString() therefore dispatches to the concrete object's label without duplicating formatting in each subclass.

    This is the useful rule: when a value is meant to vary by subtype as part of behaviour, expose it through an overridable method rather than through a same-named field.

    #What static and dynamic dispatch mean

    Given a base-typed reference, Java chooses a method implementation from the object's runtime class. Field access does not work that way: the compiler selects the field declared by the reference's static type. The language permits both forms because fields can intentionally hide other fields, but the two mechanisms have different contracts.

    @Override makes the method contract visible to both the reader and the compiler. It cannot apply to a field, which is a useful signal that a field is not participating in polymorphic dispatch.

    #Test through the abstraction

    The inventory tests exercise a List<Container> containing all three concrete container types and assert that each rendered representation contains its label(). Testing through the base type confirms the contract that callers actually receive: common behaviour with subtype-specific values.

    For C++, the analogous choice requires a virtual member function when runtime dispatch is required. A base type used to delete derived objects should also have a virtual destructor. The syntax differs, but the design question is the same: is this member data, or is it behaviour selected by the concrete type?
