    GitHub Actions

    GitHub's hosted CI. labour-fraud-analysis carries one workflow, .github/workflows/ci.yml, triggered on every push and pull request — the only CI across the repositories ingested with it. ubuntu-latest, actions/setup-python@v5 pinned to 3.12 with the pip cache enabled, then six steps.

    #The steps, and what each one actually asserts

    Step Enforces
    ruff check srclint only
    python src/build_db.pythe SQLite build runs with foreign keys on, so 0 FK violations across the dataset
    build_docs.py then git diff --exit-code on four pathsthe committed generated docs match what the data produces — generated-docs-checked-by-ci-diff
    validate_anonymization.pystructural integrity plus a regex PII sweep — and nothing more, see below
    pytest -qprimary-key uniqueness, foreign-key closure, row counts against the manifest, and two signal-preservation tests — pytest
    nbconvert --executethe analysis notebook runs end-to-end headless, 240-second timeout

    Two habits here are worth copying. Step names are assertions, not verbs — "Build database — asserts 0 foreign-key violations", "Derived docs are in sync with data/", "Notebook executes end-to-end". A red build tells you what became false, from the run summary alone, before you open a log. And the notebook is executed in CI, which is rare: a stored notebook is a screenshot of a result, an executed one is a test of it. See reproducible-analysis.

    #The finding: the workflow is more honest than the README

    confidence: high — interview-confirmed, 2026-07-28.

    The README claims no value in the published data identifies a real party, "a claim that is test-verified in CI". The workflow's own comment says otherwise:

    "On a clean runner the private source + rules are absent, so the leak/stem scans skip and this enforces structural integrity + the PII regex sweep."

    labour-fraud-analysis-a-forensic-data-investigation/.github/workflows/ci.yml, 2026-07-11

    Two of the disclosure-gate's four checks — the run-time blocklist built from the private corpus, and the stem guard from a git-ignored rules module — cannot execute where their inputs do not exist. Public CI enforces the other two. This is a general property of secret-scanning gates rather than a local mistake, and the workflow states it in the place a reader will find it. The README does not. See documentation-drift.

    #Environment gaps CI does not close

    • It installs requirements.txt, never the package. pyproject.toml declares no dependencies key at all, so pip install -e . would install nothing — setuptools-and-pyproject.
    • It runs 3.12 only, while the project declares support from 3.10 and lints to a py310 target. The declared floor is never exercised by anything.
    • Dependencies are floor-pinned with no upper bound and no lockfile, so a green run today is not evidence about tomorrow's resolution.

    #Relationship to the Makefile

    CI's step list is make ci spelled out in YAML rather than invoked — db docs validate lint test, plus lint first and the notebook last. The duplication is small and the make target is the documented clean-clone contract, so a developer can reproduce the pipeline locally with one command. Keeping them in sync is manual; nothing checks that they agree.
