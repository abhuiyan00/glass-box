    Idempotent Loading

    A load script is idempotent when running it twice leaves the store exactly as running it once did. This is the difference between a script you can re-run while developing and a script you must remember to precede with a manual wipe.

    Two repositories solve it two ways, and the pairing is what makes the concept transferable — this is one of the few concepts spanning both python-programming-laboratories and discrete-mathematics-laboratories.

    #Relational: constraint plus conflict clause

    UNIQUE(context, knowledge, response)
INSERT OR IGNORE INTO ...

    The database enforces the identity; the insert declares what to do when it is violated. Lab 13 loads 610 rows; the second run inserts 0. That number is the test — an idempotent loader is one you can observe being idempotent, which is why the row count is reported rather than assumed.

    The critical part is that uniqueness lives in the schema, not in the loader. A loader-side "check then insert" is a race and a lie: it works until two processes run it. INSERT OR IGNORE delegates the decision to the only component that can make it atomically. See sqlite.

    #Graph: MERGE plus uniqueness constraints

    cypher's MERGE is match-or-create against a pattern. Lab 6 uses it with node uniqueness constraints so that re-running the LOAD CSV import re-attaches to existing nodes instead of duplicating them — one :Object per CSV row regardless of how many times the script runs. The repo records the payoff explicitly when the dataset count was corrected:

    "Data note. The dataset holds 39 countries; earlier drafts of the guide said 38 (and 950 HAS_VALUE). The numbers were corrected to 39 objects / 975 edges throughout — the import logic itself was already correct (it MERGEs one object per row)."

    Discrete-Mathematics-Laboratories/lab6_Neo4j/README.md, 2026-07-10

    The documentation was wrong; the loader was not. That is exactly what idempotence buys — the fix was a text edit, not a reload. See pawlak-information-system and neo4j.

    #The general rule

    • Declare the natural key in the schema (UNIQUE, a node constraint), never only in the loader.
    • Make the write express its conflict behaviour (INSERT OR IGNORE, MERGE, ON CONFLICT).
    • Report what changed — rows inserted, nodes merged — so the second run demonstrates zero work rather than merely not crashing.

    #Contrast

    data-warehousing-and-business-intelligence approaches the same problem from the verification side rather than the constraint side. Both are answers to "how do I know the load is right?"; only the constraint version survives being run by someone who forgot to check.
