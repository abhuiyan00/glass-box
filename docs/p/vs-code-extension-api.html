    VS Code Extension API

    The TypeScript surface an editor extension is written against: contribution points declared in package.json, an activate(ctx) entry point, and a vscode module available only inside the extension host. In agent-orchestrator it is 573 lines whose entire job is to spawn a Python subprocess, forward JSON, and host a webview.

    #The parts that carry weight

    • registerWebviewViewProvider and createWebviewPanel — the sidebar view and the wide Activity panel are two hosts for one HTML file, so both surfaces are registered against the same set of live webviews and every event is broadcast to all of them (self-contained-single-file-html).
    • ctx.secrets — encrypted SecretStorage, which is where an openrouter key belongs. Reached first, with the plaintext settings field as a fallback the panel offers to migrate (secrets-from-environment-only).
    • workspace.getConfiguration / ConfigurationTarget.Global — settings are read per run, and the autonomy toggle in the panel writes back through the same API rather than keeping its own copy.
    • workspace.workspaceFolders — the open folder is what the backend and both CLIs are given as their working directory. No folder open is a real state, not an assertion failure.
    • localResourceRoots — the webview may load from media/ and nowhere else.

    #The constraint that shapes everything else

    A WebviewView is destroyed whenever the user switches to another view container — Explorer, Source Control — and rebuilt with an empty DOM on return. Nothing in the DOM survives; anything the panel wants back it must be re-sent. That single fact produced replay-a-recorded-run, and it is worth knowing before designing a sidebar rather than after a bug report.

    #What is deliberately not used

    No LanguageModel API, no chat participant, no task provider. The extension owns no orchestration logic at all — it is a shell around a subprocess (drive-the-clis-not-the-apis), and it ships with zero runtime dependencies and no bundler (zero-dependency-no-build-step).

    Packaging is vsce producing a .vsix; the manifest's contributes block is the only place commands, settings and views exist, which is why a test asserts every contributed command is actually registered — tests-that-guard-the-repository.
