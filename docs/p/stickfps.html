    Stickfps

    A 5v5 round-based browser tactical FPS: Counter-Strike round/economy structure, Krunker-style movement feel, procedurally-generated low-poly stickmen. Server-authoritative hit registration, ephemeral 6-character room codes, AI bots, two cosmetic maps, anonymous auth only, zero PII, zero persistence beyond a match.

    Alongside farely this is one of only two non-coursework products in the source set — and the only one with a real-time networked server.

    #Architecture

    Two processes that share no code. Client sends intent only — PlayerInput carries movement axes, jump, crouch, yaw and a client tick and no position; FireRequest carries weapon id, origin, direction and tick and never a hit result. Room.resolveFireRequest is documented in-code as "the only method in this codebase that decides which player a shot hit (C1)". See server-authoritative-netcode.

    • 60 Hz fixed-timestep-simulation on both sides — server uses a drift-corrected recursive setTimeout, explicitly not setInterval; client uses a useFrame accumulator capped at 5 steps per frame.
    • client-side-prediction-and-reconciliation by blend-toward-snapshot; full input-replay is explicitly out of scope for v1.
    • entity-interpolation renders remote players 100 ms in the past from a 2-snapshot buffer.
    • Sim code is deliberately duplicated rather than extracted into a shared workspace package — see duplicate-sim-code-over-shared-package.
    • All match state is in-memory per Room. Nothing persists. supabase does exactly one thing: anonymous sign-in.
    • Every visual and audio asset is generated in code — no-external-assets.

    #Verified, and what is thinner

    Verified: 108 server + 52 client vitest tests, 2 Playwright specs, tsc and oxlint clean, vite build clean, a real Docker build/run//healthz cycle, a real WebSocket smoke test, and genuine Playwright captures of a live bot match at 1600×900. Server tests cover the authority surface densely — fire gating, friendly fire, buy validation, hit zones, grenade physics, perk tiers, round transitions, zombie-player cleanup, room-code format.

    Thinner, and stated as such in the repo itself (provenance-and-limits-stated-inline): the checked-in E2E covers only the lobby; the two-browser combat playtests of rounds 8–9 ran from scratchpad scripts and were never committed; no live pentest; no forged-packet fuzzing; no 10-player profiling ("no profiling tooling was available in the environment this was built in"); hosted Supabase never tested. confidence: medium on the test counts — they rest on PROGRESS.md's own reporting, with no CI and no coverage artefact.

    #Dead ends and things that broke

    PROGRESS.md is the highest-value document in the repo for exactly this reason — see progress-md-as-build-log for the full round-by-round list. The sharpest:

    • Round 5: no reload-request existed on the wire at all. Client reload was purely cosmetic, so every weapon was permanently empty server-side after its first magazine; later shots were silently rejected while the HUD showed full ammo.
    • Round 3: WeaponRig had never rendered a gun mesh — it return nulled for two rounds.
    • Round 5: nothing tracked round wins, so the match winner was literally undeterminable.
    • Five authority loopholes found in one round: dead players could still fire, firing was accepted in lobby and buy phase, the server did not track the equipped weapon (so a modified client could alternate weapons to beat both cooldowns), joinRoom never left the previous room (immortal zombie players holding 60 Hz loops alive), and movement had no bounds at all.
    • Client-origin raycast vulnerability: the server passed the client-reported shot origin straight into the raycast — "muzzle-to-forehead against a player across the map".
    • ±π yaw seam made remote players spin a full 360°; lighting broke twice.
    • Whole transport replaced in round 11 — websocket-tcp-over-geckos-udp.
    • Grayscale film-noir art identity retired after being a mandatory hard constraint in three documents — superseded-in-place-documentation.

    Reported and deliberately not fixed: kill-feed entries can drop when two lethal hits land in one React batch; ~1.4 MB bundle; both teams spawn stacked; no per-connection rate limiting; environment props have no collision and do not block bullets (a named scope cut, SRS FR-9.4); round win is elimination-only; bots use neither grenades nor perks.

    #How it was built

    spec-driven-development end to end: an IEEE-830-adapted SRS with FR/NFR ids and a traceability matrix, then a docs/specs/task-<id>.md per phase, then code, then independent verification. The loop itself is committed — architect-coder-tester-loop and agent-skills-checked-into-the-repo (91 files of vendored Three.js skill packs and authored subagent definitions).

    Also an instance of readme-as-guided-tour, generated-audit-artifact and — the repo's most systematic flaw — documentation-drift.
