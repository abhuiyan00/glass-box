    Secrets from Environment Only

    Credentials are read from environment variables and from nowhere else, and .gitignore is written so that the lazy path and the safe path are the same path.

    "Credentials come from the environment. Nothing resembling a secret belongs in a tracked file, and .gitignore covers .env and key material so that staying honest is the path of least resistance."

    Python-Programming-Laboratories/labs/10_web_scraping_and_email/README.md, 2026-07-25

    The second clause is the whole design. Discipline that depends on remembering fails; discipline enforced by the ignore rules does not. .env, *.pem and *.key are ignored, so the file a developer would naturally create is one git will not offer to stage.

    #What lab 10 does with it

    An SMTP + REST + scraping lab in python-programming-laboratories — the one place in either repository that handles real credentials. Three hardening choices sit beside the env-var rule:

    • EmailMessage rather than string-formatted headers. Building a message by concatenation lets a newline in a user-supplied subject inject arbitrary headers — a Bcc, a spoofed From. Using the email API makes header injection structurally impossible instead of filtered.
    • starttls(context=ssl.create_default_context()). The default context verifies the certificate and the hostname. starttls() with no context is the version that appears in most tutorials and the version that accepts any certificate.
    • timeout= on every request, so a hung endpoint fails rather than blocks forever.

    #Scope — do not overstate it

    This is what the repository does, and it is the correct baseline. It is not a secrets-management practice: there is no vault, no key rotation, no CI secret store, and no CI at all.     Nothing resembling a credential was found in either lab repository during recon — the pattern holds in practice, not only in prose.
