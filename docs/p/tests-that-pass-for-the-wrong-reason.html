    Tests That Pass for the Wrong Reason

    A failing test tells you something is broken. A passing test tells you nothing at all unless you know it could have failed. python-programming-laboratories documents two concrete instances, both of which pass against an implementation that does nothing.

    #Instance 1 — the assertion never reached the code

    "An assertion has to reach the code under test. A test whose argument is an undefined name raises NameError while evaluating the call, before the function is entered — so pytest.raises(TypeError) never sees it, and the test would pass against an implementation doing no type checking at all."

    Python-Programming-Laboratories/labs/07_testing/README.md, 2026-07-25

    The mechanics: pytest.raises(TypeError) is a context manager, and NameError is not TypeError — but the argument expression is evaluated before the call, and in this case raised inside the raises block. The test is green, the function was never invoked, and deleting the entire type check from the implementation changes nothing.

    The general failure: an exception raised while building the call is indistinguishable from one raised by the call unless you check which. Assert on the exception's message or type precisely, and be suspicious of any raises block containing more than the single call under test.

    #Instance 2 — "no" is truthy

    Lab 09 generates fixtures with factory-boy-and-faker, and the trap is in the data rather than the control flow: a CSV field containing the string "no" is truthy in Python. A test that populates every field with plausible values and asserts on a filter can pass because everything passed the filter, not because the filter worked.

    The discipline the lab adopts is the fix: factories fill the irrelevant fields; each test sets the field under test explicitly. A fixture that decides the value under test has moved the assertion into the fixture, where nobody reads it.

    #How the labs make the tests capable of failing

    • Validation order is pinned by tests, not just validation outcome — so a refactor that checks arguments in a different sequence fails loudly.
    • parametrize across methods and versions, so a test that only passes for GET and HTTP/1.1 is exposed.
    • Round-trip properties (parse → format → parse) rather than fixed expected strings — see common-log-format-parsing.

    #The wider point

    This is the reason python-programming-laboratories lists "knowing when a test passes for the wrong reason" as a skill rather than "writing tests". A suite's value is its discriminating power, and that is not measured by count. The repo's own "89 tests" headline is exactly the kind of number this concept warns about — see pytest.
