    Spec-Driven Development

    Write the specification before the code, at two levels: one document for the whole system, one document per unit of work. The code is then judged against a text that existed before it, by someone (or something) that did not write it.

    stickfps is the clearest instance in the source set — docs/ holds an SRS adapted from IEEE 830 with numbered FR/NFR identifiers and a traceability matrix, plus nine docs/specs/task-<id>.md files, one per build phase. Documentation is roughly half the repository by size.

    "Spec before code: every phase in this repo has a docs/specs/task-<id>.md written before the corresponding code — if you're adding a non-trivial feature, write the spec first."

    browser_game_stickfps/docs/CONTRIBUTING.md, 2026-07-25

    #The three properties that make it work

    Stable identifiers. FR-9.3, FR-9.4, C1, C3, C5 are referenceable from code comments, commit messages and test names. A scope cut becomes citable rather than forgotten: "environment props have no collision" is not an omission in stickfps, it is FR-9.4 declined on the record.

    A traceability matrix. Requirement → where it is implemented → what verifies it. Its value is that gaps become visible as blank cells rather than as absences you have to notice.

    An "Open Questions" section that halts work. The per-task spec is allowed to say it does not know something, and the build loop stops and asks rather than guessing — see architect-coder-tester-loop. This is what separates spec-driven from spec-shaped: a spec you are permitted to be uncertain in is a spec people actually write honestly.

    #Its characteristic failure

    Specs are written once and code moves. In stickfps the traceability matrix stops at round 9 while FR-9.9 through FR-9.14 exist, and the SRS still describes the retired transport in §1.2, §4.3, §4.4, §6.5 and its Mermaid diagrams — patched by a prose note rather than edited. That is documentation-drift arriving through the front door, and it is worse in a spec-driven repo precisely because the spec is load-bearing.

    The counter-habit that bounds it here is superseded-in-place-documentation: retired requirements are banner-stamped and left in place rather than rewritten, trading internal consistency for an auditable history of what was once required.

    #Where else this appears

    Contract-first API work in information-systems-modelling is the same instinct applied to interfaces rather than to a whole system, and the generated audit in stickfps — generated-audit-artifact — is the verification half made reproducible.
