    Java and Angular over the Spec's Python Stack

    Decision. Build the ModellingClub platform on Java 21 + Spring Boot + Angular, even though lab 1's own requirements specification proposes Linux / Python / PostgreSQL / Nginx.

    Date. From lab 2 onward — the first Spring Boot service lands 2026-04-14, the same day as the requirements document it diverges from.

    #The choice, and the principle behind it

    "Interestingly, the document proposes a Linux / Python / PostgreSQL / Nginx deployment stack — but the labs deliberately satisfy the same requirements using a Java + Angular stack. The requirements are the contract; the technology is a choice."

    Information-Systems-Modelling/README.md, 2026-07-25

    That last clause is the decision. The SRS is treated as a statement of obligations, not a statement of implementation — actors, functional and non-functional requirements, hard limits on upload size and files per build, GDPR and EU drone compliance. None of those obligations mention a language, so none of them are violated by changing one.

    The word "deliberately" matters: this is the repo declaring a known, chosen divergence rather than quietly building something else and hoping no one diffs it.

    #What was rejected and what replaced it

    lab 1 SRS proposes labs 2–7 deliver
    PythonJava 21
    (implied Python web framework)spring-boot 3.5.6
    PostgreSQLSQLite (lab 2) → h2-database file mode (labs 3–4)
    Nginxnone — spring-boot-maven-plugin, no deployment
    (no frontend named)angular 21.2 standalone + SSR

    PostgreSQL is the interesting row, because it was never fully abandoned: application-prod.properties carries a commented-out PostgreSQL + HikariCP + Flyway block, and lab 7 models the H2 → PostgreSQL changeover as a full BPMN process — see bpmn-process-modelling. The spec's database is modelled and planned for, just never run.

    #What the divergence cost, and what it bought

    Bought: the OpenAPI toolchain of contract-first-api-design — openapi-generator-maven-plugin emitting Spring interfaces from the contract — and, with it, the reason lab 4 needed aspect-oriented-programming to add cross-cutting behaviour without hand-editing generated code. A Python stack would have produced a different, probably thinner, set of labs.

    Cost: the requirements-to-implementation link became purely narrative. No lab file cites a requirement id. There is no traceability matrix, and the SRS's numbering (if it has any) is not referenced anywhere in labs 2–7. The claim "the same requirements are satisfied" is therefore asserted, not demonstrated — and lab 3 is a concrete case where it is not true: its contract promises JWT authentication with bcrypt that the code does not implement. See stateless-jwt-authentication.
