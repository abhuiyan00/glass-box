    Computer Arithmetic and Number Representation

    Positional systems, the four conversion methods, the binary codes for decimal digits, sign-magnitude and both complements, arithmetic performed inside a code, and IEEE-754 — built from the field definitions rather than from the platform. Python 3.11+, no dependencies, 1,844 tests. A clean-room-rebuild-from-specification of the first-semester Computer System Organization syllabus.

    #Why rebuild what int() and struct already do

    Because neither answers the question the material asks. int("1010", 2) returns ten without saying whether it used Horner's scheme or formed the weights, and struct.pack(">f", 0.1) returns four bytes without saying what was lost.

    Both facts are recoverable only by writing the method out, which is make-the-formal-object-observable applied to arithmetic: every conversion returns a Trace holding the intermediate quotients and subtractions an exercise expects to see in the margin, and the tests check the trace as well as the answer. A method that reaches the right result by the wrong route has not been implemented.

    #Closed forms, not ratio bands

    counted-complexity-assertions taken one step further than the DSAA repository needed. Direct method I forms every weight and costs w(w−1)/2 + 2w; Horner forms none and costs 2w. Both closed forms are asserted at five widths.

    A ratio test was written first and discarded. The measured ratios are 3.14, 3.45 and 3.68 — all short of the 4 a purely quadratic term would give, because the linear part still dominates at these widths. A tolerance band loose enough to accept 3.14 would also accept a genuinely linear implementation, which is tests-that-pass-for-the-wrong-reason in its most tempting form: the test would have passed, and it would have been measuring nothing.

    #A property that classifies, rather than a table to memorise

    Four decimal codes are usually taught as four tables. Three share a property the fourth lacks — see self-complementing-codes — and is_self_complementing computes it rather than declaring it, so a code added later classifies correctly without a flag anyone has to remember to set.

    The correction counts follow from it and are measured over all 100 single-digit pairs per code: BCD 8421 needs its plus-six on 45 of them, Aiken on 25 in both directions, Excess-3 on all 100 but unconditionally, with only the sign varying. The exercise sheet prints two examples.

    #Two defects the range tests caught

    Both passed the exercise sheet's own examples, which is the point.

    The p's complement of zero overflows its width. Complementing 000 gives 1000; the leading digit falls off the fixed width and the carry it stood for went with it, so every a − 0 came back negative. The sheets contain no subtraction by zero. The 121-pair grid does.

    Aiken's code words were self-complementing and still wrong. Two patterns satisfy the constraint for digits 5 to 7 and the published code takes the higher one; taking the first found produced a real self-complementing code that was not Aiken's — passing every round-trip test and disagreeing with the textbook table.

    Both are written up beside their fixes, following document-the-failure-mode-next-to-the-fix.

    #The error is a number

    Every figure is computed in fractions.Fraction, so the arithmetic that measures floating-point error is not itself floating point. 0.1 encodes to 13421773 / 2²⁷ in binary32 and the shortfall is stated exactly; 0.1 + 0.2 − 0.3 is exactly 2⁻⁵⁵.

    The IEEE-754 encoder is checked against struct in the useful direction only — an independent implementation agreeing with the platform is evidence, whereas wrapping the platform and comparing against itself would prove nothing. That is reference-implementation-as-specification used as a cross-check rather than as a source.
