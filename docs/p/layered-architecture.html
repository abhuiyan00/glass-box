    Layered Architecture

    Split the application into horizontal tiers where each layer may only call the one below it: api/ handles HTTP and nothing else, service/ holds the domain rules and knows nothing about HTTP, repository/ talks to the database, entity/ is the persistent shape. The constraint is the architecture — without the "only downward" rule it is just four packages.

    The payoff is substitution: swapping sqlite for h2-database between lab 2 and lab 3 touches repository/, configuration and nothing else, because no controller ever held a query.

    #As implemented

    All three Java backends in information-systems-modelling use the identical split under pl.edu.pwr.tkubik.ism — same packages, same artifactId, same names, across 11 → 41 → 76 Java files. That repetition is not accidental; it is forward-copy-lab-progression preserving the skeleton while each lab adds one capability to it.

    Lab Java files What the layering absorbed
    211generated API interfaces from contract-first-api-design
    341stateless-jwt-authentication added at the config/ seam, not inside handlers
    476aspect-oriented-programming, validation, uploads, dev/prod profiles

    Lab 4 is where the layering earns its keep. GlobalExceptionHandler converts anything thrown below into an RFC 9457 ProblemDetail at the api/ boundary, so no service needs to know it is being called over HTTP, and no stack trace reaches a client. Aspects attach to pointcuts over the service layer without any service method being edited.

    #The observation that complicates it

    Layering is a static decomposition. Everything this repo added after lab 2 that was genuinely cross-cutting — logging, timing, statistics, security auditing — could not be placed in a layer, which is precisely why lab 4 reaches for aspects. Layers handle the vertical slice; they have no answer for the horizontal one. Recording both in the same codebase is what makes the pair legible.

    #Limits observed

    • Zero tests exist for any service implementation. The two integration tests in the repo drive the full stack end-to-end through MockMvc; nothing tests a layer in isolation, which is the usual argument for having layers at all. The testability benefit is claimed by structure, not demonstrated.
    • TODO: MessageController, TelemetryController and AnalyticsController exist in lab 4 but appear in no README feature list. Whether they are finished, stubs, or abandoned mid-feature is unrecorded. confidence: low — do not assert lab 4 is feature-complete.
