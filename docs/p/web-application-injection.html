    Web Application Injection

    One root cause, many names. Injection happens when data supplied by a user is concatenated into a string that some interpreter then executes. SQL, NoSQL query documents, HTML/JavaScript, XML, shell commands, LDAP filters — the interpreter differs, the defect does not. Labs 13–14 of cybersecurity-engineering-laboratories work through the classes against OWASP Juice Shop.

    This page contains no payloads. Every class below is described by mechanism and defence only — see the redaction note on cybersecurity-engineering-laboratories.

    #The classes

    Class Interpreter What goes wrong
    SQL injectionthe database's SQL parseruser text becomes SQL syntax rather than a value; authentication predicates can be made unconditionally true, and blind variants extract data one bit at a time from timing or response differences
    NoSQL injectiona document-database query enginethe query is a structure, not a string, so a value position that should hold a scalar can be made to hold an operator object; also reachable as a denial-of-service vector
    XSSthe victim's browserattacker-controlled text is rendered as markup or script, executing in the origin of the site and inheriting its session
    XXEthe XML parsera parser that resolves external entity declarations by default turns document upload into arbitrary local file read or outbound request
    CSRFthe victim's browser plus ambient credentialsnot injection strictly, but grouped with it: the browser attaches the session cookie to a request the user never intended to make

    The NoSQL case is the one people get wrong by analogy. "Use a document database, avoid SQL injection" is false: the query is JSON-shaped, so the injection point is a type confusion — supplying an object where a string was expected — rather than a quoting failure. The defence is the same in spirit (validate the shape and the type, never build the query from user-controlled structure) and different in mechanics.

    #The one real fix

    Separate code from data before the user's input is anywhere near the interpreter.

    • Parameterised queries / prepared statements. The query text is fully defined first, then each parameter is passed alongside it. The database can then distinguish code from data regardless of what the user entered — which is the property that makes this a fix rather than a mitigation. Stored procedures achieve the same thing by defining the SQL inside the database.
    • Contextual output encoding for XSS. Escaping depends on where the value lands — HTML body, attribute, URL, JavaScript literal — and a single generic escape is not sufficient. Plus a Content Security Policy as defence in depth.
    • Disable external entity resolution in the XML parser. XXE is a default problem: the correct configuration exists in every mainstream parser and is not the default in older ones.
    • Anti-CSRF tokens and SameSite cookies, so a cross-origin request cannot carry ambient authority.

    Input filtering and blocklists are explicitly not the fix. They are approximations of a parser, maintained by hand, and they fail against encodings the filter's author did not anticipate. Allow-list validation of type/length/format is useful as defence in depth, never as the primary control.

    #The neighbouring classes from lab 13

    The tooling lab covers the categories injection sits beside, which matter because they are found with the same proxy and often in the same request:

    • Broken authentication — credentials over an unsecured channel, no password policy, validation performed client-side only.
    • Broken access control — the strongest example in the lab is object-identifier enumeration: changing a numeric identifier in a request to reach another user's resource. No injection involved; the server simply never checked ownership.
    • Improper input validation and security misconfiguration — including verbose error messages that hand an attacker the interpreter's own diagnostics.

    Client-side validation is not a control. An intercepting proxy edits the request after it leaves the browser, so every constraint enforced only in JavaScript is advisory. That is the single most transferable finding from lab 13 — see owasp-zap, and note that such a proxy is structurally a man-in-the-middle-attack with the tester on both ends.
