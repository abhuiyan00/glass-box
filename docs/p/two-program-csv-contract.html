    Two Programs, One CSV Contract

    Two languages, two processes, no interop layer. No pybind11, no ctypes, no subprocess call, no socket. They meet only at files on disk, and the file format is written down as a versioned contract with a stated rule for changing it.

    "The system is two programs that never call each other. They meet only at CSV files on disk — the frozen contract."

    Optimization Methods/final_project/ARCHITECTURE.md, 2026-07-10
    instance_generator (Python)  ──►  CSV files (the contract)  ──►  mdvrp (C++17)  ──►  solutions

    #What makes it a contract rather than just "we use CSV"

    Three things, and all three are needed:

    1. The columns are specified, in one place, as the authority. ARCHITECTURE.md §2 tabulates every file, who writes it, and its exact columns — point_type,point_id,node_id,lat,lon,demand with depots first, 0-based ids and depot demand 0; node_id,lat,lon for graph nodes; from_node,to_node,length_m for directed edges. The document declares itself the source of truth: "If code and this file disagree, treat the disagreement as a bug and reconcile both sides together, then bump the contract version."

    2. Ownership is one-directional and explicit. Python owns all level rules (config.py); the C++ side reads level parameters from the .meta.csv and never hardcodes them. That is the rule that actually prevents drift — without it, two programs "sharing" a CSV quietly grow two copies of the same constants.

    3. Changing it has a procedure.

    "Edit this file first, update both the Python writer and the C++ reader together, and bump the version (currently v1). Never change one side alone."

    Optimization Methods/final_project/ARCHITECTURE.md, 2026-07-10

    #Why it is the right shape here

    The split follows the strengths cleanly. Python does the things with good libraries and no performance requirement — download the road network with osmnx, sample instances, render figures with matplotlib, generate the leaflet maps. C++17 does the thing that runs millions of times — the GA and lazy-dijkstra-distance-cache. Neither has to be bilingual.

    The cost is real and accepted: every exchange is a serialise/parse round trip, and there is no type checking across the boundary beyond what the readers assert. In exchange, either side can be run, rewritten or debugged alone, and the intermediate state is inspectable in a text editor — which is what makes generated-audit-artifact possible at all, since verify_reports.py re-parses the C++ side's output without needing to link against it.

    The same shape appears one project earlier in miniature: first_project's C++ solver writes summary.csv and history_*.csv, and a 278-line generate_plots.py reads them. Same rule — the plotting script never calls the solver, the solver never knows plots exist.

    #Where it leaks

    The contract is honoured; the documentation around it is not uniformly. mdvrp/README.md and docs/design-notes.md still describe a flat output/solutions/{csv,txt} layout after ARCHITECTURE.md moved to per-solver subfolders, and HOW_TO_RUN.md names two scripts that do not exist. The contract document itself stayed correct because it is the one file the procedure requires editing first — the others had no such rule. See documentation-drift.

    Also note that the contract CSVs are gitignored — instances and graphs are regenerated, not committed. Since osmnx no longer returns the original geography, the contract is reproducible but its contents are not. The committed reports on the C++ side are the frozen reference instead.
