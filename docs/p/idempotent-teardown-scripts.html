    Idempotent Teardown Scripts

    Every script in the set can be run again, from any state, without editing it first. Not achieved by a migration framework or a test harness — achieved by two rules applied by hand: teardown swallows "does not exist", and anything that writes data ends in ROLLBACK.

    The property is stated as a guarantee in the README, which is what makes it a pattern rather than an accident:

    "Each script is idempotent: the teardown scripts swallow \"does not exist\", and every block that modifies data ends in ROLLBACK."

    Oracle-Database-Laboratories/README.md, 2026-07-25

    #The three mechanisms

    1. Drop child-first, in a declared order. Both teardown scripts hold the object names in a nested table in dependency order and loop over it, so no foreign key ever blocks a DROP. The object-relational teardown has a second ordering rule on top, and states why the obvious shortcut is wrong:

    "Object tables go before the types they are built on -- a type with a table depending on it cannot be dropped, and FORCE would leave the table invalid rather than removing the dependency."

    Oracle-Database-Laboratories/sql/04_object_relational/00_drop_all.sql, 2026-07-25

    2. Swallow exactly two error codes, re-raise everything else. The local drop_object procedure catches WHEN OTHERS, allows SQLCODE IN (-942, -4043) — table/view does not exist, object does not exist — and calls RAISE otherwise. That narrowness is the whole point: a blanket WHEN OTHERS THEN NULL would make the script idempotent and blind. See plsql-exception-handling.

    3. Never commit. Every exercise block that inserts, updates or fires a trigger ends in ROLLBACK, and every trigger script drops the trigger and any scratch table it created before moving on. The demonstration leaves the schema exactly as it found it, so the next script's assumptions still hold.

    #Why it matters more here than a framework would

    There is no test runner, no migration tool and no CI in oracle-database-laboratories. Re-runnable scripts are the entire reproducibility story: a reader can execute the suite top to bottom, get the documented result, and execute it again immediately. The property is structural rather than asserted — it holds because of how the code is written, not because something checks it.

    It also makes numbered-stages-in-directory-names safe. Numbered run order only helps if starting over is cheap; if step 3 leaves committed rows behind, re-running step 1 is not a reset.

    #The same instinct elsewhere in the source set

    • idempotent-loading — MERGE-based Cypher import in the discrete-maths repo, re-runnable for the same reason and fixed by re-reading rather than rebuilding.
    • etl-load-order — warehouse loads that must create before they load; the ordering half of the same problem, without the teardown half.

    The distinctive move here is the exception-code allow-list. Both other instances get idempotency from an upsert primitive the engine provides; this one gets it from deciding, explicitly, which two failures mean "already in the desired state".

    #Cost

    The ROLLBACK discipline means the scripts can never be used to actually populate a working schema — running 03_plsql/ leaves no data behind by design. Seeding is a separate step (01_schema/03_seed_data.sql), and the split is invisible until someone runs the PL/SQL scripts expecting persistence. Worth knowing before adapting any of it.
