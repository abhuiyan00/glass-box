    Compound Trigger Over Package State

    Decision. Implement a statement-spanning trigger rule as a single compound trigger rather than as three separate triggers sharing variables in a package — and keep the rejected implementation in the tree, labelled.

    Date. 2026-07-25 (evidence date), sql/03_plsql/04_triggers.sql of oracle-database-laboratories.

    #The problem both versions solve

    The rule needs the chief's ration read once before any row changes, plus running totals accumulated across every affected row, then a settlement write after the statement completes. A row-level trigger can hold neither; a statement-level trigger cannot see per-row values. See database-triggers and the mutating-table restriction it describes.

    #Version (a): three triggers plus a package

    BEFORE STATEMENT initialises package variables, BEFORE EACH ROW accumulates into them, AFTER STATEMENT settles up and writes back. It works, and the file says exactly where it is thin:

    "This works, but it is fragile in a way worth naming: the AFTER STATEMENT trigger updates Cats.mice_ration, which is the very column its own BEFORE UPDATE OF trigger watches, so it re-enters the trigger chain. The guard flag below is what stops that recursion. Version (b) has no such problem and is the one to prefer."

    Oracle-Database-Laboratories/sql/03_plsql/04_triggers.sql, 2026-07-25

    Two failure modes, not one. The re-entrancy is stopped only by a hand-managed settling boolean that every one of the three triggers must check — remove it from any of them and the chain recurses. And the state is package state: it persists for the session, so a statement that ends abnormally leaves the totals dirty for the next one, which is why the BEFORE STATEMENT trigger has to zero them by hand.

    #Version (b): one compound trigger

    "The compound trigger: one object, four timing points, state held in the trigger's own declaration section. No package, no globals leaking between statements, and the state is reinitialised automatically for each statement -- which is what the package version had to do by hand."

    Oracle-Database-Laboratories/sql/03_plsql/04_triggers.sql, 2026-07-25

    Three defects removed by one construct: no shared global, no manual reinitialisation, and — because the settlement UPDATE happens in AFTER STATEMENT of the same object rather than in a separate trigger watching the same column — no re-entrancy and therefore no guard flag.

    #Alternatives rejected

    Option Why not
    Three triggers + package variablesre-entrant; needs a hand-managed guard flag; session-scoped state must be zeroed by hand — stated in the repo
    Do the work in application code insteadnot considered in the repo; the rule is a database invariant and the exercise is trigger design

    #Why the inferior version stays in the tree

    Deliberately, and it is the interesting part of this decision. Both implementations sit in the same file, in order, with the trade-off written between them — this is keep-the-superseded-version-in-tree used pedagogically rather than archivally, and the local instance of multiple-solutions-side-by-side. Deleting version (a) would leave a compound trigger with no visible reason to exist.

    The cost is the usual one for duplication: two implementations of the same rule that must be kept in agreement, in a repository with no tests. They currently agree.
