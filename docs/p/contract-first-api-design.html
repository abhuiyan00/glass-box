    Contract-First API Design

    Write the API specification first; generate the code from it. The inverse — annotate the controllers and let a tool emit a spec afterwards — produces a document that describes whatever the code happens to do, which cannot be a contract because it can never disagree with the implementation.

    Contract-first makes the spec the artefact that other parties agree to, and makes drift a compile error rather than a documentation problem: if the handwritten class stops matching the generated interface, the build fails.

    #As implemented in lab 2

    lab2/StudentService/ in information-systems-modelling is the whole point of the lab:

    • An OpenAPI YAML document is the source. openapi-generator-maven-plugin 7.20.0 runs it at build time into target/generated-sources/openapi, wired onto the compile path by build-helper-maven-plugin — see maven.
    • interfaceOnly + delegatePattern. The generator emits only interfaces and a delegate seam; no controller body is generated, so regeneration never overwrites hand-written logic. This is the configuration that makes the pattern survive contact with a real codebase — the naive full-generation mode makes the generated tree unmergeable and the pattern gets abandoned.
    • springdoc-openapi-starter-webmvc-ui serves Swagger UI over the running app, so the contract is browsable rather than a file someone has to find.
    • Persistence via sqlite behind a layered-architecture split, on spring-boot.

    Four OpenAPI .yaml documents exist across the repo — the contract is carried forward with the rest of each lab under forward-copy-lab-progression.

    #Where it sits in the SDLC arc

    The repo runs one invented domain through requirements → contract → implementation → ontology → publishing → process models. Contract-first is the hinge between the prose requirements of lab 1 and the executable artefacts after it: the SRS says what the system must do, the OpenAPI document says exactly what the wire looks like, and only then is any Java written.

    The same instinct — hold the definition once, derive everything else — reappears as single-source-of-truth-generators in labs 6 and 7, and as generate-markup-instead-of-hand-writing-it. This repo applies it to APIs, to RDF markup and to BPMN diagrams, in three different technologies.

    #Limits observed

    • TODO: no requirement identifier from the lab 1 SRS is cited by any endpoint, schema or process model. The link from requirements to contract is narrative only — there is no traceability matrix in any format. confidence: low on any claim that the contract demonstrably satisfies the SRS.
    • The generated tree lives in target/, which inflated a naive source-file count of this repo from 134 to 231. Generated code being indistinguishable from source at a glance is a real cost of the pattern.
