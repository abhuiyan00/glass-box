    pnpm Over npm For The Capacitor Gradle Path

    Decision. Declare the farely monorepo as a pnpm workspace so that @capacitor/android resolves to apps/android/node_modules, where the gradle project's relative ../node_modules reference expects it.

    Date. 2026-07-13, recorded in CONTRIBUTING.md.

    #The reason, as written

    "pnpm vs npm: the repo declares a pnpm workspace, so pnpm install places @capacitor/android under apps/android/node_modules where the gradle project's ../node_modules reference expects it. With plain npm's hoisting you may need to ensure that path exists before building the APK."

    Farley/CONTRIBUTING.md, 2026-07-13

    This is a rare thing in the source set: a package-manager choice with its actual cause written down. The cause is not ergonomics or disk space — it is that capacitor's generated gradle project resolves a Node dependency by filesystem path, which turns node_modules layout into part of the build contract. npm hoists shared dependencies to the workspace root; pnpm's non-flat store leaves each package's dependencies under that package. Only one of those layouts satisfies a hardcoded ../node_modules.

    #Alternative rejected

    npm workspaces. Rejected for the hoisting behaviour above — and notably not rejected cleanly, see below. The failure mode it produces is nasty: nothing breaks at install time, and the error surfaces much later at gradlew assembleDebug as a missing gradle project, far from its cause. The CONTRIBUTING note exists precisely to shorten that debugging path.

    #The contradiction — decision recorded, not enacted

    The decision is documented and its alternative is named, but the repository does not implement it:

    • The only committed lockfile is package-lock.json. No pnpm-lock.yaml exists in the tree.
    • package.json declares npm workspaces: ["apps/*"] alongside pnpm-workspace.yaml.
    • Every root script is npm --prefix … — dev, build, sync, apk, cap:open.

    So the repo instructs pnpm install, ships an npm lockfile, and drives every task through npm. A contributor following the README produces a lockfile the repo does not track; a contributor running the scripts gets exactly the hoisting the note warns about. Both claims are recorded here rather than resolved — the documented decision and the committed reality disagree, which is documentation-drift reaching into the build system.

    Practically it has not bitten: the debug APK built successfully on the author's machine, and since Farely never ran on a live shift, that machine is the only environment the path has ever seen.
