    Split Frontend and Backend Hosting

    Decision: deploy the stickfps client as a static bundle on one host and the game server as a long-lived process on another, rather than shipping one application. Recorded as project constraint C5.

    "Vercel serverless functions time out at 10s and cannot hold a 60Hz authoritative loop — the game server needs a persistent process, so it's split out."

    browser_game_stickfps/PROJECT.md, 2026-07-25

    #The reasoning generalises past Vercel

    A serverless function is billed and scheduled per request; it has an execution ceiling and no identity between invocations. An authoritative game server is the opposite on all three axes: it runs continuously, it is the state (server-authoritative-netcode keeps every Room in memory), and its clock must not be interrupted (fixed-timestep-simulation at 60 Hz). Nothing about that is specific to one vendor — it disqualifies the whole serverless execution model, and it also rules out scaling by replicas without a room-affinity layer that does not exist here.

    The client, meanwhile, is the ideal serverless workload: a vite build with no server-side logic at all, deployable to any static host or CDN.

    Splitting lets each half be hosted on what suits it, and it is what allowed the backend host to be swapped entirely in render-over-fly-io without touching the frontend deployment.

    #What the split costs

    • Two deployments, in order. The backend must exist first, because VITE_* variables are inlined at build time — see vite. A server URL change is a frontend rebuild.
    • Cross-origin by construction. The CORS_ORIGIN allowlist and the WebSocket verifyClient origin check exist because of this split (ws-websocket-server).
    • Two idle behaviours to reason about. A static bundle is always warm; a free backend instance is not (render-hosting).

    #Status

    The split is real in the code and in the runbook. Whether both halves were ever deployed together is the open question on stickfps: the interview confirms multiplayer play over a real network, while docs/DEPLOYMENT.md states no deploy had been run as of the last commit, and no render.yaml or vercel.json exists in the tree.
