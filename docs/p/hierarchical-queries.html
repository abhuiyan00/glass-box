    Hierarchical Queries

    Walking a tree that is stored in a single self-referencing column. One row per node, one column pointing at the parent's key, and a query that traverses it to arbitrary depth without knowing the depth in advance. Oracle spells this CONNECT BY; ANSI SQL spells it as a recursive CTE.

    #The one thing that is easy to get backwards

    Direction lives entirely in which side of the join predicate carries PRIOR, and the source file states it at the top rather than leaving it to be discovered per query:

    CONNECT BY PRIOR nickname = chief   walks DOWN  (root -> subordinates)
CONNECT BY PRIOR chief = nickname   walks UP    (leaf -> chain of chiefs)

    Both appear in oracle-database-laboratories against the same CATS.chief self-reference — see circular-foreign-key for why a self-reference is not the awkward case.

    #The pseudocolumns

    Construct What it gives
    LEVELdepth relative to START WITH, not to the top of the tree — 1 at whatever the start clause selected
    SYS_CONNECT_BY_PATH(col, sep)the whole root-to-node path as one delimited string
    CONNECT_BY_ROOT colthe value of col at the row the walk started from

    LEVEL is also how the tree gets drawn: LPAD(' ', (LEVEL-1)*4) || … renders the indentation, one of the cheapest ways to make a relational structure legible — the same instinct as make-the-formal-object-observable reached without any tooling.

    #WHERE is applied after the walk

    The subtlety worth naming: filtering does not prune the subtree.

    "The WHERE clause is applied after the tree is walked, so pruning a cat here does not prune its subordinates -- which is exactly what is wanted: the shape of the hierarchy is preserved and only the display is filtered."

    Oracle-Database-Laboratories/sql/02_queries/02_hierarchical_queries.sql, 2026-07-25

    To prune the traversal itself you add the predicate to CONNECT BY, not to WHERE. Two clauses, two different meanings, and the difference is invisible on data whose filtered nodes happen to be leaves.

    #The same answer three ways

    "The chain of chiefs above every rank-and-file cat" is written three times in one file, and the comparison is the exercise — see multiple-solutions-side-by-side:

    Formulation Behaviour
    Repeated LEFT JOIN, one per levelexplicit and portable, but hard-codes the depth: a fourth tier needs another join
    CONNECT BY + PIVOTadapts to any depth by adding a value to the PIVOT IN list; still one column per level
    CONNECT BY + SYS_CONNECT_BY_PATHdepth-independent, but the answer is one string, so downstream consumers must parse it

    There is no winner. The trade is columns you can join against versus a shape that survives a deeper tree, and picking one is a statement about what happens to the result next.

    #The same walk over pointers

    04_object_relational/03_ref_navigation.sql runs CONNECT BY PRIOR c.nickname = c.chief.nickname over a REF column instead of a value-carrying foreign key. The traversal is unchanged; only the dereference differs — see object-relational-model.
