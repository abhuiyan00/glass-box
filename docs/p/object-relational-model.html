    Object-Relational Model

    A relational database with user-defined types layered on top: rows are objects, columns can be pointers to other objects, types carry methods, and a join becomes a dot. Oracle's implementation is the reference one; the ideas are older than any of the ORMs that reinvented them in application code.

    #The three moves

    1. CREATE TYPE … AS OBJECT — a structured type with attributes and MEMBER FUNCTION / MEMBER PROCEDURE declarations, plus a separate TYPE BODY.
    2. CREATE TABLE … OF type — a typed (object) table. Each row is an instance, addressable by a REF.
    3. REF type — a pointer column. DEREF(r) returns the whole object; alias.col.attr navigates in one step; VALUE(t) returns the row object itself.

    In oracle-database-laboratories the entire cat-herd domain is rebuilt this way as cat_type, common_type, elite_type, account_type and incident_type, alongside — not replacing — the relational schema. The two coexist in one schema, which forces the naming discipline: CatsR, IncidentsR, and _r-suffixed constraint names, because Oracle constraint names are unique per schema rather than per table.

    #A join becomes a dot

    -- relational
SELECT c.name FROM Cats c JOIN Cats chief ON c.chief = chief.nickname;

-- object-relational
SELECT c.chief.name FROM CatsR c;

    The second is shorter, and that is the whole sales pitch. It is also strictly less flexible: the navigation direction is fixed by which side holds the pointer, and there is no LEFT JOIN equivalent — a NULL REF simply yields NULL. Traversal still works: CONNECT BY runs over REFs once resolved to a comparable attribute, so hierarchical-queries carries over unchanged.

    #SCOPE FOR is the load-bearing detail

    "SCOPE FOR constrains the REF to one table. Without it a REF may point at any table of the type, the pointer needs more storage, and Oracle cannot resolve dot navigation as efficiently."

    Oracle-Database-Laboratories/sql/04_object_relational/01_types_and_tables.sql, 2026-07-25

    Three benefits from one clause — smaller pointer, faster navigation, and a correctness guarantee that the pointer cannot stray to an unexpected table of the same type. An unscoped REF is a foreign key with no target table named, which is not a thing the relational model would ever have allowed.

    #What the model does not give you

    • Dangling references are possible. Delete the row a REF points at and the pointer survives its target. IS DANGLING is the only reliable test. A foreign key would have refused the delete or cascaded it; a REF does neither by default. This is the single clearest reason the relational model is still the default.
    • Methods run per row. get_total_eats() puts the NVL arithmetic on the type instead of at every call site — genuinely better than repeating it — but it is a function call per row, not a set operation.
    • Type signatures must match their bodies exactly. Declaring RETURN DATE over a TO_CHAR body makes Oracle convert the string back through the session's NLS format: silent on a matching session, PLS-00382 on any other. The file names this trap where it occurs.
    • SELF is IN OUT by default in a MEMBER PROCEDURE, so assigning to an attribute mutates the instance the caller holds. Convenient and easy to miss.

    #The honest assessment

    The object-relational layer buys terser navigation and lets domain logic live with the data. It costs referential guarantees, portability, and a second set of teardown rules — object tables must be dropped before the types they are built on, since FORCE would leave the table invalid rather than removing the dependency. Compare database-normalisation: the relational model is a set of guarantees you give up piece by piece, and each concession should be named.
