    Jaccard Similarity Set Selection

    Using a set-overlap score not to rank items but to partition a corpus into what you have already seen and what you have not. set-similarity-metrics covers Jaccard, Dice and cosine as metrics; this page is about the specific job they are put to in physics-exam-prep — picking a maximally *dis*similar study set.

    #The construction

    tools/build_sets.mjs has one input pair and one question:

    • Set 1 — the 30 questions from the real scanned exam, transcribed.
    • The bank — 75 questions written for the app.

    " Jaccard(A,B) = |A∩B| / |A∪B| over normalized token sets"

    Physics/exam_prep/tools/build_sets.mjs, 2026-07-10

    Each question becomes a token set: stem plus all choices, lowercased, split on non-alphanumerics, with a 100-word hand-written stopword list removed. For every Set-1 question the script finds its nearest neighbour in the bank, then:

    • Set 2 — "similar": every bank question that is some exam question's nearest neighbour with score ≥ TH. 16 questions.
    • Set 3 — "coverage gaps": the complement — every bank question that is not. 59 questions.
    const TH = 0.10;                      // nearest-neighbour threshold for "similar"

    Set 2 ∪ Set 3 = 75 and Set 2 ∩ Set 3 = ∅ by construction, and the generated audit asserts both.

    #The inversion that makes it interesting

    Similarity search normally returns the most similar items. Here the useful output is the residue: the questions with no close match are the ones the exam does not touch, so Set 3 is the study list. The metric is run forwards and the answer is read backwards.

    #Cosine is a cross-check, not a second opinion

    "/ binary cosine over the same token sets — reported as a cross-check on Jaccard /"

    Physics/exam_prep/tools/build_sets.mjs, 2026-07-10

    Cosine is computed over the identical token sets and reported (mean nearest-neighbour 0.292 against Jaccard's 0.175) but never used for selection. That is the right call and a real distinction: on sets, Jaccard and Dice are monotone transforms of each other and rank identically, while cosine divides by √(|A|·|B|) and can reorder pairs when the two sets differ sharply in size — so it is a genuinely independent read on whether the overlap structure is an artefact of question length. Running it and not acting on it is the discipline.

    #The pedagogical leap, and the one check that supports it

    The design assumes low lexical similarity ⇒ topic coverage gap, which does not follow in general: two questions can share almost no vocabulary and test the same idea. Nothing in the script argues the equivalence.

    But the generated audit happens to test it from the other side, using topic ids assigned by hand rather than by the metric: Set 1 touches 15 of 29 topics, Set 2 touches 14, and Set 3 touches all 29 — so the union covers every topic and the 14 topics the exam misses are exactly the ones the audit lists. The lexical proxy and the hand labels agree here. That is one corroboration on one corpus, not a validation of the assumption.
