    Embedded Systems and IoT Laboratories

    Four Arduino exercises rebuilt as one testable C++17 project. The logic — button edges, stopwatch transitions, ADC filtering, UART command parsing — lives in a hardware-independent core; the sketches contain pin numbers and I/O and nothing else.

    20 tests pass on a laptop before a wire is connected.

    #The move that makes it possible

    Embedded coursework is usually untestable for one structural reason: the logic is written inside loop(), where it can only be reached by a board. Lifting it out is the whole design — separating-computation-from-io and pure-domain-engine-shared-across-hosts applied to a microcontroller, with the sketch as one host and the native test binary as the other.

    The core has no Arduino dependency, no heap allocation, no exceptions and no blocking calls. That list is not minimalism for its own sake; each entry is a constraint that an 8-bit target imposes and that a desktop compiler will happily let you violate.

    #The four labs and the failure each one prevents

    Lab State machine Failure prevented
    01 · Button counterindependent debouncers + bounded counterbounce-driven double counts, and while-loop lockups waiting for release
    02 · Stopwatchreset → running → pausedelapsed time lost across pause/resume
    03 · Voltage monitormoving average + sample schedulersingle-sample noise, and the 1024-vs-1023 conversion error
    04 · UART LEDstrict parser + non-blocking blinkerprefix commands accepted, invalid intervals, blocking delay()

    The 1024-vs-1023 one is the classic. A 10-bit ADC returns 0–1023, so full scale is code 1023, not 1024; dividing by the wrong constant produces a reading that is plausible, consistently slightly wrong, and never noticed on a lab bench.

    #Three rules that generalise

    Events, not sleeps. Debouncing and blinking are timestamp-driven. delay() is not a timing primitive, it is a promise that nothing else happens — which on a single-threaded controller means serial input dropped and a display not refreshed while an LED is "blinking".

    One clock rule: always now - then. Every scheduler compares elapsed time using unsigned subtraction. The natural-looking now > then + interval overflows and fails around the 49.7-day millis() rollover, and unsigned wraparound makes the subtraction form correct through the rollover rather than in spite of it. This is a bug with a 49.7-day reproduction time, which is to say a bug that is never reproduced.

    Reject, do not guess. The UART parser accepts exactly LED ON, LED OFF, LED STATUS and LED BLINK <20..60000>. Extra suffixes, partial numbers, empty intervals and overlong lines are refused. A parser that accepts a prefix is a parser that will one day act on a truncated transmission.

    #Verification

    scripts/test.ps1 or scripts/test.sh, needing only a C++17 g++; build products go to the OS temporary directory rather than the repository. Expected output is literally 20 tests passed.

    tools/ generates a deterministic state trace for all four labs — the headless counterpart to the SVG guide in assets/, and the thing to read when no board or LCD is available. Compare make-the-formal-object-observable: a state machine you can print is a state machine you can argue about.

    A 2026-08-12 local audit passed the warning-as-error C++17 build and all 20 native tests. The headless trace then exercised the documented button, stopwatch, voltage-monitor, and UART states. The run used an external temporary root because the sandbox cannot use the owner's Temp directory; that is a test-host restriction, not evidence of board validation.

    #Open gaps

    • TODO, and it is the honest headline: the native suite proves deterministic logic, not electrical correctness. Board voltage, ADC reference tolerance, switch wiring, LCD address (0x27 by default) and serial signal quality all still require hardware validation, and no physical-board result is claimed anywhere in the repository.
    • TODO: Lab 02 needs a third-party LiquidCrystal_I2C library, which is not vendored and not tested here.
    • TODO: Uno-class targets assumed. The timing rules hold generally; the pin configuration does not.
