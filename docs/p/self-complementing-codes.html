    Self-Complementing Codes

    A binary code for decimal digits is self-complementing when inverting every bit of a code word yields the code word for the nine's complement of that digit:

    for every digit d:   decode( NOT encode(d) ) == 9 - d

    That single property is what separates four codes that are otherwise usually presented as four tables to memorise.

    code weights self-complementing
    BCD 84218, 4, 2, 1no
    BCD 84-2-18, 4, −2, −1yes
    Aiken 24212, 4, 2, 1yes
    Excess-3none — digit + 3yes

    #Why it matters

    Decimal subtraction is usually done by adding a complement. In a self-complementing code that complement is a bitwise NOT — one gate per bit, no carry, no arithmetic. In BCD 8421 it is an arithmetic step, because inverting 0000 gives 1111, which is not a digit at all.

    Excess-3 is self-complementing for a reason worth seeing rather than memorising: 3 + 3 = 6 and 9 + 6 = 15, which is all ones. Encoding d as d + 3 makes the pair d and 9 − d sum to fifteen by construction, and summing to all-ones is being bitwise complements.

    #Compute the property, do not declare it

    The useful move is to make is_self_complementing a computation over the code's own table rather than a boolean field:

    @property
def is_self_complementing(self):
    for digit in range(10):
        if self.decode(self.invert(self.encode(digit))) != 9 - digit:
            return False
    return True

    A code added later is then classified correctly without anyone remembering to set a flag. This is the same instinct as counted-complexity-assertions: state the property in a form that can be checked, not in a form that has to be maintained.

    #The trade it buys, measured

    Self-complementing is not free. Each code needs a correction when two words are added, and the count over all 100 single-digit pairs is where the real comparison lives:

    code corrections per 100 pairs character of the correction
    BCD 842145conditional +6, fires when the sum leaves the digit set
    Aiken 242125±6, and it must go both directions
    Excess-3100always, but unconditional — only the sign varies

    Excess-3 corrects on every pair and is still the cheapest in hardware, because an adder that always runs is simpler than one that decides. Fewest corrections does not mean least work.

    #The near miss

    Aiken's assignment is not unique. Two patterns satisfy the self-complementing constraint for digits 5 to 7, and a generator that takes the first one found produces a genuinely self-complementing code that is not Aiken's — passing every round-trip test and disagreeing with the published table.

    The published tie-break is: digits 0-4 take the lowest valid pattern, 5-9 the highest. That is what opens the six-pattern gap in the middle of the code, and the gap is what makes the inversion land correctly.

    A property test that only checks the property will not catch this, which makes it a clean instance of tests-that-pass-for-the-wrong-reason: the code satisfied the specification it was tested against and was still the wrong code.
