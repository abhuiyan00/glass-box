    Anthropic Messages API

    The only path in farely by which content leaves the phone. Used for one job: classifying a screen the on-device keyword classifier could not name. The gating that makes it optional is the subject of opt-in-cloud-fallback; this page is the integration itself.

    #Call shape

    • vision.ts — classifyScreen(capture, apiKey), VISION_MODEL = "claude-opus-4-8", max_tokens: 700, header anthropic-version: 2023-06-01.
    • Strict-JSON classifier prompt. The response is constrained to class ∈ {offer, trip, idCheck, appUpdate, unknown} and action ∈ {freeze, note, map-control, none} — a small closed vocabulary the caller can switch on, not free prose. The prompt also explicitly instructs the model to never propose tapping accept, mirroring never-automate-the-accept-tap at the model boundary rather than trusting downstream code to filter it out.
    • Result carries VisionResult.method: "cloud" | "on-device", so provenance survives into the UI.

    #Three transports, one function

    CapacitorHttp on the device (native HTTP, sidesteps WebView CORS), a /anthropic Vite dev proxy in local development, and a direct fetch with anthropic-dangerous-direct-browser-access otherwise. That header is the notable one: it exists because browser-side calls put the key in the browser. Here the key is the driver's own, entered in Settings and persisted to localStorage in plaintext — never committed, never bundled, and .gitignore excludes .env*, *.pem, *.keystore, *.jks. The plaintext storage is a real residual risk and is not stated as a limitation anywhere in the repo.

    #Cost control

    Because it is billed per call, the gating is the design: no key ⇒ no call at all; only WINDOW_STATE_CHANGED events; a novelty-keyword gate; ≥5 minutes between calls per platform; and an early return whenever the coordinator is frozen. Every call is written to on-device-black-box-diagnostics as a vision event, so spend is observable after the fact without any server.

    • TODO: vision.ts hardcodes the most capable vision model with a comment offering a cheaper Haiku swap, for a fallback that fires at most once per five minutes per app. No rationale is recorded and it was not asked at interview — confidence: low on why that model.

    #Doc conflict

    docs/SRS.md §3.x sequence diagrams show the cloud call as normal flow, while the post-2026-07-24 README calls the same path "ships off by default" and VISION §5 calls it "a deliberate trade-off I switched on". Three documents, three postures toward one code path — see documentation-drift and the accuracy note on on-device-first-inference.
