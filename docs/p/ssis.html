    SQL Server Integration Services

    Microsoft's ETL tool: packages authored as .dtsx in Visual Studio / SSDT, built from a control flow of tasks and, inside a Data Flow Task, a data flow of typed sources, transforms and destinations. data-warehousing-and-business-intelligence ships two packages, and they use the tool in two different ways.

    #Package 1 — control flow only

    etl/ssis/Package.dtsx builds a list_four schema entirely out of Execute SQL tasks. SSIS is doing orchestration here, not transformation: the SQL is the deliverable and the package is the runner. Two things about it are worth recording.

    • Its DIM_CUSTOMER load joins addresses through the store id only, where the hand-written sql/02_star_schema/ version uses a coalesce across store and person and says why.
    • It creates a load_status table and populates it with 'Success' string literals — a row per table, written unconditionally. The hand-written load replaces exactly this with row counts and anti-join integrity checks, and argues the case in a comment. That contrast is the whole of verify-the-load-dont-declare-it, and it is unusual to have both the pattern and its counter-example in one repository.

    The two schemas disagree on column set and defaults and were never reconciled — one of four recorded instances of documentation-drift in this repo, and an example of keep-the-superseded-version-in-tree.

    #Package 2 — a real data flow

    project/twtr/ssis/Package.dtsx is the conventional shape: a Flat File source and an OLE DB destination inside one Data Flow Task, landing a CSV of daily price bars into a staging.quotes table. The staging table carries two CHECK constraints at the door — a high/low ordering rule and a non-negative volume rule — so malformed rows fail at the boundary rather than propagating into the star. Loading order from there on is etl-load-order; the destination model is star-schema.

    The CSV itself is git-ignored, so the package is committed without the input it consumes.

    #Working with .dtsx in version control

    A package is XML, so it diffs — in principle. In practice a 23 KB and a 37 KB file of generated markup with embedded, newline-escaped SQL is not reviewable by reading the diff, and the SQL inside it is invisible to any tool that greps *.sql. That is a real argument for the shape this repo mostly settled on: keep the logic in .sql files, and let the package be a thin runner over them.

    #Status

    Both packages are Visual Studio project sources, not deployed to any SSIS catalog. docs/star-schema.md makes the same disclosure for the ssas side. Nothing here executes on a clean clone — it needs SSDT and a live sql-server instance.
