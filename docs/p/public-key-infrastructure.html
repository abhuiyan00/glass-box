    Public Key Infrastructure

    The answer to the question asymmetric cryptography leaves open: you hold a public key, but whose is it? PKI is the set of roles, policies and formats that binds a public key to an identity in a way a third party can check. Lab 07 of cybersecurity-engineering-laboratories builds one end to end.

    #The roles

    Role Does
    End entitythe subject a certificate is issued to; holds its own private key
    Certification authority (CA)signs certificates, asserting the key↔identity binding
    Registration authority (RA)verifies identity before the CA signs; optional, folded into the CA when absent
    CRL issuerpublishes revocations for certificates that must stop being trusted early
    Certificate repositorystores certificates and CRLs so relying parties can fetch them

    The dominant format is X.509 v3. A certificate is a structured document — subject, public key, issuer, validity window, extensions — signed by the issuer's private key. Verification is recursive: check the signature using the issuer's public key, which comes from the issuer's certificate, up to a root you already trust. The chain terminates in a decision, not in a proof. Root certificates are trusted because they were shipped with the operating system or the browser, and that is the actual foundation of the whole edifice.

    #Why the CSR is generated on the client

    The certificate signing request carries the public key and the identity to be certified, and it is generated on the subject's own machine for one reason: the private key never leaves it. If the CA generated the keypair, the CA would have held the private key, and non-repudiation — the property digital-signatures exists to provide — would be gone. This is the single most load-bearing procedural detail in PKI and the lab records it explicitly.

    The practical corollary shows up in this repository's own handling rules: a .p12 bundle is a private key container by definition, so none are committed, and the natural illustration for this lab was rejected because it printed a private key to a terminal. See omit-rsa-private-key-screenshot.

    #What the lab built

    RSA keypair generation, signing and verification via openssl; a parallel OpenPGP keypair (ECC and RSA) via GnuPG; a certificate authority stood up with Easy-RSA, a CSR issued and signed, and the resulting certificates used for OpenVPN in the secure-communication lab. Also PKCS#12 packaging and HMAC.

    The two trust models placed side by side is the useful part. X.509 is hierarchical — trust flows down from roots, and revocation is centralised through CRLs (or OCSP). OpenPGP is a web of trust — peers sign each other's keys and each relying party decides how much transitive trust to extend. The same cryptographic primitives, two entirely different governance answers to "whose key is this".

    #Where PKI shows up in transport security

    TLS is the mass deployment. The server presents a certificate chain, the client validates it against its trust store, and only then does key agreement proceed — which is exactly the authentication step whose absence makes unauthenticated Diffie–Hellman vulnerable to a man-in-the-middle-attack. Lab 09 inspects TLS 1.2 and 1.3 handshakes in wireshark and captures an OpenVPN tunnel interface against the underlying one, confirming that an observer outside the tunnel sees ciphertext. See cia-triad for the properties being claimed and symmetric-vs-asymmetric-cryptography for the hybrid construction underneath.

    #The parts that are hard in practice

    Revocation is the weak joint: a certificate is valid until it expires unless something actively says otherwise, and CRL/OCSP distribution is slow, cacheable and frequently fails open. Certificate lifetime management, key rotation and CA compromise are all operational problems that the mathematics does not touch, and none of them are exercised in a single-session lab.
