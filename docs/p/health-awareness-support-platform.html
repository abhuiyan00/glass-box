    Health Awareness Support Platform

    Clearpath — a Django health-education product rebuilt from a bachelor capstone by the same author. Server-rendered, no client framework, synthetic users only, and explicit about being not a medical device: it does not diagnose, triage, treat, or stand in for a professional.

    The rebuild exists because the student-era version did not have the controls described below. Authorship settles ownership, not quality — a distinction the repository states itself rather than leaving to a reader.

    #The design problem

    A health application is the case where the two obvious product instincts are both wrong. Collecting more makes the recommendation better and the breach worse; saying more makes the advice useful and the liability real. The reconstruction resolves both by removing capability, and records what it removed in docs/product-decisions.md rather than quietly not building it.

    The prompt function takes three broad self-ratings and returns one educational route. It cannot infer a condition, compute a risk score, contact a third party, or turn free text into a profile. That is a deliberate ceiling, not an unfinished feature — data-minimisation applied at the point where the data would have been useful.

    #What carries the weight

    Deterministic rules instead of a score. Selection is a pure function in learning/services.py — no model, no opacity, no training data. A reader can predict its output, and a test can pin it. The same instinct as separating-computation-from-io: the part that decides is the part with no I/O in it.

    Ownership filters on the server, with tests that try to break them. Check-ins and progress records belong to an account, and the query boundary is enforced in the view rather than in the template. learning/tests.py includes cross-user disclosure attempts — the tests that only exist if someone thought to act as a second user, which is exactly the omission that produced authorization-in-the-query-predicate in the neighbouring project-management-web-platform.

    Response security as configuration, not folklore. CSRF on every state change, POST-only mutations, secure cookie defaults, CSP, clickjacking and referrer policies. These are the controls a capstone demo reliably skips because nothing visible breaks without them.

    No committed secret, database, or upload. Demo seeding is idempotent and takes its password from DEMO_PASSWORD in the environment — secrets-from-environment-only — and the seeded users are invented. Compare generate-fixtures-not-commit: a fixture that must be generated cannot be leaked by being checked in.

    #Privacy as a document, not a posture

    docs/privacy-threat-model.md names the adversaries and the boundaries rather than asserting that the application "takes privacy seriously". It is the artefact that makes the product decisions auditable, and it is why the removed features are legible as choices. Related: privacy-documented-beside-the-feature, disclosure-gate, controller-vs-processor, gdpr-legal-bases.

    The evidence boundary is stated in the same register: learning content is a small demonstration that links to its publisher, and the README lists what a real service would additionally need — clinical governance, dated review, regional crisis routes, translation review, withdrawal procedures. See provenance-and-limits-stated-inline.

    #Verification

    manage.py test, plus makemigrations --check --dry-run so a model change cannot land without its migration, plus manage.py check. The test suite covers privacy, CSRF, publication state, validation, response headers, and the prompt rules.

    A 2026-08-12 local audit ran that documented gate unchanged: 11 Django tests passed, migrations were current, and Django reported no system-check issues. The wide and narrow real captures were also reviewed manually; the page remains a strong reference for the stated-limit and real-visual parts of the repository style.

    The landing capture in assets/ is generated from the running application by a repeatable headless procedure, not drawn as a mock-up — the same standard applied across the collection.

    #Open gaps

    • TODO: SQLite only. The committed schema and the tests are the evidence; a real deployment needs a managed database, TLS, backups, monitoring, a retention policy and an incident process, and the README refuses to pretend a development container supplies them.
    • TODO: no public signup, password reset, social login or analytics. Deliberate, but it means the authentication surface is narrower than a real product's.
    • TODO: learning content is a demonstration set. Without editorial governance it should not be read as health guidance, which is why every module is source-labelled.
