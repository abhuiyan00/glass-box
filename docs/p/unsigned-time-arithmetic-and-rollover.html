    Unsigned Time Arithmetic and Rollover

    A millisecond counter in a fixed-width unsigned type wraps to zero. On a 32-bit millis() that happens after 49.7 days. Whether the wrap is harmless or fatal is decided by one line of arithmetic.

    if (now - then >= interval)          // correct through the rollover
if (now > then + interval)           // fails at the rollover

    #Why the subtraction form survives

    Unsigned arithmetic in C and C++ is defined to wrap modulo 2ⁿ. So when now has wrapped and then has not, now - then also wraps — and comes out as the true elapsed interval, not as an enormous number. The overflow in the subtraction cancels the overflow in the clock.

    The addition form has no such symmetry. then + interval overflows to a small number, the comparison now > small becomes true immediately or stays false for weeks depending on where the wrap fell, and the scheduler either fires continuously or never fires again.

    The rule is worth stating positively, because it generalises past clocks: compare differences, not sums. Any monotonically increasing counter in a bounded type — sequence numbers, tick counters, byte offsets — behaves the same way.

    #Why it is almost never caught

    The reproduction time is 49.7 days of continuous uptime. No test suite waits for it, no lab demonstration reaches it, and no code review notices it, because the wrong form is the one that reads more naturally in English: "if now is past then-plus-the-interval".

    It is therefore a defect discovered exclusively in deployed systems, months after the person who wrote it moved on. That profile — invisible to every check that exists, correct in every observation anyone makes — is the same one that makes tests-that-pass-for-the-wrong-reason worth its own page.

    The fix in a test suite is not to wait. It is to make the clock a parameter, so a test can hand the state machine a timestamp near the wrap boundary and assert the transition. That is available only if the logic was lifted out of loop() first — see separating-computation-from-io.

    #The related trap: blocking instead of scheduling

    delay() is not a timing primitive; it is a promise that nothing else happens. A "blink" implemented with delay() drops serial input and freezes display refreshes for its duration, on a controller with no other thread to pick up the slack. Timestamp-driven scheduling — record then, return, and check the difference on the next pass — is what makes several timed behaviours coexist in one loop.
