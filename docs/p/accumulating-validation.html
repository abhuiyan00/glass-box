    Accumulating Validation

    Validation that reports every failure at once, rather than throwing on the first one — and that never constructs the object while it is still deciding whether the object should exist.

    Two properties, and the second is the one that gets missed.

    #Why fail-fast is the wrong default at a boundary

    Throwing on the first bad field is correct for an invariant violated inside a system. It is wrong at an input boundary, where the caller is a person or another service:

    • A form that reveals one error per submission takes five round trips to fill in five fields wrong, and each round trip is a chance to break a field that was previously fine.
    • An API that returns one error per request cannot be driven by a client that wants to correct its payload, so the client guesses.
    • A batch import that stops at the first bad row makes the operator discover the file's problems one deploy at a time.

    The shape of the answer follows from the shape of the question: "is this valid?" has one answer, but "what is wrong with this?" has a list.

    #The part that is easy to miss

    Exception-based validation usually runs after construction. The object is built, then checked, then thrown away — which means a half-valid instance existed, was reachable, and in a mutable design may have been stored, logged or passed to a listener before anyone decided it was invalid.

    Accumulating validation inverts that: gather the failures, and construct only on the empty-failure branch. The type then carries a real guarantee — if you are holding one, it passed. There is no state in which an invalid instance exists, so no code downstream needs a defensive re-check, and no test needs to cover "what if a partially valid object gets through".

    validate(raw) -> Either[List[Error], TeamMember]

    Errors are a list because there may be several; success is the constructed value because there is nothing else to say.

    #What it costs

    The validators must be independent, since all of them run. Dependent checks — "this field is required when that one is set" — either become one combined check or need ordering, and pretending otherwise produces a cascade of confusing messages derived from a single root cause. A missing file reported as five errors is worse than one.

    The other cost is discipline about the error type. A list of strings is enough to display and not enough to act on; a list of structured failures with a field reference is what lets a client attach each message to its input. Compare the details object in distributed-systems-protocol-labs, which exists for the same reason.

    #Relation to error-as-value

    This is the boundary case of returning failures as values rather than raising them. The same rebuild applies it throughout: Either and validated result types instead of null, unchecked casts, or sentinel numbers — each of which is a failure the type system was offering to catch for free. See functional-programming-scala-laboratories.
