    SQL Server

    Microsoft's relational engine, driven here as T-SQL on SQL Server 2019 across seven annotated scripts in data-warehousing-and-business-intelligence — two analytics labs, a star-schema DDL/ETL pair, and a three-script pipeline for the price mart.

    #The analytics surface

    sql/01_analytics/ is a tour of the reporting operators the engine provides and portable SQL does not: PIVOT for months-across-years-down crosstabs, ROLLUP and GROUPING SETS for subtotal rows, GROUPING() to tell a subtotal NULL apart from a data NULL, CASE banding, and ROW_NUMBER for profiling. These are the operators that make a BI query one statement instead of a union of five.

    #Locale is a correctness problem, not a display problem

    Two comments in the repo make the same point about the same class of bug — functions whose output depends on server configuration rather than on the data:

    • DATENAME(MONTH, ...) returns the session language's month name, so a PIVOT whose IN list is a set of English literals silently produces all-NULL columns on a differently configured server. The fix used is CHOOSE(MONTH(...), 'January', ...) — an explicit mapping.
    • DATEPART(WEEKDAY, ...) depends on SET DATEFIRST.

    "DATEPART(WEEKDAY) depends on SET DATEFIRST, which varies by server language. This form is absolute: 1 = Monday, 7 = Sunday, everywhere."

    Data-Warehousing-and-Business-Intelligence/sql/02_star_schema/02_load_star_schema.sql, 2026-07-25

    The replacement is (DATEDIFF(DAY, '19000101', d.[Date]) % 7) + 1 — arithmetic on a fixed epoch, which no session setting can move. Both fixes trade a readable builtin for a form whose result is a function of the input alone.

    #Types chosen against the default

    Prices are DECIMAL(18, 6), never FLOAT, and the reason is written down: binary floating point cannot represent a decimal price exactly, so sums drift and equality comparisons stop being reliable. The AdventureWorks fact carries DECIMAL(19,4) money columns and a DECIMAL(38,6) line total for the same reason. DailyRange AS (High - Low) PERSISTED is a computed column materialised on write — derived data that cannot drift out of sync with its inputs.

    #ISNULL, not DEFAULT

    "ISNULL, not the column DEFAULT. A DEFAULT applies only when no value is supplied; selecting an explicit NULL into the column bypasses it, so the declared 'Unknown' would never take effect."

    Data-Warehousing-and-Business-Intelligence/sql/02_star_schema/02_load_star_schema.sql, 2026-07-25

    A DEFAULT constraint is a property of the insert statement, not of the column. An ETL that projects a source column straight into the target never triggers it. This is the kind of thing that looks fine in a schema review and produces a dimension full of nulls in production.

    #Other engine features leaned on

    OUTER APPLY to pull one correlated row per customer (a primary address) without a window function or a subquery-in-select. IDENTITY(1,1) for the repo's single true surrogate key — see surrogate-vs-natural-keys. Window frames with ROWS BETWEEN 13 PRECEDING AND CURRENT ROW carry the whole moving-average indicator: window-function-frames and relative-strength-index. Foreign keys and CHECK constraints are declared and relied on rather than enforced in application code — see verify-the-load-dont-declare-it.

    #The cost

    SQL Server is the heaviest environment in the source set. Running any of this needs a live SQL Server 2019 instance with both AdventureWorks2019 and AdventureWorksDW2019 attached, plus SQL Server Data Tools for the ssis and ssas projects. Nothing in the repo executes on a clean clone, and no query output is committed. That is precisely why the price indicator was re-expressed in Python over sqlite as a runnable specification — reference-implementation-as-specification — and it is the sharpest contrast in the source set with zero-dependency-no-build-step.
