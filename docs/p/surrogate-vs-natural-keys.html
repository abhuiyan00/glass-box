    Surrogate vs Natural Keys

    A natural key is the identifier the source system already uses — a product id, a customer id, an order-line id. A surrogate key is a meaningless integer the warehouse mints itself, usually with IDENTITY or a sequence. Standard Kimball practice prefers surrogates in dimensions, because they insulate the warehouse from source-system renumbering and because Type-2 history needs one row per version of an entity and a natural key cannot be unique across versions.

    #The contrast inside one repository

    data-warehousing-and-business-intelligence does it both ways, in two marts built by the same author, which is what makes the trade-off legible rather than theoretical.

    Retail mart Price mart
    DIM_PRODUCT / DIM_CUSTOMER / DIM_SALESPERSONnatural — the source ids are the PKs—
    DIM_TIME / DIM_DATEsmart natural — yyyymmdd as an INTsame convention
    DIM_TICKER—surrogate — TickerKey INT IDENTITY(1,1), with Symbol kept UNIQUE
    Fact PKthe source order-line id, a degenerate keycomposite of the two dimension keys

    DIM_TICKER is the only true surrogate in the repository. It also carries ListedOn / DelistedOn — a hand-rolled validity window that is the closest thing to slowly-changing-dimension handling anywhere in the repo, and it is populated by a single hard-coded row.

    #The date key is the interesting middle case

    CONVERT(INT, CONVERT(CHAR(8), d.[Date], 112)) produces 20240115. It is natural (derivable from the date), surrogate-shaped (a compact integer that joins fast), and human-readable in a query plan — which is why the yyyymmdd integer is near-universal for calendar dimensions and is used in both marts here.

    #What the absence of surrogates costs here

    Because every load is truncate-and-rebuild, the usual argument for surrogates — supporting Type-2 history — never has to be made. There is no SCD handling in this repository at all: no EffectiveFrom/EffectiveTo, no IsCurrent, no version rows. Natural keys are adequate precisely because history is not kept. That is a coupling worth naming: the key choice and the load strategy in etl-load-order are the same decision seen from two sides. See also fact-grain.
