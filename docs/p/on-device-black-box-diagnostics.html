    On-Device Black Box Diagnostics

    When you cannot attach a debugger — the user is driving, the failure is a screen you have never seen, and no telemetry may leave the device — record a bounded local flight recorder and give the owner a button to export it. It replaces the observability a server would have given you, without becoming a server.

    farely's implementation: indexeddb database farely-diag, one events store keyed by id with a ts index, ring-buffered to DIAG_CAP = 2000, manual JSON export to a dated filename.

    #The design rules that make it a black box rather than a log

    • Bounded, never growing. A ring buffer means the feature cannot fill a driver's phone. Old rows fall off; that is accepted, because the interesting failure is always recent.
    • Never throws, never blocks. Writes are fire-and-forget; a diagnostics failure must not take down the thing it is diagnosing. If IndexedDB is unavailable, an in-memory bounded fallback takes over and the app does not notice.
    • Zero dependencies. diagStore.ts is hand-written against the raw IndexedDB API — the module-level survival of zero-dependency-no-build-step inside a repo with ~40 direct dependencies.
    • Export is a user action. Nothing is uploaded. The data is only useful if the owner chooses to look at it, which is what keeps it compatible with on-device-first-inference.

    #What is recorded

    Eight DiagKinds: error, exception, decision, unknown-case, vision, coord, network, events. The two that carry the design weight are decision — every ACCEPT / MARGINAL / DECLINE with the inputs that produced it, so a wrong verdict can be re-argued afterwards — and unknown-case, the screens the local classifier could not name. The unknown-case stream is the tuning input for taught-selectors-over-guessed-labels: rather than escalating to a model, unknown screens accumulate until the driver teaches the selector.

    A farely:diag CustomEvent mirrors every write to a live in-app view, so the recorder doubles as the debug UI with no second code path.

    #As an audit artifact

    The exported farely-diagnostics-YYYY-MM-DD.json is a self-generated evidence file about the app's own behaviour — a new form of generated-audit-artifact, where the artifact is produced by the running product rather than by a build step.

    #Limit worth stating

    The store is unencrypted, like everything else in the app's local persistence, and decision rows contain the driver's earnings inputs. The repo does not state this as a limitation anywhere.
