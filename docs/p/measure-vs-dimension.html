    Measure vs Dimension

    In a star-schema, a measure is a number you aggregate; a dimension is a thing you aggregate by. The test is not the data type. It is whether the value describes an entity that exists independently of the fact, or is itself an observation made at the fact's grain.

    A derived number computed from the fact's own measures — a ratio, a moving average, an indicator — is still a measure. Giving it a dimension table inverts the arrow: the fact would then reference a table whose rows only exist because the fact does.

    #The worked argument

    data-warehousing-and-business-intelligence argues this at length for a technical indicator:

    "It is tempting to give an indicator its own dimension table, with the value and a pair of overbought/oversold flags. That inverts the star"

    Data-Warehousing-and-Business-Intelligence/docs/star-schema.md, 2026-07-25

    The second half of the argument is about thresholds, and it generalises well beyond finance:

    "Storing them would freeze one analyst's convention — 70 and 30 — into the warehouse, so moving the threshold would mean rewriting history."

    Data-Warehousing-and-Business-Intelligence/docs/star-schema.md, 2026-07-25

    A stored boolean is a materialised interpretation. Change the convention and every historic row is wrong. The repo's answer is to store the continuous measure on the fact and derive the flags in a view, where the cut-points are one edit away. The cost is stated rather than hidden: reading a single day's indicator now takes two joins.

    #Two shapes of "derived"

    Stored on the fact Derived at read time
    Example herethe indicator value, DailyRange as a PERSISTED computed columnthe overbought/oversold flags, in a view
    Whyexpensive to recompute, convention-freecheap, and encodes a convention that may change

    The dividing line is whether the value embeds a judgement. Numbers are stored; judgements are derived. That is the transferable rule.

    #The repository contradicts itself

    The SQL side ships the argument's winner. The SSAS side ships the loser: Dim RSI.dim exists with RSIKey, IsOverbought, IsOversold and DateKey attributes — exactly the design the document rejects — alongside a second cube built on it. See rsi-as-measure-not-dimension, keep-the-superseded-version-in-tree and documentation-drift.
