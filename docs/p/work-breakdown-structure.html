    Work Breakdown Structure

    Hierarchical decomposition of a project's total scope into progressively smaller deliverables, until the leaves are units small enough to estimate, assign and schedule. Everything else in computer-project-management — dependencies, resourcing, critical path, cost — hangs off this one structure. It is the spine, not a diagram.

    #The shape used

    Three levels plus a milestone layer, held constant across all five lab stages:

    Level Count Example
    Phases (level 1)3Preparatory · Execution · Finalization
    Task groups (level 2)9System requirements analysis, Platform development, Testing phase
    Working tasks (level 3)26Market research Europe–Asia routes, Backend API development, User acceptance testing
    Control-point milestones7one 0-day checkpoint closing each main block of work

    Milestones are not a fourth level of work — they are zero-duration markers attached to the outline so that completion becomes a reportable event. That is what makes schedule-baseline-and-variance readable per phase rather than only in aggregate.

    #Two properties worth naming

    The outline is built before it is linked. docs/images/wbs-initial.png shows the lab-2 task list with every task still starting on day one — decomposition first, sequencing second. Only once the leaves exist do FS/SS/FF dependencies get drawn between them.

    The structure survives every later change. Task counts move (29 practice → 38 → 45) as milestones and re-decomposition arrive, but the 3/9/26 skeleton is the same object in lab 7–8's report as in lab 2's plan. A WBS that had to be rebuilt each lab would not be a baseline for anything.

    #Practised on a throwaway first

    Lab 1 exists only to learn the mechanics — indenting, durations, the first Finish-to-Start links — on a plan that is explicitly discarded:

    "This file is a throwaway sandbox, not the Export/Import project. It exists to practise the"

    Computer Project Management/lab1_WBS_Practice/README.md, 2026-07-10

    The same separation shows up as directory names in numbered-stages-in-directory-names: the sandbox and the real artefact live in different folders and are never merged.

    #What the repo does not do

    • No 100 % rule stated. The principle that a parent's children must sum to exactly the parent's scope is never named, though the rolled-up durations in the lab 7–8 report behave as if it holds.
    • No WBS dictionary. Tasks are named but not defined; there are no entry/exit criteria, no acceptance criteria, no owner per work package outside the resource assignment.
    • No decomposition rule. Nothing records why 26 leaves rather than 15 or 60, or what stopping criterion ended the breakdown. TODO: unrecorded, not asked at interview — confidence: low on the rationale, medium on the counts, which come from README tables over unread .mpp files.
