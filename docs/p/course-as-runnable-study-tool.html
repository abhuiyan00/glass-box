    Course as Runnable Study Tool

    Four separate courses were revised by building the syllabus into a program rather than by reading notes. Same architecture every time, in four unrelated repositories. This is the most distinctive habit in the source set that no single repo reveals.

    #Lineage, not parallel invention

    "One was first and I copied it forward."

    interview, 2026-07-28

    The origin is IT Applications in Business and Commerce. Worth one caveat for honesty: the earliest in-repo timestamp evidence points elsewhere — Physics/exam_prep/js/* carries mtimes of 2026-06-27→06-30, weeks before the others appear in any tree. The quiz app in IT Applications has no comparable in-repo timestamp because that project's development history lives in a different repository, so the mtime ordering cannot settle it either way. The interview is treated as authoritative here; the mtime observation is recorded rather than dropped.

    #The shared architecture

    Every instance, independently:

    • No build step, no dependencies, opens from file:// — see zero-dependency-no-build-step
    • Plain HTML + CSS + vanilla JS; data, logic and presentation in separate files
    • localStorage progress with a STORAGE_VERSION integer that invalidates saved state on schema change (IT Applications is at version 7 — six prior breaks implied)
    • Hash-based routing and deep links to a single chapter
    • Canvas demos rather than static figures: 13 physics simulators, 23 optimisation demos
    • A hand-rolled test harness using node:vm plus a DOM shim, loading the production JS and driving real event handlers — Physics/exam_prep/tools/qa.mjs, IT Applications.../lecture/exam_prep/qa_test.js
    • A generated question bank with its pristine source kept beside it — see generated-artifact-with-pristine-source

    #Why the shape recurs

    The constraint is the exam room, not the browser: revision has to work with no network, on any machine, at any hour. That produces the same design pressure as offline-first-static-deliverable, and the two patterns share their whole toolbox.

    #What the tools verify, and what they do not

    The harnesses are real — qa_test.js exits non-zero on failure, qa.mjs runs 34 static checks including "every file loaded by index.html is precached by the service worker". What none of them check is subject-matter correctness: Physics claims its Bohr simulator reproduces the Balmer lines, but qa.mjs validates ids, assets and KaTeX parsing, never numerical output. The pedagogical claims rest on prose. See provenance-and-limits-stated-inline.

    Physics did catch two answer-key errors in a provided exam set — recorded in its own generated audit, unconfirmed with the lecturer. TODO: whether the tool was used for the exam is recorded at medium confidence only; the interview did not state it outright.
