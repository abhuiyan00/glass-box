    Architect / Coder / Tester Loop

    Three roles, one task at a time: architect writes the spec, coder implements it, tester verifies it independently. The roles are not a naming convention — they are enforced by what each one is permitted to touch.

    #Separation by capability, not by instruction

    Each subagent definition in stickfps carries an explicit tool grant, and the grants are the mechanism:

    • architect — Read, Grep, Glob, Write, Edit, but barred from /src. It can write specs and cannot write code.
    • coder — the same plus Bash. It can build and run.
    • tester — no Write and no Edit at all, deliberately.

    "Never let the tester subagent edit files, and never let the architect subagent touch application source — that separation is what keeps this loop honest."

    browser_game_stickfps/.tooling/commands/game-loop.md, 2026-07-25

    The reasoning generalises past agents entirely. A verifier that can edit will, under pressure, make the failure go away rather than report it — the same reason a test author who can change the assertion tends to. Removing the capability removes the temptation, and it is enforceable, which an instruction is not.

    #The orchestration loop

    /game-loop runs: spec → implement → verify, with four rules worth extracting.

    1. Max 3 fix attempts per task, then stop. A three-strike rule converts "keep trying" into an explicit hand-back to a human, which is the point at which someone re-reads the spec instead of the code.
    2. Stop and ask on any "Open Questions" in the spec. Uncertainty halts the loop rather than getting resolved by guess — see spec-driven-development.
    3. On PASS: tick the TASKS.md box, log to PROGRESS.md, commit.
    4. Every third task, rewrite the state summary "in under 300 tokens" so the working state survives a context compaction. This is the interesting one: it treats context as a resource with a budget and schedules maintenance of it, rather than discovering it is gone.

    #Where it was not followed

    Step 3's commit instruction was not obeyed — stickfps has 9 commits for 11 rounds of work, made in one 7-hour import session, and PROGRESS.md twice records "No commit made (user hasn't asked)". The logging half of step 3 was followed rigorously, which is why progress-md-as-build-log exists at all and why the git history is not the working record. See import-finished-work-into-git.

    The four .tooling files also still name the retired transport and host — documentation-drift.

    #Confidence

    confidence: medium. The definitions and the loop are directly evidenced and the outputs (9 specs, 11 logged rounds) are consistent with them, but the pattern is observed in one repository, so it is not yet established as a recurring habit.
