    Length-Prefixed Message Framing

    TCP is a byte stream, not a message stream. It guarantees order and delivery and guarantees nothing about boundaries: one send can arrive as three reads, and three sends can arrive as one. Any application that exchanges messages over it must define where each message ends.

    The standard answer is to say so up front:

    4-byte unsigned big-endian length || UTF-8 payload

    Read exactly four bytes, decode the length, then read exactly that many. One connection carries many frames.

    #The bug this replaces

    sock.recv(4096) and hope. It works perfectly on loopback, where messages are small and arrive whole, and it fails in production under three conditions the developer never reproduced: a message larger than the buffer, two messages coalesced by Nagle's algorithm, and a message split across TCP segments by a smaller path MTU.

    The variants are no better. Reading until the buffer "looks like valid JSON" makes the parser the framer and breaks on any payload containing a nested structure. Delimiter framing — newline, \0 — requires escaping the delimiter in the payload, and the escaping is what gets forgotten.

    #Why the length must be bounded

    An attacker-supplied length prefix is an allocation instruction. 0xFFFFFFFF asks the server to allocate 4 GiB before a single byte of payload arrives, and a handful of connections doing that is a denial of service that costs the attacker twelve bytes.

    So the cap comes first — 64 KiB in the implementation this is written from — and it is checked before allocating, not after reading. An invalid size gets a framed error response where that is still possible, then the connection closes, because a stream whose framing is in doubt cannot be resynchronised: there is no way to tell payload bytes from a length prefix once you have lost your place.

    This is the same ordering discipline as verify-then-parse in hmac-session-tokens-over-jwt. Everything after the boundary is attacker-controlled until something trusted says otherwise.

    #What HTTP does instead

    HTTP solves the identical problem twice — Content-Length, or chunked transfer encoding — which is why an HTTP adapter needs no framing code of its own. That is not the framing disappearing; it is the framing living in a library. Disagreement between two implementations about which of those two mechanisms applies to a request is the entire basis of request-smuggling attacks, so "the library handles it" is a statement about where the complexity lives, not whether it exists.

    Building both transports against one contract is what makes the distinction visible: see distributed-systems-protocol-labs and dual-implementation-as-cross-check.

    #Read timeouts belong here too

    A peer that sends a length prefix and then nothing holds a server thread forever. Framing code needs an idle read timeout as much as it needs a size cap — both are limits on what a single unauthenticated connection can consume.
