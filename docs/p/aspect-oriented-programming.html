    Aspect Oriented Programming

    A cross-cutting concern — logging, timing, auditing, usage counting — is one that would otherwise be copy-pasted into every method that needs it. AOP moves it out of the methods and into an aspect: a declaration of where (a pointcut) and when (an advice type) the extra behaviour runs. The business code never mentions it.

    Realised in Information-Systems-Modelling lab 4 on top of spring-boot-starter-aop. Four aspects ship, and between them they exercise every advice type Spring AOP offers.

    #The four aspects and what each demonstrates

    Aspect Advice types Pointcut Purpose
    LoggingAspect@Before, @AfterReturning, @AfterThrowingexecution(public * …service.*Impl.*(..))service-layer entry/exit/exception log
    PerformanceAspect@Around@annotation(…Timed)warn above a 500 ms threshold
    SecurityAuditAspect@AfterReturning, @Afterone controller method, plus all admin callslogin-success/failure audit trail
    StatisticsAspect@AfterReturningall controller methods minus threeendpoint call counting

    Two design details are worth more than the list:

    Pointcuts are written to exclude, not just to include. StatisticsAspect targets every public method in the api package and then subtracts StatisticsController, AnalyticsController and SystemController with !within(...) — otherwise reading the statistics would increment them. LoggingAspect targets only *Impl classes, which keeps analytics and controllers out of scope. Both are the same instinct: an aspect that fires on itself is the classic AOP failure mode.

    @Timed is opt-in, not blanket. Rather than time everything, a custom annotation marks the two heavy JDBC aggregation methods (AnalyticsService.dashboard() and .ai()), and PerformanceAspect binds its @Around advice to the annotation. Blanket timing would drown the signal.

    #The rationale is recorded in the source

    Unusually for this corpus, the why is written down rather than inferred:

    "Why AOP here instead of code in the controller: Controllers implement generated OpenAPI interfaces; adding audit calls inside them couples business logic to observability."

    Information-Systems-Modelling/lab4/.../aspect/SecurityAuditAspect.java, 2026-05-28

    That reason is specific to this codebase and follows directly from contract-first-api-design: the controllers are implementations of generated interfaces, so anything hand-added to them is at risk every time the generator runs. AOP puts the observability somewhere the generator cannot reach.

    #Where it sits in the stack

    The aspects wrap the api → service → repository → entity split described in layered-architecture, which is what makes the pointcut expressions short: the package names are the layers. Lab 4 is the only lab that uses AOP — labs 2 and 3 are its ancestors under forward-copy-lab-progression and carry no spring-boot-starter-aop dependency.

    #What is not verified

    Zero tests cover any of the four aspects. Lab 4's entire Java test suite is one contextLoads() and one BuildsControllerIntegrationTest with a single @Test. A pointcut that silently stops matching — a renamed package, a controller that no longer ends in Impl — would fail open and nothing would catch it.
