    Numbered Docs Chapters

    Prose documentation is organised as a numbered book: 01-architecture.md, 02-roadmap.md, 03-android-permissions-and-legal.md, 04-accessibility-service.md, an index README mapping each chapter to what it covers, and a newest-first dated CHANGELOG.md alongside them.

    farely is the only repository in the source set that applies numbering to documents. Elsewhere the same instinct lands on directories of code — see numbered-stages-in-directory-names, which treats this as its prose variant.

    #The division of labour

    The four chapters divide by question asked, not by component: how it works, what is left to do, what it is allowed to do, how the capture layer behaves. The CHANGELOG then carries everything time-shaped, which keeps the chapters in the present tense. That separation is why the architecture chapter still reads cleanly a month later while the roadmap moved constantly — see phase-status-board.

    The number is a reading order, not a dependency order. Chapter 01 is where a cold reader starts, which makes this the same premise as readme-as-guided-tour applied one level down.

    #Evidence

    The chapters carry real argument, not summary. Chapter 01 states the reading strategy the whole product depends on:

    "Node tree before OCR. OCR is the expensive, fragile path. Many Android apps expose offer text as real TextView nodes, readable in microseconds with no image processing. OCR is a fallback, not the default."

    Farley/docs/ocr-overlay/01-architecture.md, 2026-07-02

    And the index README, which should be the most stable file of the set, is the one that rotted:

    "Phase 0 — Documentation. No native code merged yet"

    Farley/docs/ocr-overlay/README.md, 2026-07-02

    That line still stands roughly thirteen phases behind 02-roadmap.md.

    #The failure mode the pattern invites

    Numbering fixes the order of documents; it does nothing for their currency, and it adds a place where staleness hides. A reader who trusts the index — the correct behaviour, since the index is what the numbering advertises — is the reader most likely to be misled. This is the local shape of documentation-drift, and Farely's version is severe: the chapters describe ML Kit OCR as shipped when it is a stub, and the numbering makes those documents look authoritative.

    The mitigation the repo actually has is the CHANGELOG, which is append-only and therefore cannot lie about the past even when the chapters lie about the present. Where the chapters and the changelog disagree, the dated entries win. That is also how import-finished-work-into-git is recoverable here at all: ten days of pre-git work exist only as changelog entries.
