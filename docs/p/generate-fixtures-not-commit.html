    Generate Fixtures Rather Than Commit Them

    Decision. Ship a four-line generator for the 1 MB / 5 MB / 10 MB inputs used to time RSA, and .gitignore the outputs — rather than committing 16 MB of filler.

    Date. 2026-07-25 (the publishing commit), labs/04_asymmetric_ciphers/ of cybersecurity-engineering-laboratories.

    #Why

    The argument is written in the script's own docstring and turns on a property of the measurement rather than on repository hygiene generally:

    "each file is a single character repeated to the required length ... they are generated rather than committed: 16 MB of a repeated character is the largest thing that could go in this repository and the least informative."

    Cybersecurity-Engineering-Laboratories/labs/04_asymmetric_ciphers/generate_test_files.py, 2026-07-25

    Largest and least informative is the whole case. Lab 04 measures how RSA encryption cost scales with input size, so the content of the input is irrelevant by construction — see symmetric-vs-asymmetric-cryptography. A fixture whose content does not matter is a fixture that should be described rather than stored, and four lines of Python describe it exactly.

    The README states the rule in the same section as the two key-material rules, which is where it belongs — all three are about what does not go in a repository:

    "Fixtures are generated, not stored. Lab 4 times RSA against 1 MB, 5 MB and 10 MB inputs whose content is irrelevant to the measurement."

    Cybersecurity-Engineering-Laboratories/README.md, 2026-07-25

    #Alternatives rejected

    Option Why not
    Commit the three files16 MB of a repeated character; every clone pays for it forever, and git stores it in history even if later deleted
    Git LFSinfrastructure and a dependency for data that can be recreated in a second — and this repo has no .gitattributes at all
    Commit smaller files and scale the resultschanges the measurement; the whole experiment is about size
    Document the sizes in prose and generate by handthe reader would have to reconstruct the fixtures from a description, which is what the script already is — only unreliable

    #What the script gets right beyond the decision

    It is 50 lines of stdlib-only Python and worth reading as a small example of the repo's habits:

    • Writes in 1 MB chunks, so producing the 10 MB file does not need 10 MB of memory — the docstring says so at the function that does it.
    • pathlib throughout, with the destination as an optional argument defaulting to the script's own directory.
    • Returns an exit code from main and prints the byte count of each file written, so a run is self-verifying.
    • .gitignore carries *mb.txt with a comment naming the script that produces them — the ignore rule and the generator point at each other, so neither can be found without the other.

    That last detail is what makes this durable rather than merely tidy. An ignore rule with no stated producer becomes a mystery within a year; here the tree explains itself. Compare provenance-and-limits-stated-inline.

    #The general form

    If an artefact is deterministic and cheap to reproduce, commit the producer, not the product. The same reasoning appears elsewhere in this source set from the opposite direction — see generated-audit-artifact, where the output is committed precisely because it is the evidence rather than an input. The test is what the artefact is for: an input that only needs to exist should be generated; an output that needs to be reviewable should be committed.

    The sibling decision in the same README section is omit-rsa-private-key-screenshot — the other half of "what does not belong in this repository".
