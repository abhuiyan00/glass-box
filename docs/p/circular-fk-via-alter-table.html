    Resolve the Circular Foreign Key via ALTER TABLE

    Decision. Break the CATS ↔ BANDS cycle by creating one table without its foreign key, adding the constraint by ALTER TABLE once both tables exist, and seeding with a deliberate null-then- UPDATE pass — rather than declaring both constraints DEFERRABLE INITIALLY DEFERRED.

    Date. 2026-07-25 (evidence date), sql/01_schema/ of oracle-database-laboratories.

    #Why

    The rejected alternative is named explicitly, in two places, with the trade stated rather than implied:

    "The alternative — deferrable constraints checked at COMMIT — buys free insert ordering at the cost of per-statement error reporting."

    Oracle-Database-Laboratories/README.md, 2026-07-25

    Deferring the check moves the failure from the statement that caused it to the COMMIT that ends the transaction. In a teaching script whose whole purpose is to show which constraint stops which statement, that is the wrong direction: the diagnostic is the deliverable.

    #The procedure, and why the order is not negotiable

    "Both scripts work around it in the same way, and the order is not negotiable: 1. CATS is created without its band key. 2. BANDS is created in full. 3. ALTER TABLE CATS ADD CONSTRAINT cats_band_no_fk ... closes the loop. 4. Seeding inserts BANDS rows with band_chief NULL, then all of CATS, then UPDATEs the chiefs into place."

    Oracle-Database-Laboratories/docs/schema.md, 2026-07-25

    Two separate problems are being solved by that sequence. Steps 1–3 solve schema creation: neither table can be created with both keys in place. Step 4 solves data loading: the first insert into either table would otherwise reference a row that does not exist yet. A solution to one is not a solution to the other, which is what makes the cycle expensive — see circular-foreign-key.

    #Alternatives rejected

    Option Why not
    Deferrable constraints checked at COMMITfree insert ordering, but per-statement error reporting is lost — stated in the repo
    Leave BANDS.band_chief unconstrainedturns a load-order problem into an integrity problem; the UNIQUE "one band per chief" rule would also go
    Drop CATS.band_no and derive membership from the band's chiefloses many-to-one membership entirely; the two relationships are genuinely different facts

    TODO: only the first rejection is evidenced in the repository. The other two are stated here as what the alternatives are, not as choices the author recorded weighing. Do not attribute them.

    #What it costs

    The UPDATE step is mandatory and silent if skipped: bands keep null chiefs, every query still runs, and the model is quietly half-built. There is no constraint that can catch it, because "eventually non-null" is not expressible. 03_seed_data.sql carries the sequence in its header comment as the only guard — documentation as the enforcement mechanism, which is exactly the exposure documentation-drift describes. In this repo the docs and the code do agree; that is a property of this repo, not of the technique.
