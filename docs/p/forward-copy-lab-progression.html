    Forward-Copy Lab Progression

    Each lab is a whole copy of the previous lab plus one new capability, committed as a new directory. Nothing is refactored into a shared module, nothing is deleted, and every intermediate version stays runnable side by side. The repository is not a project with a history — it is a project with all its history checked out at once.

    Confirmed in Information-Systems-Modelling, which states the intent in its own words:

    "Read top to bottom and it reads like a build diary: each lab picks up exactly where the last one left off."

    Information-Systems-Modelling/README.md, 2026-07-25

    #The chain

    Lab Directory = previous lab, plus
    2lab2/StudentService/(baseline) OpenAPI contract, generated interfaces, SQLite
    3lab3/StudentService_vlab3/h2-database in file mode, an auth contract
    4lab4/StudentService/AOP, validation, actuator, jjwt + BCrypt, uploads, profiles, an angular SPA

    Same package pl.edu.pwr.tkubik.ism, same artifactId, same api → service → repository → entity split every time — see layered-architecture. The Java source count tells the story on its own: 11 → 41 → 76 files, strictly additive.

    Lab 3's README announces its one delta in its first sentence:

    "The skeleton becomes a real backend."

    Information-Systems-Modelling/lab3/README.md, 2026-07-09

    #What this buys

    A grader — or a reader — can open lab 2 and lab 4 next to each other and see exactly what authentication or AOP cost, because nothing else moved. Extracting a shared parent module would destroy that: the diff would become a config change instead of a visible delta. For coursework whose deliverable is the demonstration of a technique, keeping the ancestors is the correct call, and it is the same reasoning as multiple-solutions-side-by-side.

    The numbering carries the order in the directory names rather than in a table of contents — see numbered-stages-in-directory-names.

    #What it costs, measured

    Copy-forward makes every earlier lab a fossil that nobody maintains, and this repo shows all three consequences:

    1. Divergence goes unnoticed. Lab 3's OpenAPI contract and README both promise stateless JWT auth; the lab 3 code has no jjwt, no BCrypt and no password check. The capability only becomes real in the lab 4 copy. See stateless-jwt-authentication.
    2. Duplicates accumulate. A 39-file pre-rewrite Angular scaffold sits nested inside the real lab 4 SPA; ontology.ttl exists as byte-identical copies in labs 5 and 6; instances.ttl (557 lines) and cardinalityTest.owl are tracked and referenced by nothing. This repository is the corpus's four-way instance of keep-the-superseded-version-in-tree.
    3. Fixes do not propagate backwards. Nothing that was learned in lab 4 was ever applied to labs 2 and 3, because they are finished artefacts, not living code. Per the interview the whole repo is "All finished and frozen" (2026-07-28), so that is a description rather than a complaint.

    #Scope

    Evidenced in one repository. The corpus-wide relative is the family of repos that keep alternatives visible rather than replacing them — multiple-solutions-side-by-side and numbered-stages-in-directory-names — but the specific move of copying a whole working application forward and adding to it is, so far, particular to this coursework.
