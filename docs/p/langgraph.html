    In short

    A Python library for building stateful, multi-step graphs of function calls

    LangGraph

    A Python library for building stateful, multi-step graphs of function calls. Nodes are plain functions over a typed state dict; edges — including conditional ones — decide what runs next. It is the whole of the backend's control flow in agent-orchestrator, and the project's only runtime dependency (langgraph>=0.3).

    #What it is actually used for here

    START → recon → planner → (direct | schedule ⇄ worker) → synth → END

    Two features carry the design, and neither is incidental:

    • Send fan-out. schedule returns a list of Send("worker", …), one per subtask released in the current wave. That is how a plan becomes parallel work without the graph knowing in advance how many workers there will be — see dag-scheduling-in-waves.
    • Additive reducers. State fields are Annotated[List, operator.add], so concurrent workers append rather than overwrite. Without this, two agents finishing at once lose one result, and the loss is silent.

    schedule → worker → schedule is a loop, so each wave costs two supersteps. LangGraph's default recursion_limit of 25 aborted deep plans partway through; the project sets 150.

    #Why it earns its place

    The graph is a subprocess precisely because LangGraph is Python and the VS Code API is TypeScript (drive-the-clis-not-the-apis is the other half of that story). The payoff is that the whole orchestration is runnable and testable with no editor at all — python graph.py "task" — and every pure function in it is unit-testable without touching the graph, which is what the 145 pytest units do.

    #Cost

    One import at module scope means CI must install it even though no test builds a graph. Recorded as such in the workflow rather than worked around.
