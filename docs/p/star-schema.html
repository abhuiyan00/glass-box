    Star Schema

    One fact table of measurements surrounded by denormalised dimension tables that describe them. The fact holds numbers and foreign keys; each dimension holds the text you group and filter by, flattened so a query needs one join per dimension and never a chain of them. It is the deliberate opposite of third-normal-form: redundancy is accepted because the workload is read-heavy analytical scans, not transactional updates.

    #Two independent instances

    data-warehousing-and-business-intelligence builds the model twice, which is what makes it worth a page rather than a paragraph.

    Mart A — retail sales. FACT_SALES at order-line grain, with DIM_TIME, DIM_PRODUCT, DIM_CUSTOMER and DIM_SALESPERSON. Five foreign keys are declared on the fact and three non-clustered indexes cover the columns queries actually filter on. DIM_PRODUCT collapses a snowflake: the source Product → ProductSubcategory → ProductCategory chain becomes one wide dimension with a derived IsPurchased flag.

    Mart B — daily price quotes. FACT_QUOTES at ticker-day grain over DIM_DATE and DIM_TICKER, with derived columns (DailyRange as a PERSISTED computed column, DailyReturnPct, RSI14) and a view on top that derives the overbought/oversold flags at read time rather than storing them.

    #The parts that are easy to get wrong

    • Grain is declared by the primary key, not by convention. See fact-grain.
    • Role-playing dimensions. DIM_TIME is joined twice from the same fact, as OrderDateKey and ShipDateKey. One physical dimension, two semantic roles — no second calendar table.
    • Degenerate keys. FACT_SALES uses the source order-line identifier as its own primary key rather than inventing a surrogate; DIM_TICKER does the opposite. That contrast is surrogate-vs-natural-keys.
    • What belongs in the fact and what belongs in a dimension is the argument that produced measure-vs-dimension and rsi-as-measure-not-dimension.
    • Nullable foreign keys are legitimate when the business genuinely has none — see nullable-salesperson-key.
    • The dimensions must exist before the fact can reference them, which fixes the load sequence: etl-load-order.

    #Cost, stated in the source

    The repo does not present the star as free. Comments name the price of each choice — a denormalised product dimension repeats category text on every row, and deriving an indicator at query time "takes two joins" rather than a single column read. That habit is provenance-and-limits-stated-inline.

    #Gap

    • TODO: the README calls the AdventureWorks mart "a Kimball-style star schema — conformed dimensions", but nothing in the repo defines conformed, and no dimension is shared across two fact tables. Mart A and Mart B live in different databases with different calendar tables, so they do not conform to each other either. confidence: low on the conformance claim specifically; the rest of this page is read directly from the DDL. Do not repeat "conformed dimensions" as verified.
