    PROGRESS.md as Build Log

    An append-only narrative log of the build, kept in the repo, written per round of work. In stickfps it is 40.5 KB across eleven rounds and it is the real working record — the git history is a nine-commit import that says nothing about how the thing was made (import-finished-work-into-git).

    Its structure has three parts worth copying: an append-only round-by-round narrative, a rewritten state summary at the top (the only mutable section, kept short deliberately — see architect-coder-tester-loop), and strikethrough on items as they are resolved, so a fixed problem stays visible as history instead of vanishing.

    #Dead ends are the payload

    This is the one artefact in the entire source set that records what did not work. Nothing else does — code shows the final state, specs show the intent, git shows a squashed import. From stickfps:

    • No reload-request message existed on the wire at all. Client-side reload was purely cosmetic, so every weapon was permanently empty server-side after its first magazine and every later shot was silently rejected while the HUD showed full ammo. Two systems each individually correct.
    • WeaponRig never rendered a mesh for two rounds — a return null hiding a real three-js gotcha about camera-parented meshes.
    • Nothing tracked round wins, so the match winner was undeterminable; elimination also advanced the round on the very next tick, making the death moment last ~16 ms.
    • Five authority loopholes in one round — dead players firing, firing accepted in lobby and buy phase, no server-side equipped-weapon tracking, joinRoom leaving immortal zombie players holding 60 Hz loops alive, and movement with no bounds at all. See server-authoritative-netcode.
    • A real vulnerability: the client-reported shot origin passed straight into the server raycast.
    • The ±π yaw seam spinning remote players 360° (entity-interpolation); lighting broke twice; a whole transport replaced (websocket-tcp-over-geckos-udp); the grayscale art identity retired after being a mandatory constraint in three documents.

    A code reviewer can find none of these from the tree. That is the argument for the file.

    #Honesty markers

    The log states its own limits where they occur (provenance-and-limits-stated-inline), including that one round was reconstructed after the fact:

    "Full input-replay reconciliation (re-simulating unacknowledged inputs after a server correction) is not implemented — v1 uses a simpler blend-toward-snapshot approach... Fine at low latency, will feel soft under real internet jitter."

    browser_game_stickfps/PROGRESS.md, 2026-07-25

    "No commit made (user hasn't asked)."

    browser_game_stickfps/PROGRESS.md, 2026-07-25

    The second line, recorded twice, is why the git history and the work history diverge — and it is itself logged rather than left to be inferred.

    #Cost

    The log is the only source for several load-bearing claims — the 108/52 test counts among them — with no CI and no coverage artefact to corroborate, so those inherit confidence: medium. A self-reported log is evidence of intent and sequence, not of a passing suite.
