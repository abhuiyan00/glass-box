    Vite

    Build tool and dev server for the stickfps client — vite ^8.1.1 with @vitejs/plugin-react ^6.0.3, producing the static bundle that is deployed separately from the game server under split-frontend-backend-hosting.

    #The property that shapes the deployment

    VITE_* variables are inlined at build time, not read at runtime. VITE_SERVER_URL, VITE_SERVER_PORT, VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY are baked into the bundle by vite build. Changing the backend address is therefore a rebuild and redeploy, not a configuration change — which is why the deployment runbook is ordered backend-first: the server URL must exist before the frontend can be built against it.

    The corollary is a security one worth stating: anything with a VITE_ prefix is public by construction. It is visible in the shipped JavaScript. Only publishable values belong there — the anon key in supabase is designed for that, a service key never would be.

    #Vitest

    vitest ^4.1.10 on both sides of the repo, sharing Vite's transform pipeline, plus jsdom ^29.1.1 and @testing-library/react ^16.3.2 on the client. 52 client tests, all over pure functions; playwright covers anything needing a real GL context.

    The server keeps a vitest.config.ts that exists for a single line: fileParallelism: false, working around a vitest 4 worker-loading failure on Windows under CommonJS. Worth recording as the kind of config file that looks arbitrary a year later — the reason is in PROGRESS.md, not beside the setting, and that gap is exactly where documentation-drift starts.

    #Toolchain shape

    tsc and oxlint ^1.71.0 both run clean, and vite build is clean. Two build pipelines and twelve runtime dependencies across client and server put stickfps firmly on the other side of zero-dependency-no-build-step from the coursework repositories — the same instinct reappears one layer down as an absolute rule about assets rather than about tooling, in no-external-assets.
