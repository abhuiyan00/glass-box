    SQL Server Analysis Services

    Microsoft's OLAP layer. A multidimensional SSAS project sits on top of a relational mart and declares, as XML source files: a data source (.ds), a data source view binding specific tables (.dsv), one .dim per dimension, one .cube per cube with its measure groups, and a .partitions file. data-warehousing-and-business-intelligence holds three such projects.

    Project Cube(s) Over
    olap/ssas/Adventure Works2019.cubethe five mart tables — four .dim files
    project/twtr/ssas/Twitter.cubeFactTwitterData + DimDate
    project/twtr/ssas/Twitter_rsi.cubeFactRSI + DimRSI + DimDate

    The AdventureWorks cube's measure group exposes quantity, unit price, discount, line total and a row count, with the time dimension role-played twice as order date and ship date — the OLAP expression of the same modelling choice made in the DDL. See star-schema and measure-vs-dimension.

    #The SSAS side ships the design the SQL side rejects

    This is the sharpest finding in the repository. docs/star-schema.md argues at length that a technical indicator belongs on the fact table as a measure, with thresholds pushed into a view — rsi-as-measure-not-dimension. And project/twtr/ssas/Dim RSI.dim implements the indicator as a dimension, with RSIKey, IsOverbought and IsOversold attributes, feeding a second cube whose only measure is a row count.

    Both artefacts are committed. The winner ships in SQL; the loser ships in SSAS. See keep-the-superseded-version-in-tree.

    #Three further drifts

    • Twitter.dsv binds FactTwitterData and DimDate; Twitter_rsi.dsv binds FactRSI and DimRSI. None of those four tables is created by any committed DDL, which builds dw.FACT_QUOTES, dw.DIM_DATE and dw.DIM_TICKER. The cubes and the schema do not describe the same database.
    • olap/ssas/DIM TIME.dim exposes only DateKey, Day, Month and Year, while the DDL defines Quarter, MonthName and IsWeekend as well. The cube sees a narrower dimension than the mart offers.
    • All of it is documentation-drift of the kind that only surfaces when someone tries to process the cube.

    #Never deployed

    "They are Visual Studio project files rather than deployed databases; opening them needs SQL Server Data Tools."

    Data-Warehousing-and-Business-Intelligence/docs/star-schema.md, 2026-07-25

    Stated by the repo itself, which is the honest move — provenance-and-limits-stated-inline. The .dim, .cube and .partitions files are committed as plain blobs with no .gitattributes and no Git LFS.
