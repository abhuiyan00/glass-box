    Critical Path Method

    The longest chain of dependent tasks through a network, and therefore the shortest possible project duration. Tasks on it have zero float: slip one and the finish date moves by exactly that amount. Tasks off it have slack and can absorb delay silently.

    In computer-project-management the critical path is not computed by hand — it is read off Microsoft Project's own critical flag and rendered in the tracking Gantt, ten tasks long:

    "Ten tasks lie on the critical path — any slip on these moves the finish date directly."

    Computer Project Management/README.md, 2026-07-10

    From the June reporting date onward it runs integration testing → user-acceptance testing → deployment → documentation → closure.

    #Why it is the concept the repo actually demonstrates

    The plan's headline number is an 11-day slip, and the critical path is the mechanism that produces it. Unit testing was extended by 16 days; the finish moved by 11. The two numbers differ because part of the extension was absorbed by float elsewhere and part propagated — which is the whole content of the method. See schedule-baseline-and-variance for the arithmetic.

    The path is also created, not merely observed. Re-linking integration testing to start after unit testing rather than in parallel puts both tasks on one chain, and that chain became the critical one — sequence-integration-after-unit-testing. A scheduling decision taken to fix a resource conflict changed the network topology, and the finish date followed.

    #Relation to the other two levers

    Lever Moves the finish date by Instance here
    Decompositionchanging what the chain is made ofwork-breakdown-structure — 38 → 45 tasks
    Resourcingforcing overlapping tasks apartresource-leveling — 110 d → 121 d
    Sequencingchanging dependency type or ordersequence-integration-after-unit-testing — 123 d → 134 d

    Only the third one is a free choice; the first two are consequences.

    #What is missing

    • No float or slack figures anywhere. The critical path is reported as a task list; the near-critical tasks — the ones that would become critical next — are never identified.
    • No PERT or three-point estimation. Durations are single-point. There is no probabilistic finish date and no schedule risk analysis in any readable file.
    • No crashing or fast-tracking analysis. Once the slip appeared it was accepted and reported; no compression alternative is costed. TODO: unrecorded, not asked at interview.
    • confidence: medium — the ten-task claim exists only as prose in the READMEs and a red-bar screenshot. No exported task list confirms it, and the .mpp files are unread by policy.
