    Authorisation in the Query Predicate

    Authorisation is a domain decision: the system determines whether an authenticated actor may operate on a loaded resource, then performs the requested operation. A persistence query can select the resource to write, but a zero-match query result must not be the only expression of that decision.

    #The explicit contract

    The project-management API follows load, decide, write. Its policy functions receive already-loaded entities and return a boolean or throw a policy-specific error:

    ~~~ts const project = await store.projects.findById(projectId); if (project === null) throw new NotFoundError("Project"); assertUpdateProject(actor, project); return store.projects.update(projectId, patch); ~~~

    The authz module keeps these rules pure: project owners and administrators may update a project; task permissions additionally account for assignment. The use case remains responsible for loading the entity and applying the resulting decision before it writes.

    This separation makes three outcomes explicit:

    • a resource is absent;
    • a resource exists but is not visible to this caller;
    • a visible resource is not permitted for a particular operation.

    Each outcome has a deliberate HTTP response rather than inheriting whatever a storage adapter happens to report.

    #Why queries are not policy

    A predicate such as ownerId = actor.userId is still useful when listing a caller's own resources. It is not enough on its own for an operation that must tell the caller whether the operation was refused. A policy assertion can be exercised without a database or HTTP response, and a use case can preserve the same rule when its storage implementation changes.

    Keeping the decision alongside the use case also makes new entry points less surprising. The same operation may be called by an HTTP route, a command, or a scheduled job; each obtains an actor and asks the same policy function.

    #Visibility is part of the policy

    The API returns 404 when an unrelated caller must not learn that a resource exists. That prevents identifier-taking endpoints from becoming discovery oracles. Administrators receive 403 for a denial because they are entitled to know the resource exists. An assignee who can read a task also receives 403 when attempting its deletion: claiming that a readable task is absent would contradict the API's own view of the resource.

    The distinction belongs in the visibility assertion helpers, not in ad hoc route branches, so a caller sees a consistent contract across project and task operations.

    #Test the actor boundary

    The access-control suite constructs separate actors and checks both the refused response and the unchanged resource. Those tests cover ownership, assignment, administration, and resource visibility. They test the policy boundary rather than merely proving that an owner can complete a normal workflow.
