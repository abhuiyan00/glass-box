    OWASP ZAP

    The Zed Attack Proxy — an open-source web application security scanner maintained by OWASP volunteers, usable both as an automated scanner and as a manual testing proxy. It carries labs 13 and 14 of cybersecurity-engineering-laboratories, alongside Burp Suite and Postman, against the deliberately vulnerable OWASP Juice Shop.

    #The proxy is the whole idea

    Configure the browser to route through ZAP and every request is captured after it leaves the browser. The tester can then read it, modify it, and forward it.

    The lab reports name the structural point directly: this is a man-in-the-middle-attack where the tester holds both roles. And the consequence is the single most important finding in lab 13:

    Every validation performed only in client-side JavaScript is advisory. Length limits, format checks, hidden fields, disabled controls, price values in a form — all of it is editable in the proxy after the client-side code has run and before the server sees it. Client-side validation is a UX feature; it is not a security control. Everything that matters must be re-checked server-side.

    #What the labs used it for

    Capability Exercised on
    Intercepting proxymodifying requests to bypass client-side validation
    Spider / passive scanmapping the application surface
    Active scanautomated probing for known vulnerability classes
    Request replay / manual editbroken authentication and broken access control, including object-identifier enumeration
    Fuzzersubstituting payload lists into a parameter position

    The vulnerability classes themselves are covered on web-application-injection — injection, broken authentication, broken access control, improper input validation, security misconfiguration — without any payload strings.

    #Where the labs stopped short

    The fuzzing exercises did not complete. The lab-13 report records the fuzzer not running and the author following the task sheet, then outside instructions, without success; the lab-14 report records a local instance that would not start and a task the author records not understanding.

    TODO: whether these were completed later is unrecorded. confidence: low on the completeness of the tooling exercises; confidence: high on the proxy-interception findings, which the reports document working.

    #Automated scanning is a floor, not a ceiling

    Worth stating because the tool invites the opposite belief. An active scan finds known patterns: reflected inputs, missing headers, default files, obvious injection points. It does not find business logic flaws, and broken access control — the class the lab exercised most successfully — is almost entirely invisible to it, because the request is well-formed and the response is a valid 200. Only someone who knows which identifier belongs to whom can tell that the answer was wrong. The manual proxy work, not the scanner, is where the lab's real findings came from.
