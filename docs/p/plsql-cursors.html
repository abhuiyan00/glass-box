    PL/SQL Cursors

    A cursor is a named handle over a result set that procedural code walks a row at a time. The whole subject reduces to three questions: who closes it, can it write back to the row it is sitting on, and is row-at-a-time the right shape at all.

    #Implicit versus explicit — a real choice, not a style preference

    02_cursors.sql in oracle-database-laboratories opens with the rule:

    "Cursor FOR loops open, fetch and close automatically and cannot leak. Explicit OPEN / FETCH / CLOSE is only worth the extra code when the loop needs to stop early -- and then the CLOSE has to be written on every path out, including the exception path."

    Oracle-Database-Laboratories/sql/03_plsql/02_cursors.sql, 2026-07-25

    And the file then demonstrates the cost it just described. The "five hungriest cats" block exits after five fetches, so it must use an explicit cursor — and it carries a WHEN OTHERS handler that tests %ISOPEN, closes, and re-raises. An unclosed cursor holds its slot for the whole session; the leak is silent until the session hits OPEN_CURSORS.

    This is the same shape as any resource with a lifetime: the convenient form is convenient precisely because it removes a path you would otherwise have to handle by hand.

    #FOR UPDATE and WHERE CURRENT OF

    Declaring a cursor FOR UPDATE OF col locks the selected rows for the transaction and lets the loop body write back with WHERE CURRENT OF cursor_name — updating exactly the row the cursor is on, without re-stating the predicate and without re-finding the row by key.

    The lab uses it for an iterative pass: raise every ration by 10 %, capped at the function's ceiling, repeatedly, until the herd total clears a threshold. The termination condition is the interesting part — it exits when a pass changes nothing, not when the target is met, because once every cat sits at its ceiling the target may simply be unreachable and a WHILE total <= … loop would spin forever. Loop-termination-on-no-progress is a general fixpoint idiom, not a database one.

    #Cursor attributes

    %FOUND, %NOTFOUND, %ROWCOUNT, %ISOPEN on the cursor; %ROWTYPE to declare a record matching its projection and %TYPE to declare a variable matching one column. The last two matter beyond convenience: they make the block survive a column widening in the table without an edit.

    #When row-at-a-time is the wrong shape

    The cross-tabulation exercise (bands down the side, functions across the top, gender splitting each band) is built by aggregating once into an associative array — TABLE OF NUMBER INDEX BY VARCHAR2(60) — and then formatting from memory. Driving the report straight from SQL would issue one query per cell.

    One trap comes with it: reading an associative array at a key that was never assigned raises NO_DATA_FOUND rather than returning NULL, so every read in the block goes through an EXISTS helper instead of through NVL — see plsql-exception-handling for why that is a raise and not a return value.

    The rule the file is teaching: a cursor loop that issues a query per iteration is a join written badly. Aggregate once, then iterate over the result.
