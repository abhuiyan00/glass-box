    Playwright

    Browser automation, @playwright/test ^1.61.1. Used in stickfps for two distinct jobs: end-to-end testing across two real browser contexts, and generating the screenshots in the README.

    Also present as a claim in farely's README, where no test runner exists at all — see documentation-drift.

    #What is checked in, and what is not

    Checked in: two specs, covering the lobby only — create room, join room, roster, host start, bad code. That is the multiplayer setup path, verified with two browser contexts talking to one server.

    Not checked in: the combat loops. Full two-browser playtests covering payouts, kill feed and round advance were run twice from scratchpad scripts in rounds 8–9 and never committed. There is no committed spec for combat, movement or the round timer.

    This gap is stated in the repo rather than hidden (provenance-and-limits-stated-inline), and it is the honest reading of the test story: the 108 server + 52 client unit tests carry the authority surface, while the browser-level evidence for the game actually playing end to end is a transcript, not an artefact. confidence: medium on all test counts — they rest on PROGRESS.md's own reporting, with no CI and no coverage output. TODO: whether the suite still passes at head, and whether the round 8–9 scratchpad scripts survive anywhere, is unknown.

    #Three harness quirks, named as harness quirks

    The repo separates environment artefacts from product bugs by name, which is the practice worth copying:

    • Chromium injects a stray look delta on pointer-lock grant under CDP — the camera moves once, by itself, in automation only.
    • page.mouse.click implicitly moves the pointer, which rotates a pointer-locked camera. Aiming in a test is not the same action as aiming by hand.
    • Headless software GL runs the simulation at ~40% of wall time, because the client's step accumulator is capped — see fixed-timestep-simulation. Any assertion comparing in-game seconds to real seconds is wrong for reasons unrelated to the code under test.

    #As a screenshot harness

    The README's images are genuine captures of a live bot match at 1600×900, and assets/README.md documents the capture settings — downscale to 1440 px, progressive JPEG q90, chosen over PNG to avoid banding. Using the E2E driver to produce documentation images means the screenshots show the real running product and can be regenerated, which is what makes readme-as-guided-tour hold up here.
