    Reasoning Effort as a Portable Label

    Every vendor exposes "think harder" differently: a token on a ladder, a numeric budget, a flag that does not exist. A planner that emitted vendor parameters would have to know which executor it was addressing before it could finish a sentence. So the planner emits a label —

    light · medium · high · extra-high · ultra

    — and one translation layer per product turns the label into whatever that product accepts. The label is the interface; the parameter is an implementation detail of the executor.

    #Translation is not a lookup

    Three things happen on the way down, and each exists because the naive version failed:

    • Clamping. codex-cli publishes a per-model ceiling, and asking above it is rejected by the CLI. The requested level is clamped down the ladder rather than sent and hoped for — a run must not die on an adjective.
    • Omission. Some models take no reasoning parameter at all; for those, none is sent. Likewise openrouter: if the configured router advertises no reasoning support in /models, the field is left off rather than passed and ignored.
    • Reporting what ran. Because the label can be clamped, the label alone would misreport the work. The effective per-product value is what gets recorded, not the request.

    That last point is the one worth keeping. An abstraction that translates downward owes its user the result of the translation; otherwise the log says ultra and the model ran at high, and the person reading the log draws a wrong conclusion about the model rather than about the clamp.

    #Why not just expose vendor parameters

    Because the executor for a subtask is not final when the effort is chosen — it can move under read-capability-routing or after a fallback, and a vendor parameter chosen for one executor is meaningless on another. A portable label survives rerouting; xhigh does not.
