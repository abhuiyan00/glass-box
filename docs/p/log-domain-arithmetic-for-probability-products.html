    Log-Domain Arithmetic for Probability Products

    Multiplying many probabilities underflows to zero, and when it does, every candidate ties at zero and the answer becomes whichever one was checked first. Working in logs turns the product into a sum and the floor disappears.

    That is usually presented as an optimisation. It is not — it is the difference between a classifier that works and one that silently returns a constant.

    #The measured cliff

    Bernoulli naive Bayes contributes one factor per word. Measured on a four-document corpus at four vocabulary sizes:

    vocabulary log-posterior as a product
    400−115.85.29 × 10⁻⁵¹
    900−259.61.80 × 10⁻¹¹³
    1,600−461.06.27 × 10⁻²⁰¹
    2,600−748.70.0 — dead

    The threshold is about −745, where the smallest subnormal double runs out. A 2,600-word vocabulary is small for text classification, which makes this a routine operating condition rather than an edge case.

    The log form is finite at every row and keeps counting past the last one.

    #Three reformulations that cost nothing

    The same discipline appears three times in one repository, and in each case the stable form is no more expensive than the naive one:

    The sigmoid. 1/(1+exp(-a)) raises OverflowError at about a = -746. Splitting on the sign moves the large exponent into the numerator, where it underflows harmlessly to zero:

    if a >= 0:  return 1 / (1 + exp(-a))
exp_a = exp(a)
return exp_a / (1 + exp_a)

    An unscaled feature reaches that magnitude within a few hundred gradient steps, so this is a crash waiting on iteration count, not on unusual input.

    The log-likelihood. The textbook form y·log σ + (1−y)·log(1−σ) evaluates log(0) exactly when the model is confident and right — the best case triggers the failure. Folding the sign in and using -log1p(exp(-|a|)) + min(a, 0) never does.

    log1p itself exists because log(1 + x) loses all significance for small x, where the 1 swamps the x before the logarithm sees it.

    #The general shape

    Each of these is the same move: the mathematically obvious expression and the numerically usable expression are different expressions of the same function. Choosing between them is not premature optimisation, because they do not compute the same thing in floating point.

    Related, from the other end of the same subject: condition-number-as-digits-lost is what happens when the reformulation is not available and accuracy simply has to be paid for.

    #How to catch it

    Not by inspection. The tests here assert the failure and the fix side by side — naive_sigmoid is kept in the module purely so a test can watch it raise, and the underflow table above is a parametrised assertion at four widths rather than a comment.

    Keeping the broken version next to the working one is document-the-failure-mode-next-to-the-fix: the stable form looks like pointless complexity until the naive form is standing beside it, failing.
