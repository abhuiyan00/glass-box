    One Command Surface, Two Dispatchers

    Publish one vocabulary of verbs — test, package, lint, shots, clean — and implement it twice: a Makefile for anyone with make, and a PowerShell script with the same target names for a Windows machine that has none. The documentation names the verb, never the runner.

    #Why not pick one

    Neither wins. make is absent from a default Windows install and the alternatives are a download; PowerShell is not what a contributor on Linux reaches for. The projects here are developed on Windows and published for everyone, so the choice is between excluding a machine, adding a task runner as a dependency, or writing the second dispatcher — about eighty lines that never change.

    The scripts are dispatchers, not build systems. The real work lives in npm run, pytest, node harness/… and the Python entry points; both files only route to it. That keeps the duplication shallow, which is the only reason it stays correct.

    #The failure mode, and the guard

    Two dispatchers drift: a target gets added to one and forgotten in the other, and the README's instruction is now wrong for half its readers. agent-orchestrator closes that with a unit test — test_both_runners_offer_the_same_targets parses the target names out of both files and asserts the sets are equal (tests-that-guard-the-repository). Drift becomes a red test rather than a bug report from the one contributor on the other OS.

    This wiki's own tooling has the same shape (Makefile beside brain.ps1) and, at the time of writing, no such guard.

    #The nice second-order effect

    Having to name every operation as a verb forces the operations to be nameable. A repository where make test means the whole gate — and says how many checks that is — has already decided what "the gate" is. That decision is more valuable than either script.
