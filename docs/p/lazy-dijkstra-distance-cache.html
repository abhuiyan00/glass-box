    Lazy Dijkstra Distance Cache

    Do not build the all-pairs distance matrix. The first time anything asks for dist(a, ·), run one Dijkstra from a and cache every a→* distance it produced along the way; every later query from a is then O(1). Sources are populated on demand and never recomputed.

    The insight is that Dijkstra is already single-source-all-destinations — stopping early at a single target throws away work you have already done. Caching the whole row costs one array per source and turns a repeated-query workload into an amortised one.

    #Why it fits this workload exactly

    In multi-depot-vehicle-routing the road graph is far larger than the instance. A 5000 m Wrocław drive network is thousands of nodes; an instance uses 200 customers plus 5 depots. An all-pairs matrix over the graph would be enormous and almost entirely unused, while an all-pairs matrix over just the instance points would still need one Dijkstra per point up front — paid whether or not the search ever visits that point.

    Distances are also directed — one-way streets are respected, so dist(a,b) ≠ dist(b,a) in general and the cache is genuinely per-source, not symmetric. The graph is truncated to its largest strongly-connected component precisely so that a query can never fail to find a path.

    #The behaviour it produces, documented rather than debugged

    The visible consequence is a warm-up transient, and the spec calls it out so nobody reads it as a bug:

    "It is computed lazily: the first query from a source a runs one Dijkstra from a and caches every a→* distance; later queries from a are O(1). No upfront full matrix. Generation 0 is slow while the cache fills, then evaluation accelerates — expected behaviour, not a stall."

    Optimization Methods/final_project/ARCHITECTURE.md, 2026-07-10

    That sentence is a small instance of provenance-and-limits-stated-inline — the surprising runtime shape is written down beside the design that causes it, so the next reader does not spend an evening profiling generation 0.

    #The constraint it imposed later

    The distance oracle is a concrete Dist type with a non-virtual operator(), and the GA takes it by reference. That is fast — no vtable in the innermost evaluation loop — but it means an alternative scorer cannot be substituted at runtime. When the LBBS variant needed a penalised distance function, it could not be injected into the GA at all:

    "Cannot feed BannedDist into the GA (Dist has no virtual operator() and distance.hpp must not change)."

    Optimization Methods/final_project/mdvrp/include/lbbs.hpp, 2026-07-10

    So the two-phase LBBS design explores with real distances and applies the ban only in the final decode. A performance decision in the distance layer became an architectural constraint two solvers later — see soft-multiplicative-ban-penalty and workload-balance-vs-distance.

    #Related

    The same family of shortest-path trade-offs — when to precompute, when not to bother at all — is catalogued on shortest-path-algorithm-family, where a 25-node graph in discrete-mathematics-laboratories takes the opposite decision and skips the optimisation explicitly.
