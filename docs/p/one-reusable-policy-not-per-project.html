    One Reusable Policy, Not Per-Project

    Decision. Maintain one privacy policy in its own repository, written to be copied and edited for any project, instead of writing a bespoke policy inside each project that needs one.

    Date. Stated in the expanded README committed 2026-07-10. Confirmed at interview, 2026-07-28: "A template, and Pages is live."

    #Why

    The intent is declared in the first paragraph the reader sees:

    "that does not run analytics, ads, or trackers, and is designed to be reused as a template for"

    privacy-policy/README.md, 2026-07-10

    and the policy text itself repeats it, so the reuse claim survives being copied away from the README:

    "and to be reusable across the projects maintained by the author."

    privacy-policy/PRIVACY_POLICY.md, 2026-07-10

    Writing privacy law is the expensive part; the per-project delta is usually four fields. So the repo supplies a checklist of exactly those four — owner name and contact, effective date, the hosting section, and the cookies/analytics sections — under a "Reuse it for another project" heading. That list is the decision made operational.

    #What it covers today: nothing else in the corpus

    This is the finding that matters, and it is chronological. privacy-policy was created 2026-02-28 and its full text landed 2026-07-10. farely's first commit is 2026-07-12; stickfps's is 2026-07-24. The template predates both by roughly 4.5 and 5 months, so it covers neither.

    The content agrees independently. Farely is an Android app with an accessibility service, on-device inference, an optional cloud-vision path and a third-party events feed — and it carries its own privacy documentation that never links here. Stickfps has accounts and a database. The policy discloses only host server logs and inbound email, "None set by this Service by default" for cookies, and no other processor. Two independent lines of evidence: confidence: high.

    So the template is real and the reuse workflow is real, but as of the last commit it is being applied to one thing — the author's own GitHub Pages presence — not to a portfolio of products.

    #Alternatives rejected

    Option Why not
    A policy file inside each projectduplicates the legal text N times; a fix to one never reaches the others
    No policy at allthe author chose to publish one before any product needed it — creation predates every product repo
    A generated policy from a serviceno vendor, no generator, no dependency anywhere in the repo — consistent with zero-dependency-no-build-step

    #The standing risk

    A template's factual claims are only true of the deployment it was written for. Applied unedited to a project with analytics, a database or a cloud API, §6's "does not set its own cookies" and §7's "No other third-party processors" become false statements in a legal document — the worst kind of drift, because nothing in the file changed. The README's four-field checklist is the mitigation and is the reason controller-vs-processor flags §7 as the section that moves.

    The mechanism is ordinary documentation-drift with unusually high stakes; the current state is safe only because the policy currently describes exactly one site, which is exactly what it says it describes. See host-on-github-pages and data-minimisation for why the unedited defaults are so absolute in the first place.
