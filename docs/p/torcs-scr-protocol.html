    TORCS and the SCR Protocol

    TORCS is an open-source racing simulator. SCR (Simulated Car Racing) is the competition patch that exposes a driving agent over a UDP socket instead of requiring it to be compiled into the simulator as a C++ robot. Everything the PPO agent in it-applications-in-business-and-commerce can see or do passes through that socket, and the protocol's shape determines the whole design of the project.

    #The sensor and actuator surface

    The client (snakeoil3_gym.py, 605 lines, vendored from Chris X Edwards' original snakeoil library and present identically in both agent trees) encodes and decodes a string-based sensor/actuator message over a blocking recvfrom with a timeout.

    Readable: angle, curLapTime, damage, distFromStart, distRaced, focus, fuel, gear, lastLapTime, opponents, racePos, rpm, speedX, speedY, speedZ, track, trackPos, wheelSpinVel, z.

    Writable: accel, brake, clutch, gear, steer, focus, meta.

    That list is the entire observable universe. The 33-dimensional tracking-error state in residual-reinforcement-learning is a function of it; the reward terms catalogued in reward-shaping are functions of it; and every "why doesn't the agent just…" question about this project usually has the answer because the protocol does not expose it.

    #The constraint that shaped the architecture

    The clearest example: the racing line in minimum-curvature-racing-line needs track geometry, and TORCS holds that geometry in a C++ runtime structure the socket cannot reach.

    "tTrackSeg is a TORCS C++ runtime structure. It is ONLY visible to a robot compiled inside TORCS. Our agent talks to TORCS over the SCR UDP protocol (snakeoil3_gym.py) and CANNOT see tTrackSeg."

    IT Applications in Business and Commerce/project/code/a.bhuiyan/guide.txt, 2026-07-10

    The response was to obtain the same geometry offline from the track XML — recorded as parse-track-xml-not-ttrackseg. Runtime localisation then uses only sensors that are available: distFromStart for arc length, trackPos for lateral offset, angle for heading error, speedX for speed.

    Two further protocol consequences show up in the code: gear must be commanded, so a gearbox policy had to be built (see data-driven-gearing-over-hand-tuned-rpm-bands); and the only acceleration signal available is the difference of successive speedX readings, which the gear_strategy_max_jerk branch report explicitly calls out as noisy.

    #Deliberately not vendored

    The simulator itself — roughly 1 GB of third-party C/C++ per branch — is excluded, and the .gitignore says why rather than silently dropping it:

    "# Vendored TORCS simulator — a third-party prerequisite, not committed here"

    IT Applications in Business and Commerce/.gitignore, 2026-07-10

    NOTICE attributes TORCS, SCR and the upstream gym_torcs wrapper. project/README.md carries a "Not included:" callout naming exactly what is and is not the team's work. Good provenance-and-limits-stated-inline, and the reason nothing in this repo runs without a manual TORCS install first.
