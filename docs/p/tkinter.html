    Tkinter

    Python's standard-library GUI toolkit. Chosen in both lab repositories for the same stated reason: it ships with Python, so a marker can run the program without installing anything.

    #Nim game — Discrete Maths lab 4

    A four-variant Nim implementation with an AI opponent, see sprague-grundy-nim-sum. The structure is worth recording independently of the toolkit:

    • Layered: variants → players → state → screens. The game rules never touch a widget, so the same engine drives all four variants.
    • Screens instantiated once, raised with tkraise() rather than destroyed and rebuilt on navigation. Widget state survives, and there is no rebuild cost or stale-callback risk from tearing down frames.

    PROJECT.md defends the choice only as "no external UI dependencies". TODO: whether PyQt, pygame or a web UI were considered, or stdlib-only was a hard course constraint, is not recorded. confidence: low on the rationale.

    #Knowledge browser — Python labs 13/14

    A sqlite-backed browser over a 610-row corpus, in python-programming-laboratories. Two choices that generalise past Tkinter:

    • Listbox rows are mapped by index to their record, never by parsing the displayed label back into data. Parsing your own UI text is the bug that appears the moment a label contains a separator character.
    • The database connection is opened in main() and closed by contextlib.closing, not opened at import — the same boundary discipline as separating-computation-from-io.

    #Where it sits among the alternatives

    Both uses are desktop apps that had to be handed in and run. Compare the browser-based deliverables in the same Discrete Maths repo — offline-first-static-deliverable — which solve the "runs anywhere with no install" problem with an HTML file instead. Tkinter wins when the program is Python and must stay Python; the HTML route wins when it must open on a machine with no interpreter.
