    Digital Signatures

    Sign with the private key, verify with the public one — the reverse of encryption's key usage, and the source of three properties encryption alone does not provide. Labs 06 and 07 of cybersecurity-engineering-laboratories build and then attack them.

    #The three guarantees

    Property Meaning
    Authenticationthe holder of the private key produced this
    Integritythe data has not changed since it was signed
    Non-repudiationthe signer cannot later disown the signature

    Non-repudiation is the one that has no symmetric-key equivalent. A MAC gives authentication and integrity, but both parties hold the same key, so either could have produced the tag — neither can prove the other did. That asymmetry of evidence is why signatures underpin contracts, code signing, certificate issuance and blockchain transactions.

    #The construction, and where the hash sits

    Three algorithms: key generation, signing, verification. Signing does not encrypt the document — it hashes the document and applies the private-key operation to the digest. The hash is not a performance optimisation bolted on; it is structural, and it relocates the entire security of the scheme onto the hash function.

    Which sets up the attack.

    #The hash-collision attack on a signature

    If two different documents hash to the same value, one signature is valid for both. Get a signature on the innocuous document, attach it to the malicious one, and verification passes — the verifier only ever sees the digest. Lab 06 runs exactly this demonstration in cryptool: construct a collision, sign one preimage, verify against the other.

    The consequence for practice: MD5 and SHA-1 are unusable for signatures regardless of how carefully the signing key is managed. Collision resistance — not preimage resistance — is the property that matters here, and it is the one that falls first.

    #Verification failure modes

    The repository's own selected screenshot for lab 07 is the sign/verify page, and the reason given for choosing it is that the failures are more instructive than the success: verifying against the wrong public key, and omitting the signature argument, fail in different ways. A verification step that can only be observed succeeding teaches nothing about what a real rejection looks like — the same instinct as document-the-failure-mode-next-to-the-fix.

    The page that would have been the obvious illustration was deliberately not used, because it printed a private key — see omit-rsa-private-key-screenshot.

    #The algorithms

    RSA (sign with the private exponent), DSA, and the elliptic-curve family ECDSA/EdDSA. The lab exercises RSA signing through openssl dgst and OpenPGP signing through GnuPG, plus HMAC as the symmetric counterpart. The attack models enumerated are key-only, known-message and adaptive chosen-message — the same taxonomy cryptanalysis-by-measurement uses for ciphers, applied to a signature scheme.

    #Signatures are only as good as the binding

    A valid signature proves a private key was used. It says nothing about whose key that was. The binding from key to identity is external to the signature entirely, which is what public-key-infrastructure provides — and why signature verification in TLS or in a package manager is always chained to a trust store rather than terminating at a single key.
