    Duplicated Sim Code Instead of a Shared Package

    Decision: keep the shared simulation logic as two hand-synchronised copies — one in client/src, one in server/src — rather than extracting it into a workspace package both import.

    "server/src/sim/movement.ts — server-authoritative stepPlayer — intentionally duplicated from client/src/game/player/playerController.ts, not imported, so the server has no runtime dependency on client code."

    browser_game_stickfps/docs/specs/task-4.1.md, 2026-07-25

    Three pairs are duplicated this way: the movement step, the weapon rules/definitions, and the message type definitions.

    #The reason, stated and narrow

    The server must have no runtime dependency on client code. Under server-authoritative-netcode the server is the security boundary; a shared package makes it import from the same tree as the untrusted half, and every change to client rendering code becomes a change that can reach the authority. Duplication makes the boundary structural instead of a convention.

    The secondary effect is deployment shape: the two halves build and ship independently (split-frontend-backend-hosting), with no workspace root to resolve, which keeps the docker image and the Render build simple.

    #The cost, which is real

    Duplicated movement code that drifts breaks client-side-prediction-and-reconciliation silently — prediction error grows and the blend never catches up, and it manifests as "the controls feel bad", not as a failing test. Duplicated message types break the wire format at runtime rather than at compile time.

    What makes it survivable here is that the client copies are explicitly cosmetic: the client predicts with them, and nothing they compute is ever scored. A divergence produces visual drift, not a wrong kill. That asymmetry is the precondition for this trade, and it is the thing to check before copying the pattern — duplication is affordable exactly where one copy is not authoritative.

    Extraction into a shared workspace package is recorded in the spec as a named follow-up, not as an oversight.

    #Alternative rejected

    A packages/shared workspace importing into both — the conventional answer. Rejected on the runtime dependency argument above. Note it would not have removed the need for fixed-timestep-simulation to run at an identical rate on both sides; a shared package makes the code identical, not the schedule.
