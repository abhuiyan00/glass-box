    ETL Load Order

    Load order in a star-schema is not a style choice. Declared foreign keys make it a hard dependency graph: every dimension a fact references must be populated before the fact is inserted, or the insert fails. The interesting part is what you populate the dimension from.

    #The dependency chain, as built

    In data-warehousing-and-business-intelligence, the retail load runs in six stages:

    1. DIM_TIME — from the source order-header table
    2. DIM_CUSTOMER — a LEFT JOIN chain plus an OUTER APPLY for the primary address
    3. DIM_PRODUCT — independent of 2
    4. DIM_SALESPERSON — independent of 2 and 3
    5. FACT_SALES — joins the source header to its detail rows
    6. verification — a UNION ALL row-count roll-call across all five tables, then two anti-join referential-integrity checks

    Stages 2–4 are mutually independent and could run in any order or in parallel; only the dimension→fact edge is real. Stage 6 is the subject of verify-the-load-dont-declare-it.

    #The counter-case that makes the rule concrete

    The obvious way to build a calendar dimension is to select the distinct dates out of the fact table — it is the smaller, more relevant set. The source comment writes out why that deadlocks: the dimension would be built from an empty fact, the fact load would then find no matching parent rows for its foreign keys, and the warehouse "would build cleanly and contain nothing". Building DIM_TIME from the source header instead — a UNION of order dates and ship dates, because the calendar is role-played twice — breaks the cycle.

    This is the transferable form of the rule: a dimension must be sourced from upstream of the fact, never from the fact it serves. A build that succeeds and produces nothing is the failure mode to design against, because it does not raise an error.

    #Truncate-and-rebuild, not incremental

    Every load here is full rebuild — the DDL opens with DROP TABLE IF EXISTS. There is no change-data-capture, no watermark column, no merge, and no slowly-changing-dimension handling anywhere in the repository. That simplifies ordering enormously: with no history to preserve, the only constraint is the FK graph. It also makes natural keys sufficient.

    #Staging as a separate stage

    The price mart adds a landing step first: ssis moves a flat file into a staging.quotes table that carries CHECK constraints at the door (high ≥ low with open and close bounded by both; non-negative volume), so malformed rows are rejected before any modelling happens. Then the star loads, then a separate script backfills the derived indicator — see window-function-frames. Rejecting bad input at the boundary rather than downstream is the same discipline as separating-computation-from-io.
