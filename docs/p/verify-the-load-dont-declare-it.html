    Verify the Load, Don't Declare It

    A data pipeline ends with a query whose result can be wrong, not with a status row saying it went fine. The distinction sounds pedantic until you have shipped an empty warehouse that logged 'Success' five times.

    "A row count is a fact; a status table populated with 'Success' literals is a claim. These queries are cheap and they fail loudly."

    Data-Warehousing-and-Business-Intelligence/sql/02_star_schema/02_load_star_schema.sql, 2026-07-25

    #Both sides of the argument are in one repository

    The unusual thing about data-warehousing-and-business-intelligence is that it ships the counter-example alongside the pattern. etl/ssis/Package.dtsx creates a load_status table and inserts one 'Success' literal per table, unconditionally — see ssis. The hand-written sql/02_star_schema/ version deletes that idea and replaces it with three things that can fail:

    1. A row-count roll-call — a UNION ALL returning the count of all five tables in one result set. Zero rows anywhere is visible at a glance.
    2. Anti-join integrity checks — NOT EXISTS against the parent dimension for orphaned order dates and for fact rows with no product, each returning a Failures count. The comment beside them reads "Referential integrity actually holds, rather than being asserted."
    3. Property checks on the derived column, in the price mart:

    "A working RSI spends most of its life between 30 and 70. If nearly every row sits at an extreme, the window frame is not doing its job."

    Data-Warehousing-and-Business-Intelligence/project/twtr/sql/03_technical_indicators.sql, 2026-07-25

    That third one is the strongest form. A row count catches an empty load; a foreign-key check catches a broken join; only a property of the output distribution catches a load that ran, joined cleanly, and computed the wrong thing. The same script also asserts the exact warm-up count — thirteen rows with no indicator, the days before the first full window — which is a check on window-function-frames rather than on the data.

    #Why the checks live inside the load script

    The verification is section 6 of the load, not a separate file someone might not run. It is also the reason the dimension is built from the source rather than from the fact table — the load script's own header explains that the alternative would "build cleanly and contain nothing", which is precisely the failure a 'Success' row cannot see. See etl-load-order and fact-grain.

    #The same discipline, enforced rather than written

    labour-fraud-analysis takes the pattern the rest of the way, because it has somewhere to enforce it:

    • build_db.py loads with PRAGMA foreign_keys = ON, so a successful build is the FK proof.
    • test_counts_match_manifest reconciles every CSV's row count against a committed manifest — a real count-vs-expectation check, not a self-report.
    • make validate "must print RESULT: PASS" — the privacy analogue, disclosure-gate.
    • All of it runs on every push via github-actions.

    #The honest limit

    In the warehousing repo the pattern is written but never executed and recorded. Every check is a query needing a live sql-server with both AdventureWorks databases attached; no output, log or expected-count file is committed anywhere in the tree. "0 orphans" is a query, not a result. The difference between the two repositories is not the idea — it is whether a machine other than the author's ever runs it. See generated-audit-artifact and reproducible-analysis.
