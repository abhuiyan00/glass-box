    OpenRouter

    A single OpenAI-compatible HTTP endpoint in front of many vendors' models, billed per token against one account. In agent-orchestrator it is the router: the model that plans, answers directly when a request does not need agents, writes the optional workspace brief, and merges the finished subtasks.

    #The property the design leans on

    The router is the one component that reads every subtask's output — and it has no tools at all. That asymmetry is the security model's load-bearing claim: text that persuades the router can produce a wrong answer but cannot produce an action. The executors have the tools; the reader has none.

    #No vendor is named in code

    The model id is configuration (z-ai/glm-5.2 by default, any id OpenRouter serves). At start-up the backend resolves the display name, context window and reasoning support from /models, and if the id is absent from that catalog it still uses it and logs a line saying so. So switching router is a settings change, and a model released next week works without a code change.

    Where a configured router advertises no reasoning parameter, none is sent — the same restraint as reasoning-effort-as-a-portable-label one level up.

    #Cost and key handling

    Only these calls cost money: roughly $0.002 for a two-subtask run, because the agents themselves run on the user's existing CLI subscriptions (claude-code-cli, codex-cli). The key lives in VS Code's encrypted SecretStorage, reaches the backend as an environment variable, and is never sent to the webview — secrets-from-environment-only. The plaintext settings field still works and the panel offers to migrate it, because a key already typed into settings is a fact to handle, not a mistake to lecture about.
