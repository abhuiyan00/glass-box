    PL/SQL Exception Handling

    PL/SQL reports failure by raising, not by returning. That single fact reshapes how blocks are written, because the most common statement in the language — SELECT INTO — has three outcomes and only one of them is a value.

    #SELECT INTO is all-or-nothing

    "SELECT INTO is all-or-nothing. Exactly one row satisfies it; zero rows raise NO_DATA_FOUND and two or more raise TOO_MANY_ROWS. Both are exceptions, not return values, so every block below that uses it handles them explicitly."

    Oracle-Database-Laboratories/sql/03_plsql/01_blocks_and_exceptions.sql, 2026-07-25

    A consequence that bites: when SELECT INTO raises, its INTO target is left unassigned. The lookup block in oracle-database-laboratories therefore prints the searched-for variable in its handlers, not the target — reporting the target would print an empty string exactly where the diagnostic is needed. Handlers must read from state that was valid before the failure.

    #Three sources of exception

    Source Example here
    PredefinedNO_DATA_FOUND, TOO_MANY_ROWS around SELECT INTO
    User-definedalready_exists, invalid_band_no — declared EXCEPTION, raised by RAISE, caught by name
    SQLCODE inspectionthe teardown script catches WHEN OTHERS, allows ORA-00942 and ORA-04043, re-raises everything else

    The third pattern is worth isolating. A bare WHEN OTHERS THEN NULL swallows everything and is the single most damaging idiom in the language. The teardown script's version tests SQLCODE IN (-942, -4043) and calls RAISE in the ELSE — so "the object was already gone" is tolerated and a genuine failure still propagates. That narrow, deliberate swallow is what makes idempotent-teardown-scripts safe rather than reckless.

    #Reporting failure across a boundary

    A stored procedure that catches its own exception and prints a message returns normally, leaving the caller unable to distinguish success from rejection. herd_admin.add_band instead raises through RAISE_APPLICATION_ERROR in the -20000 to -20999 range Oracle reserves for application errors — any other code produces ORA-21000 in place of the intended message. See plsql.

    The caller's side of the same contract is visible in the exercise loop: each call is wrapped in its own inner BEGIN … EXCEPTION WHEN OTHERS THEN that prints SQLERRM and continues, so one rejection does not abort the batch. Raise at the boundary, decide at the call site.

    #Two failures that look like a working handler

    Both are recorded in the same file, and both produce a wrong answer rather than an error:

    • Name collision. Where a PL/SQL variable or parameter shares a name with a column, PL/SQL resolves in favour of the PL/SQL identifier. WHERE name = name_band becomes a tautology, the duplicate check silently passes on everything, and nothing raises. The fix is to qualify every predicate with the table name. The procedure version in 03_procedures_and_packages.sql documents exactly this collision at the point where it would occur.
    • Buffer overflow inside the handler. The clash-message buffer is VARCHAR2(200), not 50, because three appended clashes overflow a 50-character buffer and ORA-06502 replaces the diagnostic the handler existed to produce. A handler that can itself raise is not a handler.

    Both are instances of tests-that-pass-for-the-wrong-reason expressed in a language with no tests — the check runs, reports success, and checks nothing.
