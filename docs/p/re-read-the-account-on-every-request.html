    Re-read the Account on Every Request

    Decision. project-management-web-platform verifies a session token and then loads the account named by its claims for every authenticated request. Authorisation receives the actor created from that current account record, rather than treating the token's role claim as the current source of authority.

    One store lookup per authenticated request is an intentional part of the contract.

    #The authentication flow

    The authenticate service performs the steps in order:

    1. verify the token's HMAC, structure, and expiry;
    2. load the user by the verified identifier;
    3. reject a missing or blocked account;
    4. derive an actor from the loaded user and pass it to policy code.

    A valid signature proves that this service issued the credential; it does not by itself prove that the named account is still active or holds the same role. Reloading the account gives the service current state when it makes the access decision.

    The HTTP middleware keeps that verified actor and user in a WeakMap keyed by the request object. Client-controlled request JSON is therefore separate from authenticated identity.

    #Observable session behaviour

    The HTTP authentication tests cover the resulting guarantees:

    • blocking an account takes effect on its next request;
    • deleting an account makes a still-unexpired credential unusable;
    • granting or removing an administrative role changes the next authorisation decision;
    • a token for a missing account is rejected as an authentication failure.

    These are properties of the current account record, not promises embedded in a credential at issuance time.

    #Cost and scaling boundary

    The cost is one additional lookup for each authenticated request. At this repository's scale, that direct lookup keeps the policy simple: there is no token denylist, token-version store, or separate revocation state to reconcile.

    A higher-throughput service may cache accounts for a short TTL and accept a bounded delay before a state change takes effect. That is a different contract and should state both the TTL and the acceptable revocation window. This API chooses immediate use of the stored state instead.
