    Parse Track XML Instead of tTrackSeg

    Decision. Reconstruct the track centreline offline, by parsing the track's XML definition, instead of reading TORCS's own tTrackSeg geometry at runtime.

    Date. Recorded in guide.txt §0, published 2026-07-10. The work it governs (racing_line.py) predates publication — the branch it comes from has upstream commits from 2026-04-19 onward, and the generated racing line is dated 2026-06-04/05.

    #The rejected alternative, and why it fails

    The original plan said to relax the racing line along tTrackSeg coordinates — the natural choice, since that is the simulator's own internal representation of the track. It is unreachable:

    "The plan says 'run the relaxation along the tTrackSeg coordinates.' tTrackSeg is a TORCS C++ runtime structure. It is ONLY visible to a robot compiled inside TORCS. Our agent talks to TORCS over the SCR UDP protocol (snakeoil3_gym.py) and CANNOT see tTrackSeg."

    IT Applications in Business and Commerce/project/code/a.bhuiyan/guide.txt, 2026-07-10

    Taking tTrackSeg would have meant abandoning torcs-scr-protocol and compiling the agent into the simulator as a C++ robot — which would also mean abandoning Python, pytorch and the entire training stack. The alternative was rejected on reachability, not on quality.

    #What replaced it

    "Fix: get the identical geometry OFFLINE by parsing the track XML (torcs/tracks/road/<track>/<track>.xml). It encodes the track as an ordered list of segments: straights (lg) and arcs (radius, arc, lft/rgt). Integrate those to rebuild the centerline, then relax. Same math, a source we can actually reach from Python."

    IT Applications in Business and Commerce/project/code/a.bhuiyan/guide.txt, 2026-07-10

    racing_line.py (507 lines) does exactly that: arc-length integration over straights and arcs including clothoid transitions (r0/r1), then periodic Laplacian relaxation inside a ±(w/2 − 1.5 m) corridor. See minimum-curvature-racing-line.

    Runtime localisation then uses only sensors the UDP protocol does expose — distFromStart as arc length, trackPos as lateral offset, angle as heading error, speedX as speed. The precomputed line becomes a lookup keyed on distFromStart, which is what makes the tracking-error state of residual-reinforcement-learning possible at all.

    #The consequence nobody planned: this became the house style

    Having established that vendor XML is the reachable source of truth, the same move was applied to the car. car_spec.py walks practice.xml → scr_server.xml → the car XML to pull gear ratios, final drive, tyre radius, the rpm→torque curve and the rev limiter — see data-driven-gearing-over-hand-tuned-rpm-bands. Two independent subsystems, one technique: parse the simulator's configuration files rather than guess at, or try to reach, its runtime state.

    #Costs accepted

    • The line is per-track and precomputed. Change the track in the TORCS GUI and the .npz must be regenerated; the guide says so explicitly.
    • Offline geometry has no ground-truth alignment to the runtime s origin. guide.txt gotcha G5 flags that distFromStart may not coincide with XML segment[0], and gotcha G4 names a recon_lap.py calibration tool — which does not exist in the tree.
    • TODO: how the trackPos sign convention and the distFromStart offset were actually calibrated is unrecorded, since the tool the guide points at was never committed. confidence: low on the calibration story. Do not invent one. See documentation-drift.
