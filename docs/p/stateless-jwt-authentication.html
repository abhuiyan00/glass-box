    Stateless JWT Authentication

    The server keeps no session. A client registers, logs in once, receives a signed JSON Web Token, and sends it on every subsequent request as Authorization: Bearer <token>. The server verifies the signature and reads the claims — user id, role, expiry — and that is the entire authentication state. Nothing is stored between requests, so any instance can serve any request and a restart logs nobody out, provided the signing key is stable.

    #⚠ It exists in lab 4. It does not exist in lab 3.

    This is the sharpest contract-versus-implementation gap in the source set, and both the lab 3 README and the lab 3 OpenAPI document assert the opposite of what the lab 3 code does.

    The lab 3 contract specifies it:

    "UC-02: Login – issues HttpOnly JWT session cookie (bcrypt verify)"

    Information-Systems-Modelling/lab3/StudentService_vlab3/src/main/resources/openapi/openapi.yaml, 2026-04-14

    The lab 3 README repeats it:

    "The skeleton becomes a real backend. StudentService_vlab3 (Spring Boot 3.5.6 / Java 21) adds stateless JWT authentication — register, log in for a token, then send Authorization: Bearer <token> on protected endpoints"

    Information-Systems-Modelling/lab3/README.md, 2026-07-09

    The lab 3 code implements none of it. Verified at HEAD:

    • lab3/.../pom.xml contains no jjwt and no spring-security-crypto — the dependencies first appear in lab 4.
    • There is no security/ package in lab 3 — no JwtService, no AuthInterceptor, no CurrentUser. grep for Jwts, BCrypt or Bearer across lab3/.../src/main/java returns nothing.
    • UserServiceImpl.register passes request.getPassword() straight into the UserEntity constructor, which assigns it to the password column. Passwords are stored in the clear.
    • AuthController.authLoginPost calls userService.findByEmail(...) and returns the profile if a row exists. The submitted password is never compared to anything — any known email logs in.

    Recorded as a finding, not repaired: the wiki does not edit source repos. This goes beyond documentation-drift — the drift is between a contract and its implementation, which is the exact failure contract-first-api-design is supposed to make visible.

    #Lab 4 is the real implementation

    Class Role
    JwtServiceissues and verifies tokens (jjwt 0.12.6, HMAC-SHA, 24 h TTL)
    AuthInterceptorSpring MVC interceptor, registered in WebMvcConfig.addInterceptors
    CurrentUserthe resolved principal handed to controllers

    AuthController.authLoginPost calls userService.verifyCredentials(email, password), returns 401 on failure, and on success issues a token via jwtService.issue(id, role) inside a LoginResponse. register hashes with passwordEncoder.encode(...) — BCrypt from spring-security-crypto, which is the only piece of Spring Security in the build. See bcrypt-crypto-only-no-spring-security.

    The angular SPA in lab 4 is the consuming client: it stores the token, attaches it to REST calls and guards routes on its presence.

    #The dev-key hazard, documented rather than hidden

    JwtService reads jwt.secret from configuration. If it is blank it generates a random 256-bit key per JVM start and logs a warning — every issued token dies on restart. The javadoc states the condition and the fix:

    "If blank, a random key is generated per JVM start (dev mode only — all issued tokens are invalidated on restart)."

    Information-Systems-Modelling/lab4/.../security/JwtService.java, 2026-05-28

    provenance-and-limits-stated-inline applied to a security control: the insecure default is allowed, but it announces itself in the logs and in the source. No key, secret or demo credential from this repository is reproduced in this wiki.

    #What statelessness costs, and what is untested

    Statelessness buys horizontal scaling and costs revocation: a token is valid until it expires, so logout is client-side only and a compromised token cannot be recalled inside its 24-hour TTL. Nothing implements a deny-list or a refresh-token scheme, and no README raises the question.

    BuildsControllerIntegrationTest exists in both labs with one @Test each, driving register → login → POST /builds through MockMvc. In lab 3 that flow passes precisely because nothing is enforced — a test that passes for the wrong reason. No test covers token expiry, tampering, a missing header, a wrong role, or the interceptor's exclusion list.
