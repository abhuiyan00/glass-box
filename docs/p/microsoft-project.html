    Microsoft Project

    Desktop scheduling tool; the primary artefact format of computer-project-management and the only piece of proprietary tooling in the source set. Four .mpp files carry the entire deliverable — one throwaway practice plan plus export-import-system.mpp at three maturity stages, each in its own lab folder under the same filename.

    #What the tool supplies to the coursework

    Every concept the labs teach is a Project feature exercised in order:

    Feature Recorded as
    outline / indent hierarchywork-breakdown-structure
    FS / SS / FF task linkswork-breakdown-structure, sequence-integration-after-unit-testing
    resource pool + assignment + over-allocation flagsresource-leveling
    Save Baseline, then actuals against itschedule-baseline-and-variance
    the critical-path flag and tracking Ganttcritical-path-method
    cost rollup from hourly ratesschedule-baseline-and-variance

    The critical path is a striking case: it is never computed in the repo, only read off a red bar in the tracking Gantt. The tool is the algorithm.

    #The format is the problem

    .mpp is a closed binary. The repo handles that in two ways, both deliberate:

    "# Treat the binary coursework artifacts as binary — no line-ending"

    Computer Project Management/.gitattributes, 2026-07-10

    Four glob rules — *.mpp, *.pptx, *.pdf, *.png — stop git normalising or attempting to diff/merge them. And the README supplies an escape hatch for readers without a licence: ProjectLibre or GanttProject to open the files, or the PDF reports, which "render the full plan — schedule, Gantt, resources and costs — with no software needed".

    That escape hatch is the same instinct as offline-first-static-deliverable pointed at a different constraint: not "no network" but "no licence". It only half works — the PDFs are the lab 5–6 and 7–8 reports, so the earlier stages remain openable only in a scheduling tool.

    Consequence for this wiki: the .mpp and .pdf files are unread by policy, so every quantitative claim on the Computer Project Management pages rests on hand-written README tables alone. That is the single largest verification gap in this group of repos and is why those pages carry confidence: medium.

    #Version control fit

    588 KB of binaries committed raw — no Git LFS, despite the format being exactly the case LFS exists for. Every edit to a plan stores a whole new copy. At four files and one publishing session this costs nothing; on a live plan revised weekly it would. Same posture as optimization-methods, which commits an 11 MB PDF without LFS.
