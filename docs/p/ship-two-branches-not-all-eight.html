    Ship Two Branches, Not All Eight

    Decision. Publish two of the ten experiment branches as running code, and cover the rest with written per-branch reports.

    Date. 2026-07-10, the day the whole tree was imported to git.

    #The choice and its criterion

    "Two variants of the agent are included, as requested: stable (the best result) and a.bhuiyan (the most different architecture). The per-branch reports document the entire team's work, so nothing is lost by shipping only two code trees."

    IT Applications in Business and Commerce/project/README.md, 2026-07-10

    The selection rule is stated, and it is not "the two best". It is best plus most different — maximum result and maximum coverage of the design space, which is a deliberately different criterion from ranking. stable is the danger-reward agent with split actor/critic trunks; a.bhuiyan is the offline racing line plus residual-reinforcement-learning rewrite. Two branches that agree with each other would have taught a reader nothing.

    #The rejected alternatives

    • Ship all ten. Rejected implicitly by "as requested" — the constraint came from outside. The cost would have been real: each tree carries its own ~1500-line environment wrapper, a duplicated 605-line snakeoil3_gym.py and ~0.9 MB of checkpoints.
    • Ship the best only. Rejected in favour of including the architectural outlier. This is the interesting half of the decision, because a.bhuiyan is not the better performer — its own README records that it never completed a clean lap.
    • Ship code and skip the write-ups. Rejected: the compensation clause — "the per-branch reports document the entire team's work" — is what makes shipping two trees defensible rather than lossy. Eleven markdown files, 846 lines, with tip SHAs, constants tables and reward pseudocode. See generated-audit-artifact and branch-per-experiment.

    #The same instinct one paragraph earlier

    The README applies the identical logic to the results it reports:

    "Reporting only the best lap would overstate reliability, so consistency was measured over a batch"

    IT Applications in Business and Commerce/project/README.md, 2026-07-10

    Best-plus-spread for the numbers, best-plus-most-different for the code. Both are refusals to let a single flattering artefact stand in for the work — the habit catalogued as provenance-and-limits-stated-inline.

    #What the decision actually cost

    Six of the branches now exist only as prose. Nothing in them is reproducible from this repository: the parallel branch's throughput result has no code behind it, and the report itself claims only ~9× environment concurrency rather than the ~9× rollout throughput the top-level README reports. The reports are an audit of a different repository — Szymon1905/AI_racer_pytorch — and the tool that produced them was not committed, so the audit cannot be re-run either.

    There is a softening, too. project/README.md describes the a.bhuiyan branch as having "reduced but didn't eliminate" its S-curve errors, where that branch's own README says flatly that it "did not fully solve the S-curve" and the car "did not finish a clean full lap in the earlier runs". The top-level page is the more generous of the two. See documentation-drift.
