    BPMN Process Modelling

    BPMN 2.0 (OMG Business Process Model and Notation — not UML) models the work that happens around a system rather than inside it: who does what, in which order, who waits on whom, and what happens when a step fails. A model is a collaboration when it spans more than one participant: each participant is a pool, roles inside a pool are lanes, sequence flows may not leave a pool, and anything crossing a pool boundary must be a message flow.

    Information-Systems-Modelling lab 7 ships 8 collaborations covering the ModellingClub platform's operational life cycle. This is the only place in the source set where formal process models exist as real artefacts rather than as prose.

    #The eight processes

    # Process Theme Notation exercised
    1Scheduled Backup & Verificationmaintenancetimer start, parallel split/join, boundary error, error end
    2Software Upgrade / Dependency Patchmaintenancemessage start, severity gateway, staging loop-back, rollback
    3Release & Blue-Green Deploymentdeploymentparallel build+test, approval gate, 5 lanes
    4H2 → PostgreSQL Migrationdeploymentmaintenance-window timer, reversible cut-over
    5Data Archiving, Retention & GDPR Erasuredata / securitytwo start events, legal-hold gateway, 30-day boundary timer
    6Security Incident Responsedata / securitysignal start, 3-way severity, 72 h GDPR timer
    7Member Onboarding & Provisioningbusiness3-pool collaboration, boundary timer, SLA accept/reject
    8System Decommissioning / End-of-Lifebusinessnotice timers, terminate end, contract-termination message flow

    Participants reach well beyond the application's own actors — DevOps, Release Manager, DBA, Data Protection Officer, security on-call, an Operations Committee, the cloud provider, offsite storage and the GDPR supervisory authority. Several are modelled as black-box pools: present, addressed by message flow, with no internal detail. That is the correct BPMN treatment of a party whose internals you do not control.

    Process 4 is a quiet cross-reference: the thing being migrated is h2-database, the actual dev database of labs 3 and 4.

    #Three artefacts from one specification

    Each process exists once, as a JavaScript object in lab7/src/specs.js (605 lines), declaring pools, lanes, nodes with event markers, sequence flows and message flows. A ~1,400-line zero-dependency Node generator turns that into three deliverables: a self-contained SVG diagram, a Camunda-compatible .bpmn XML file including diagram interchange (DI), and a section of the PDF report. See single-source-of-truth-generators and generate-markup-instead-of-hand-writing-it.

    Diagram interchange matters here: a .bpmn file without DI carries the semantics but not the layout, so a modeller re-opening it gets a valid process arranged as a heap. lab7/src/layout.js (307 lines) computes a layered auto-layout so that the SVG a reader sees and the .bpmn a modeller opens show the same picture.

    Files are numbered p1-backup … p8-eol across bpmn/, diagrams/ and the P1…P8 constants in specs.js — see numbered-stages-in-directory-names.

    #What was checked, and what could not be

    "Every model was checked against BPMN execution semantics: each path reaches an end event; parallel splits are matched by parallel joins; exclusive / event-based gateways carry mutually-exclusive conditions; message flows only ever cross a pool boundary."

    Information-Systems-Modelling/lab7/README.md, 2026-07-09

    That is a real correctness checklist, and it is the right one. But the same README also asserts all eight files import warning-free in bpmn-moddle, and bpmn-moddle appears in no package.json and no script anywhere in the repo.
