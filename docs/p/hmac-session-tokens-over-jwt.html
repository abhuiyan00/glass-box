    HMAC Session Tokens Over JWT

    Decision. project-management-web-platform issues session credentials as a base64url JSON payload and an HMAC-SHA256 tag, using node:crypto rather than a JWT library.

    ~~~text base64url(JSON({ u, r, iat, exp })) . base64url(HMAC-SHA256(payload, secret)) ~~~

    The session secret comes from validated configuration. The payload identifies the account and records its issuance and expiry; request authentication reloads the account before building the current actor.

    #A small, fixed protocol

    The token implementation has one signing algorithm: HMAC-SHA256. It has no caller-supplied algorithm field, and verification compares the expected tag in constant time before parsing the payload. It also rejects malformed structures, invalid claims, expired tokens, and timestamps that are too far in the future.

    Keeping those checks in one short module makes the token boundary visible. The accompanying node:test suite covers valid issuance, forgery, tampering, expiry, malformed input, and bearer header parsing.

    #Why this format fits here

    The API is a single service with one runtime dependency, Express. Node provides the HMAC primitive through its standard library, so this format does not introduce a second runtime package for a single verifier.

    This is not a general recommendation to avoid JWTs. A maintained JWT library is a good fit when other services must validate the same credential or when a standard interoperable representation is required. In that situation, the project's own source recommends adopting the maintained library rather than porting this format.

    #The trade-off is interoperability

    These credentials are intentionally local to this service. Another verifier would need an agreed protocol and compatible key handling, so interoperability is the point at which the format's small surface area stops being an advantage.

    The format also does not make the service stateless. The API chooses to reload the named account on each authenticated request so a block, deletion, or role change takes effect from current data. That complementary decision is described in re-read-the-account-on-every-request.
