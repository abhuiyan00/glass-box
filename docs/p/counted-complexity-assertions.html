    Counted Complexity Assertions

    Turning an asymptotic claim into an ordinary unit-test assertion by counting operations instead of measuring time.

    #The problem with the obvious approach

    A test that asserts merge sort beats insertion sort by the clock is a test about the machine it ran on. It passes on a quiet laptop, fails on a loaded CI runner, and in neither case says anything about the algorithms. So complexity claims end up in comments, where nothing checks them and they drift away from the code underneath.

    #The mechanism

    1. Charge the algorithm. Every operation takes a counter and increments it for each key comparison, element move and structural probe. The cost becomes part of the signature, not an estimate made afterwards.
    2. Measure over a doubling series. Run at n, 2n, 4n, … with a fresh counter each time.
    3. Fit scale-free. For each candidate growth function g, take the constant that best explains the data — the mean of ops(n) / g(n) — and score the candidate by mean relative error. Lowest wins. Dividing the constant out is what makes the verdict an order and nothing else, which is exactly the claim asymptotic notation makes.
    4. Assert the class. assertEquals(Growth.LINEARITHMIC, classify(measure(sizes, work))).

    Counts are deterministic for a fixed input, so the assertion is reproducible everywhere. The same idea appears in a different guise in cryptanalysis-by-measurement: replace an argument about behaviour with a number the code produces.

    #What it is not

    Not a proof. It measures the sizes it was given over the inputs it was given. A quadratic worst case hiding behind a linear average is a property of the input generator, which is why a quicksort test that wants to see the worst case must feed it a sorted array on purpose.

    Not able to name a class outside its candidate set. Shell sort is O(n^1.5) and jump search O(√n); with neither in the candidates, both are asserted negatively — "not quadratic", "the cost doubles when n quadruples" — rather than forced into a box. An honest negative beats a confident wrong label.

    Not immune to small n. n/4 + 1000 classifies as constant at n ≤ 512 and linear at n ≥ 8192, and the fitter is correct both times: asymptotic behaviour is a claim about large n. Every growth assertion has to pick sizes where the term under test dominates, and the disagreement itself is worth keeping as a test.

    #What it caught

    Two documented claims that were wrong, found because the measurement disagreed with the javadoc:

    • Repeated heap insertion measures linear on shuffled input. The familiar O(n log n) is the worst case; a random key sifts up about one level. The gap appears only on descending keys.
    • Linear probing with nearly consecutive hashes is not constant per operation at all. Its measured total is neither linear nor monotonic in n, while double hashing on the same keys is a straight line.

    Both were fixed in the documentation rather than by relaxing the assertion, which is the useful direction: see document-the-failure-mode-next-to-the-fix and data-structures-and-algorithms for the full record.
