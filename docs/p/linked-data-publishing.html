    Linked Data Publishing

    Publishing linked data means shipping a web page that is simultaneously readable by a person and parseable as a graph by a machine, with every entity identified by an IRI that can actually be fetched. Three obligations follow, and Information-Systems-Modelling lab 6 meets all three.

    #1. The same facts in two syntaxes, from one source

    Every page carries RDFa 1.1 attributes inline in the body markup and a JSON-LD block in the head. Both are emitted by one renderer from the JSON files in lab6/app/data/ — builds.json, communities.json, marketplace.json, testruns.json, users.json, site.json. The data is the ABox; the vocabulary comes from lab6/vocabulary/ontology.ttl and mc-context.jsonld.

    This is the whole point of the lab and the subject of generate-markup-instead-of-hand-writing-it: the previous version hand-wrote both syntaxes into six HTML files, so each fact existed in two to four places and could drift.

    #2. Dereferenceable IRIs — 303 plus content negotiation

    An IRI that names a thing (a build) must not be confused with the IRI of a document about that thing. lab6/app/src/server.js implements the W3C recommendation directly:

    • request /resource/build-falcon with Accept: text/html → 303 See Other to the human page
    • request it with Accept: application/ld+json → the data graph

    "every resource IRI is dereferenceable with content negotiation (W3C Linked Data best practice): a browser (Accept: text/html) is redirected to the human page, while an RDF client (Accept: application/ld+json) gets the data graph at the same /resource/<id> URL."

    Information-Systems-Modelling/lab6/app/src/server.js, 2026-07-09

    The server is node:http and nothing else — see zero-dependency-no-build-step. The same source tree runs as a live SSR server (npm run dev) or emits a static site into dist/.

    #3. A shared vocabulary first, a private one only where needed

    Terms come from schema.org wherever schema.org has them, and from the mc: namespace of the lab 5 TBox where it does not — see schema-org-first-custom-vocab-fallback and ontology-modelling-tbox-abox. src/rdf/vocabmap.js applies the rule programmatically rather than by hand, and writes a VOCAB MAP provenance comment into every generated page by walking that page's own graph, so the comment cannot go stale the way a hand-maintained one would. That is provenance-and-limits-stated-inline applied to machine-readable output.

    #Verification is a script that prints, not a test that fails

    lab6/app/scripts/validate.py uses rdflib to count triples per page and site-wide. The README reports 333 triples across the site and 76 for build-falcon.html.

    • TODO: validate.py prints counts and asserts nothing, so any edit to data/*.json silently invalidates those numbers without failing anything. confidence: low on the counts as stated. Converting the script to assertions would fix it.
