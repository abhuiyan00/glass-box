    Ontology Modelling: TBox and ABox

    An RDF knowledge base splits into two halves that live in the same triple store but answer different questions:

    • TBox (terminology) — the schema. What classes exist, how they specialise each other, what properties connect them, what their domains and ranges are. "A Builder is a User is a Person is an Agent."
    • ABox (assertions) — the instances. "mc:alice is a mc:Builder."

    The split is what makes a reasoner useful. Load both, and the store can derive facts nobody wrote: assert mc:alice a mc:Builder, and RDFS inference over rdfs:subClassOf answers "list all Agents" with Alice in it. In a relational schema the same question needs a join the modeller anticipated; here it needs no query change at all.

    #How lab 5 realises it

    Information-Systems-Modelling lab 5 keeps the halves in separate Turtle files under src/main/resources/, and App.java loads them into an in-memory rdf4j repository wrapped in an RDFS inferencer:

    File Role Lines
    ontology.ttlTBox — the ModellingClub vocabulary577
    sample-data.ttlABox — instances209

    The TBox declares a real taxonomy rather than a flat list of types: 24 rdfs:subClassOf statements, rooted at mc:Agent → mc:Person / mc:SystemAccount, then mc:User → mc:AdminUser / mc:Builder, each class carrying an rdfs:label and an rdfs:comment. Every term is namespaced under http://modellingclub.local/ontology# and the ontology resource itself carries owl:Ontology metadata with a Dublin Core title, description and creator.

    Eight SPARQL SELECT queries run against the loaded store. Two of them exist specifically to prove the reasoner is doing work rather than the data: listInferredKnowsLinks (a symmetric property returning links nobody asserted in that direction) and listTransitiveCommunityMembership. The others — builds with creators, approved builds by score, drone telemetry, votes per build, marketplace listings, test-run attendees — are ordinary retrieval.

    SampleDataWriter.addAdditionalUser also writes triples programmatically before querying, so the same store is exercised through both a file loader and the RDF4J model API.

    #Where the TBox goes next

    The identical ontology.ttl reappears in lab6/vocabulary/ and becomes the fallback vocabulary for linked-data-publishing — where schema.org has no term, the mc: term from this TBox is used instead. See schema-org-first-custom-vocab-fallback.

    The two copies are byte-identical rather than shared, which is a small instance of keep-the-superseded-version-in-tree and sits awkwardly beside lab 6's own headline principle that no fact should be written twice.
